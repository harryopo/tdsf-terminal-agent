## 1. 摘要

TDSF Terminal Agent 是一款面向 Linux 运维教学场景的桌面应用，采用 **Tauri 2（Rust）+ React 19（TypeScript）+ Python Sidecar（LangGraph）** 三进程分离架构，将终端操作、SSH 远程管理、AI 智能辅助与离线知识库深度融合。

系统核心创新包括：
- **三进程分离架构**：Rust 主进程负责系统级操作与安全边界，React 前端专注 UI 渲染，Python Sidecar 承载 AI 推理，三者松耦合通信。
- **PAOR 监督循环**：基于 LangGraph 的 7 节点状态图（supervisor → plan → act → tool_call → permission_check → observe → reflect），实现 AI Agent 的自主决策闭环。
- **9 Agent + 9 MCP 工具**：9 个专职 Agent 覆盖运维教学全场景，9 个 MCP 工具提供风险评估、置信度融合、知识接地、决策引擎等能力。
- **离线知识库双路检索**：ChromaDB 向量检索 + SQLite FTS5 关键词检索并行，兼顾语义与精确匹配。
- **安全审批机制**：AI 工具调用分级审批，结合 4 层风险评估管道，确保操作安全可控。

本文档详细阐述系统的架构设计、通信协议、安全模型、AI Agent 系统、终端渲染池、SSH 管理、主题系统等核心技术内容。

## 2. 引言

### 2.1 背景

Linux 运维是计算机科学教育的核心技能，但教学过程中面临多重挑战：命令复杂度高、实践环境碎片化、知识获取低效、缺乏即时指导。传统方案中，学生需要同时使用终端模拟器、SSH 客户端、代码编辑器、浏览器等多个工具，工具之间缺乏协同，学习体验割裂。

近年来，AI 大语言模型（LLM）的快速发展为运维辅助提供了新的可能。然而，现有 AI 助手大多只能"纸上谈兵"——能回答问题，但无法直接操作终端；或者缺乏安全约束，可能执行危险命令。

### 2.2 目标

TDSF Terminal Agent 旨在构建一个**终端优先的 Linux 运维 AI 工作台**，实现以下目标：

1. **统一工作台**：将终端、SSH、文件管理、代码编辑、AI 辅助整合为一体化桌面应用。
2. **AI 可操作**：AI Agent 不仅能回答问题，还能通过 MCP 工具直接执行终端命令。
3. **安全可控**：AI 操作经过审批机制和风险评估，防止误操作。
4. **离线可用**：知识库本地化部署，无网络环境也能正常检索。
5. **可扩展**：支持 BYOA（Bring Your Own Agent）和技能系统扩展。

### 3.2 Tauri 主进程（Rust）

Tauri 主进程是系统的"安全堡垒"和"能力引擎"，所有 OS 级操作均通过 Rust 命令注册表执行。

#### 3.2.1 命令注册表

系统注册了 47+ 条 Tauri 命令，覆盖以下功能域：

| 功能域 | 命令示例 | 说明 |
|--------|---------|------|
| PTY 管理 | `pty_create`, `pty_write`, `pty_resize` | 本地终端生命周期管理 |
| SSH 连接 | `ssh_connect`, `ssh_disconnect`, `ssh_exec` | SSH 会话管理 |
| 文件系统 | `fs_read`, `fs_write`, `fs_list_dir` | 本地文件操作 |
| Git 操作 | `git_status`, `git_commit`, `git_push` | 版本控制 |
| 密钥管理 | `secret_get`, `secret_set`, `secret_delete` | OS 密钥库操作 |
| Sidecar | `sidecar_spawn`, `sidecar_send`, `sidecar_kill` | Python 进程管理 |
| 网络代理 | `proxy_start`, `proxy_stop` | 网络请求代理 |

#### 3.2.2 PTY 管理

基于 `portable-pty 0.9` 实现跨平台伪终端管理：

- 支持创建、读写、调整大小等完整生命周期操作。
- 与 xterm.js 前端通过 Tauri Event 实时同步终端输出。
- 支持多 PTY 实例并行，配合终端渲染池高效管理。

#### 3.2.3 SSH 客户端（russh）

基于 `russh 0.61` 的纯 Rust SSH 实现：

- 支持密码认证、公钥认证、SSH Agent 转发。
- 内建 SFTP 客户端（`russh-sftp 2.1`），支持远程文件浏览与传输。
- TOFU（Trust On First Use）主机密钥审批机制。
- 连接信息加密存储于 OS 密钥库。

#### 3.2.4 文件系统操作

提供完整的本地文件系统操作能力：

- 目录浏览、文件读写、元数据查询。
- 文件监视（watch）支持实时刷新。
- 路径安全校验，防止路径遍历攻击。

#### 3.2.5 Git 集成

基于 `git2 0.19`（libgit2 绑定）实现版本控制：

- 仓库状态查询、暂存、提交、推送。
- 分支管理、差异对比。
- 为前端源控制模块提供数据支撑。

#### 3.2.6 沙箱系统

- IPC 边界控制：所有 OS 操作必须经过 Rust 命令注册表，前端无法直接访问系统资源。
- 密钥存储：使用 `keyring 3.6` 调用 OS 原生密钥库（Windows Credential Manager / Linux Secret Service），敏感数据不写磁盘。
- SSRF 防护：DNS 固定 + 元数据端点屏蔽，防止 AI Agent 被诱导访问内部服务。
- 秘密路径拒绝列表：阻止访问敏感系统路径。

### 3.4 Python Sidecar 层

Python Sidecar 是系统的"智能核心"，由 Rust 主进程作为子进程启动，通过 JSON-RPC 2.0 over stdio 与主进程通信。

#### 3.4.1 LangGraph PAOR 循环

基于 LangGraph 构建的 7 节点状态图，实现 AI Agent 的自主决策闭环：

```
         ┌──────────────────────────────────────────────────┐
         │                                                    │
         ▼                                                    │
    ┌──────────┐    ┌──────┐    ┌──────┐    ┌────────────┐   │
    │supervisor│───▶│ plan │───▶│ act  │───▶│ tool_call  │   │
    └──────────┘    └──────┘    └──────┘    └────────────┘   │
         │                                        │            │
         │ (done/error)                           ▼            │
         │                               ┌─────────────────┐  │
         ▼                               │permission_check │  │
        END                              └─────────────────┘  │
                                                │              │
                    ┌──────────┐               ▼              │
                    │ reflect  │◀────── ┌──────────┐          │
                    └──────────┘        │ observe  │──────────┘
                         │              └──────────┘
                         │
                         └──▶ supervisor (循环)
```

各节点职责：

| 节点 | 职责 |
|------|------|
| `supervisor` | 监督节点：判断任务状态，决定继续或结束 |
| `plan` | 规划节点：分解任务，制定执行计划 |
| `act` | 执行节点：选择工具，构造调用参数 |
| `tool_call` | 工具调用节点：执行 MCP 工具 |
| `permission_check` | 权限检查节点：验证工具调用权限 |
| `observe` | 观察节点：收集执行结果 |
| `reflect` | 反思节点：评估结果，决定下一步 |

#### 3.4.2 Agent 系统

系统注册了 9 个 Agent，由 `AGENT_REGISTRY` 统一管理：

```python
AGENT_REGISTRY = {
    "main":     MainAgent,      # 主 Agent，任务分发
    "coding":   CodingAgent,    # 代码编写
    "explore":  ExploreAgent,   # 系统探索
    "history":  HistoryAgent,   # 历史案例
    "teach":    TeachAgent,     # 教学讲解
    "debug":    DebugAgent,     # 故障诊断
    "refactor": RefactorAgent,  # 代码重构
    "test":     TestAgent,      # 测试执行
    "deploy":   DeployAgent,    # 部署管理
}
```

所有 Agent 继承自 `BaseAgent`，通过模板方法模式实现 PAOR 单轮执行：

```python
class BaseAgent:
    def invoke(self, state: AgentState) -> PartialState:
        """PAOR 单轮执行（模板方法，子类不重写）"""
        # 1. plan 钩子
        plan_result = self.on_plan(state)
        # 2. act 钩子
        act_result = self.on_act(state)
        # 3. 工具调用（如有）
        tool_result = self.on_tool_call(state)
        # 4. observe 钩子
        observe_result = self.on_observe(state)
        # 5. reflect 钩子
        reflect_result = self.on_reflect(state)
        # 6. 返回状态更新
        return state_update
```

#### 3.4.3 MCP 工具

系统实现 9 个 MCP 工具，由 `TOOL_REGISTRY` 统一管理：

| 工具 | 函数 | 功能 |
|------|------|------|
| `risk` | `invoke_risk_tool` | 风险评估：4 层风控管道 → L0-L4 风险等级 |
| `confidence` | `invoke_confidence_tool` | 置信度融合：D-S + PCR5 证据融合算法 |
| `ground` | `invoke_ground_tool` | 知识接地：ChromaDB 向量 + FTS5 双路检索 |
| `decision` | `invoke_decision_tool` | 决策引擎：LangGraph DecisionEngine |
| `credibility` | `invoke_credibility_tool` | 可信度评估：来源 + 时效 + 一致性三维度 |
| `history` | `invoke_history_tool` | 历史案例：CRUD + 多维检索 |
| `worktree_fanout` | `invoke_worktree_fanout_tool` | git worktree 并行任务执行 |
| `rlm_fanout` | `invoke_rlm_fanout_tool` | 1-16 路并行子任务执行 + 结果聚合 |
| `steer_inject` | `invoke_steer_inject_tool` | 运行时向 Agent 注入指令 |

#### 3.4.4 知识库

知识库采用双路并行检索架构：

```
用户查询
    │
    ├──▶ ChromaDB 向量检索（语义相似度）──▶ 结果 A
    │
    └──▶ SQLite FTS5 关键词检索（精确匹配）──▶ 结果 B
                                                    │
                                          ┌─────────┘
                                          ▼
                                    结果融合排序
                                          │
                                          ▼
                                    返回 Top-K 结果
```

- **ChromaDB 向量检索**：将文档分块后嵌入向量空间，基于余弦相似度检索语义相近的内容。
- **SQLite FTS5 关键词检索**：基于全文索引精确匹配关键词，适合命令名、配置项等精确查询。
- **结果融合**：两路结果通过加权排序算法融合，兼顾语义与精确度。

## 4. 通信协议设计

### 4.1 Tauri IPC（前端 ↔ Rust）

前端通过 Tauri 提供的 `invoke` API 调用 Rust 命令：

```typescript
// 前端调用示例
import { invoke } from "@tauri-apps/api/core";

// 创建 PTY
const ptyId = await invoke("pty_create", { cols: 80, rows: 24 });

// 写入数据
await invoke("pty_write", { id: ptyId, data: "ls -la\n" });

// SSH 连接
const sshId = await invoke("ssh_connect", {
  host: "192.168.1.100",
  port: 22,
  username: "root",
  authMethod: "password",
  password: "***"
});
```

Tauri IPC 特性：
- 类型安全：命令参数和返回值由 Rust 类型系统保证。
- 异步非阻塞：所有命令返回 Promise。
- 权限控制：通过 Tauri capabilities 配置命令访问权限。

### 4.2 JSON-RPC 2.0 over stdio（Rust ↔ Python）

Rust 主进程与 Python Sidecar 通过标准输入/输出（stdio）进行 JSON-RPC 2.0 通信：

```
┌──────────────┐                    ┌──────────────────┐
│  Rust 主进程  │  stdin (请求)      │  Python Sidecar   │
│              │ ──────────────────▶ │                  │
│              │                     │  JSON-RPC 2.0     │
│              │  stdout (响应)      │  Server           │
│              │ ◀────────────────── │                  │
└──────────────┘                    └──────────────────┘
```

JSON-RPC 消息格式：

```json
// 请求（Rust → Python）
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "agent.invoke",
  "params": {
    "agent": "main",
    "message": "查看当前系统负载",
    "session_id": "abc-123"
  }
}

// 响应（Python → Rust）
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "status": "done",
    "response": "当前系统负载：load average: 0.52, 0.38, 0.41",
    "agent": "main"
  }
}
```

已注册的 JSON-RPC 方法：

| 方法 | 说明 |
|------|------|
| `agent.invoke` | 调用指定 Agent 执行任务 |
| `agent.list` | 获取已注册 Agent 列表 |
| `knowledge.search` | 知识库检索 |
| `knowledge.add` | 添加知识条目 |
| `history.search` | 历史案例检索 |
| `tool.invoke` | 调用指定 MCP 工具 |
| `system.ping` | 健康检查 |
| `system.shutdown` | 优雅关闭 |

### 4.3 Tauri Event 转发（Python → 前端）

Python Sidecar 的实时事件（如 Agent 消息、工具调用进度）通过以下路径转发至前端：

```
Python Sidecar
    │
    │  stdout (JSON-RPC Notification)
    ▼
Rust 主进程
    │
    │  Tauri Event emit
    ▼
WebView 前端
    │
    │  Event listener 回调
    ▼
UI 更新（AI 面板、Agent 状态等）
```

事件类型：

| 事件 | 说明 |
|------|------|
| `agent_message` | Agent 消息推送（AI 回复内容） |
| `tool_call` | 工具调用进度通知 |
| `agent_switch` | 主 Agent 路由到子 Agent 时推送 |
| `mood_change` | Agent 情绪状态变化 |

## 5. 安全模型

### 5.1 IPC 边界控制

TDSF Terminal Agent 的安全模型基于"最小权限"原则：

- **前端零权限**：WebView 前端无法直接访问文件系统、网络、进程等系统资源，所有操作必须通过 Tauri IPC 调用 Rust 命令。
- **命令注册表**：Rust 侧维护命令注册表，每个命令有明确的参数类型和权限要求。
- **Capabilities 配置**：通过 Tauri capabilities 文件精细控制命令的访问权限。

```
前端 ──invoke──▶ Rust 命令注册表 ──权限检查──▶ OS 操作
                         │
                         ▼
                   拒绝非法请求
```

### 5.2 密钥管理（keyring）

敏感数据（SSH 密码、API 密钥等）通过 `keyring 3.6` 存储于 OS 原生密钥库：

- **Windows**：Credential Manager
- **Linux**：Secret Service（GNOME Keyring / KWallet）
- **macOS**：Keychain

密钥不写磁盘，不存配置文件，进程退出后密钥仍安全存储于 OS 密钥库中。

### 5.3 AI 工具审批机制

AI Agent 调用工具时，根据操作风险等级执行不同策略：

```
AI 工具调用请求
       │
       ▼
 ┌─────────────┐
 │ 风险评估工具  │  ← risk MCP tool
 └─────────────┘
       │
       ▼
 ┌─────────────────────────────────┐
 │ 风险等级判定                       │
 │                                   │
 │ 只读操作 (L0)  → 自动执行          │
 │ 低风险 (L1)    → 自动执行 + 日志   │
 │ 中风险 (L2)    → 用户审批          │
 │ 高风险 (L3-L4) → 强制审批 + 警告   │
 └─────────────────────────────────┘
```

审批流程：
1. AI Agent 构造工具调用参数。
2. `risk` 工具评估操作风险等级。
3. 只读操作（如 `ls`、`cat`）自动执行。
4. 变更操作（如 `rm`、`systemctl restart`）弹出审批对话框。
5. 用户确认后执行，拒绝则取消。

### 5.4 SSRF 防护

为防止 AI Agent 被诱导访问内部服务（如云元数据端点 `169.254.169.254`），系统实施以下防护：

- **DNS 固定**：关键域名解析结果缓存，防止 DNS 重绑定攻击。
- **元数据端点屏蔽**：硬编码屏蔽云服务商元数据端点 IP 段。
- **秘密路径拒绝列表**：阻止访问 `/etc/shadow`、`~/.ssh/id_rsa` 等敏感路径。
- **网络请求白名单**：AI Agent 的网络请求受白名单限制。

## 6. AI Agent 系统设计

### 6.1 PAOR 监督循环（7 节点）

PAOR（Plan-Act-Observe-Reflect）监督循环是 TDSF Terminal Agent AI 系统的核心架构，基于 LangGraph 的 `StateGraph` 实现：

```python
# graph/graph.py 核心逻辑
builder = StateGraph(AgentState)

# 添加 7 个节点
builder.add_node("supervisor", supervisor_node)
builder.add_node("plan", plan_node)
builder.add_node("act", act_node)
builder.add_node("observe", observe_node)
builder.add_node("reflect", reflect_node)
builder.add_node("tool_call", tool_call_node)
builder.add_node("permission_check", permission_check_node)

# 添加边
builder.add_edge(START, "supervisor")
builder.add_conditional_edges("supervisor", route_from_supervisor, 
    {"plan": "plan", "end": END})
builder.add_edge("plan", "act")
builder.add_edge("act", "tool_call")
builder.add_edge("tool_call", "permission_check")
builder.add_conditional_edges("permission_check", route_from_permission,
    {"observe": "observe", "supervisor": "supervisor"})
builder.add_edge("observe", "reflect")
builder.add_conditional_edges("reflect", route_from_reflect,
    {"supervisor": "supervisor", "end": END})
```

状态流转：

| 流转 | 条件 |
|------|------|
| supervisor → plan | 任务继续执行 |
| supervisor → END | 任务完成或出错 |
| plan → act | 规划完成 |
| act → tool_call | 需要调用工具 |
| tool_call → permission_check | 工具调用构造完成 |
| permission_check → observe | 权限验证通过 |
| permission_check → supervisor | 权限被拒绝，回到监督 |
| observe → reflect | 观察完成 |
| reflect → supervisor | 需要继续循环 |
| reflect → END | 任务完成 |

### 6.2 多 Agent 协作（9 个 Agent）

系统采用"主 Agent + 子 Agent"的协作模式：

```
用户请求
    │
    ▼
┌──────────┐
│   main   │  ← 主 Agent：理解意图，分发任务
└──────────┘
    │
    ├──▶ coding    代码编写任务
    ├──▶ explore   系统探索任务
    ├──▶ history   历史查询任务
    ├──▶ teach     教学讲解任务
    ├──▶ debug     故障诊断任务
    ├──▶ refactor  代码重构任务
    ├──▶ test      测试执行任务
    └──▶ deploy    部署管理任务
```

主 Agent（`MainAgent`）职责：
1. 理解用户请求意图。
2. 选择合适的子 Agent 处理。
3. 协调多 Agent 执行顺序。
4. 汇总子 Agent 结果，生成最终回复。

子 Agent 职责：
- 每个子 Agent 专注于特定领域，拥有专属工具集和系统提示词。
- 子 Agent 通过 `BaseAgent.invoke()` 模板方法执行 PAOR 单轮。
- 执行结果返回主 Agent，由主 Agent 决定是否继续路由。

BYOA（Bring Your Own Agent）扩展：
- 用户可通过 `AGENT_REGISTRY` 注册自定义 Agent。
- 自定义 Agent 继承 `BaseAgent`，实现 PAOR 钩子方法。
- 运行时通过 `steer_inject` 工具动态注入指令。

### 6.3 知识库双路检索

知识库系统采用双路并行检索架构，兼顾语义相似度和精确匹配：

**路径一：ChromaDB 向量检索**

```
文档 → 分块 → Embedding 模型 → 向量 → ChromaDB 存储
                                              │
查询 → Embedding 模型 → 查询向量 ──────────────┤
                                              │
                                         余弦相似度
                                              │
                                         Top-K 结果
```

- 适用场景：语义相近的内容检索，如"如何配置 Nginx 反向代理"。
- 优势：理解查询意图，即使用词不同也能匹配。

**路径二：SQLite FTS5 关键词检索**

```
文档 → 分词 → SQLite FTS5 索引
                    │
查询 → 分词 → 关键词 ──▶ FTS5 MATCH ──▶ Top-K 结果
```

- 适用场景：精确命令名、配置项、错误码检索，如"error 502 bad gateway"。
- 优势：精确匹配，速度快。

**结果融合**：两路结果通过加权排序融合，最终返回 Top-K 条最相关的知识条目。

### 6.4 技能系统

技能系统（Skills）提供预置的运维操作模板：

- 每个技能封装一组相关命令和操作步骤。
- 技能卡片式展示，支持搜索和分类。
- 一键执行，自动触发 AI Agent 完成操作。
- 支持自定义技能扩展。

## 7. 终端渲染池架构

终端渲染池是 TDSF Terminal Agent 前端的核心创新，解决多终端实例的性能问题。

### 7.1 设计目标

- 避免频繁创建/销毁 xterm.js 实例带来的内存和 CPU 开销。
- 支持快速切换终端标签页，无需重新渲染。
- 控制最大活跃终端数量，防止资源耗尽。

### 7.2 架构设计

```
┌─────────────────────────────────────────────┐
│              Terminal Pool Manager            │
│                                               │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐        │
│  │ Slot 0  │ │ Slot 1  │ │ Slot 2  │ ...    │
│  │ (active)│ │ (active)│ │ (idle)  │        │
│  └─────────┘ └─────────┘ └─────────┘        │
│                                               │
│  最大活跃槽位：5                                │
│                                               │
│  ┌───────────────────────────────────────┐    │
│  │         DormantRing (回收环)            │    │
│  │  休眠实例缓存，快速复用                   │    │
│  └───────────────────────────────────────┘    │
└─────────────────────────────────────────────┘
```

### 7.3 工作流程

1. **创建终端**：从空闲槽位分配，或从 DormantRing 回收休眠实例。
2. **切换标签**：活跃实例保持状态，非活跃实例进入 DormantRing。
3. **回收机制**：超过最大槽位数时，最久未使用的实例进入 DormantRing。
4. **复用实例**：新终端请求优先从 DormantRing 获取已初始化的 xterm.js 实例，重置状态后复用。

### 7.4 性能优势

- 终端切换延迟从秒级降至毫秒级（复用已初始化实例）。
- 内存占用可控（最大 5 活跃 + DormantRing 缓存）。
- 避免 xterm.js 频繁创建/销毁导致的 DOM 碎片。

## 8. SSH 远程管理

### 8.1 SSH 客户端

基于 `russh 0.61` 实现的纯 Rust SSH 客户端：

- **认证方式**：密码认证、公钥认证、SSH Agent 转发。
- **通道管理**：支持多通道并行（会话通道、端口转发）。
- **Keep-Alive**：自动心跳保活，防止连接超时。

### 8.2 SSH 资源管理器

前端 `ssh-explorer` 模块提供可视化的远程主机管理：

- 主机列表管理（增删改查）。
- 连接信息加密存储（keyring）。
- 一键连接，自动打开终端标签。
- 连接状态实时显示。

### 8.3 远程文件管理

基于 `russh-sftp 2.1` 实现的 SFTP 文件管理器：

- 远程目录树浏览。
- 文件上传/下载（支持拖拽）。
- 远程文件在线编辑（Monaco Editor）。
- 文件权限查看与修改。

### 8.4 TOFU 主机密钥审批

采用 TOFU（Trust On First Use）机制：

1. 首次连接时，展示服务器主机密钥指纹。
2. 用户确认后，密钥存储于本地信任库。
3. 后续连接自动验证密钥，防止中间人攻击。
4. 密钥变化时发出警告。

## 12. 总结与展望

### 12.1 总结

TDSF Terminal Agent 通过创新的三进程分离架构，将 Rust 的系统级能力、React 的 UI 表现力、Python 的 AI 生态完美融合。PAOR 监督循环确保 AI Agent 行为可控，9 个专职 Agent 覆盖运维教学全场景，双路知识库支撑离线检索，安全审批机制防止误操作。

- **协作教学**：支持多人协作教学场景，教师可远程监控和指导学生。
- **插件生态**：开放插件 API，构建第三方开发者生态。
- **跨平台深化**：优化 macOS 和 Linux 桌面体验，实现真正的全平台覆盖。

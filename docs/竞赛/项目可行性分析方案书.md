## 1. 项目概述

### 1.1 项目名称

**TDSF Terminal Agent** —— 面向 Linux 教学的一体化智能终端工作台

### 1.2 项目定位

TDSF Terminal Agent 是一款集成 SSH 远程管理、AI 辅助对话、离线知识库与终端操作于一体的桌面应用，旨在为 Linux 教学场景提供"开箱即用"的终端工作环境。学生可通过统一界面完成远程连接、文件管理、代码编辑和 AI 辅助学习，降低 Linux 学习门槛。

### 1.3 上游关系说明

本项目基于开源项目 **crynta/terax-ai v0.8.6**（Apache-2.0 许可证）进行深度定制与优化。上游项目提供了完整的编辑器骨架与终端基础能力，本项目在其基础上：

- 新增 SSH 远程终端深度集成（rendererPool 方案）
- 新增 Strands Agent 框架集成（v1.50.2）
- 新增 Rust 层 ssh_command 远程命令执行
- 新增 SSH 文件编辑器（多 tab + CodeMirror）
- 修复了上游存在的 9 项 P0/P1 级缺陷
- 完成 Command Palette 全量汉化与界面本地化
- 建立了知识沉淀体系（4 层文档架构）

上游开源代码的使用严格遵守 Apache-2.0 许可证要求，详见项目 `LICENSE` 文件及 `docs/OPEN-SOURCE-AND-MODIFICATIONS.md`。

## 2. 项目目标

### 2.1 要解决的问题

| 问题 | 现状描述 |
|------|----------|
| Linux 教学环境分散 | 学生需在 SSH 客户端、编辑器、浏览器之间频繁切换，工具链割裂 |

- **主要用户**：高校 Linux 课程学生，需要频繁进行 SSH 远程操作
- **次要用户**：Linux 教学教师，需要演示和指导学生操作
- **扩展用户**：需要统一终端工作台的开发运维人员

## 3. 技术可行性分析

### 3.1 技术选型可行性

#### 为什么选择 Tauri 2 而非 Electron

| 对比维度 | Tauri 2 | Electron |
|----------|---------|----------|
| 安装包体积 | ~10-15 MB | ~150+ MB |
| 内存占用 | 显著更低（复用系统 WebView） | 内嵌 Chromium，内存开销大 |
| 原生能力 | Rust 后端，系统级性能 | Node.js 后端，性能有上限 |
| 安全性 | Rust 类型安全 + 权限能力模型 | 依赖 Node.js 安全模型 |
| 教学场景适配 | 学生机器配置参差不齐，轻量级更友好 | — |

**结论**：Tauri 2 在体积、性能、安全性方面均优于 Electron，更适合教学环境下大规模部署。

#### 为什么采用三进程架构

```
┌─────────────┐     ┌──────────────┐     ┌─────────────────┐
│  前端渲染层   │────▶│  Rust 主进程  │────▶│  Python Sidecar  │
│  React 19    │ IPC │  Tauri 2     │     │  LangGraph/      │
│  Vite 6      │     │  PTY/SSH/SFTP│     │  Strands Agent   │
└─────────────┘     └──────────────┘     └─────────────────┘
```

- **前端层**：负责 UI 渲染与用户交互，使用 React 19 + TypeScript 5.7
- **Rust 主进程**：负责系统级操作（PTY 伪终端、SSH 连接、SFTP 文件传输、进程管理），保证性能与安全
- **Python Sidecar**：负责 AI 推理逻辑（LangGraph/Strands Agent 框架），利用 Python 生态的 AI 工具链

三进程隔离的好处：前端崩溃不影响终端连接，AI 推理崩溃不影响文件操作，各层可独立升级。

#### 关键技术决策分析

**1. 为什么选择 LangGraph + Strands 双框架？**

项目最初采用 LangGraph 作为 Agent 编排框架，后续引入 Strands Agents SDK 作为执行引擎，两者互补：

| 维度 | LangGraph | Strands Agents SDK |
|------|-----------|-------------------|
| 定位 | Agent 编排与状态图管理 | Agent 执行与工具调用 |
| 优势 | 可视化状态流转、条件路由 | 轻量级、工具调用高效 |
| 适用场景 | 多 Agent 协作编排 | 单 Agent 快速执行 |
| 当前状态 | 已集成，用于 Agent 定义 | 已集成 v1.50.2，端到端实测通过 |

双框架方案让项目既能利用 LangGraph 的编排能力处理复杂多 Agent 场景，又能通过 Strands 实现高效的单 Agent 执行。

**2. 为什么选择 russh 而非其他 SSH 库？**

| 方案 | 语言 | 优势 | 劣势 |
|------|------|------|------|
| russh 0.61 | Rust | 纯 Rust 实现，类型安全，与 Tauri 天然集成 | 生态相对小众 |
| libssh2-sys | Rust（FFI） | 成熟稳定 | C FFI 绑定，安全隐患 |
| ssh2（Node.js） | JS | 前端直接调用 | 性能差，无法利用 Rust 安全特性 |

选择 russh 的理由：纯 Rust 实现保证了内存安全，与 Tauri 2 的 Rust 后端天然集成，无需跨语言 FFI，且 0.61 版本已支持 async/await 语法。

**3. 为什么选择 portable-pty 管理终端？**

portable-pty 是 WezTerm 终端模拟器项目的一部分，经过大规模实际使用验证。它提供跨平台（Windows/macOS/Linux）的伪终端抽象，屏蔽了 Windows ConPTY 与 POSIX pty 的差异，让应用代码无需区分平台。

**4. 前端模块架构**

项目前端采用模块化设计，共 25 个功能模块，核心模块职责如下：


**5. 安全模型**

项目采用多层安全设计：

- **Tauri 能力模型**：通过 `capabilities/` 目录声明式权限控制，前端只能调用已授权的 Rust 命令
- **CSP 策略**：配置了严格的 Content-Security-Policy，限制脚本来源、禁止 `object-src`、限制 `form-action`
- **SSH 密钥管理**：通过 keyring 3.6 集成系统密钥链，密钥不明文存储
- **Sidecar 隔离**：Python Sidecar 作为独立进程运行，通过 IPC 通信，无法直接访问文件系统
- **资产协议**：仅启用 `protocol-asset` 特性，限制文件访问范围

### 3.3 技术风险分析

#### 已识别的技术风险

| 风险编号 | 风险描述 | 严重等级 | 当前状态 |
|----------|----------|----------|----------|
| R1 | Strands 工具调用无 fix-loop 保护，可能导致无限循环 | 高 | 未修复 |
| R2 | Strands 模式下 main_agent PAOR 路由失效 | 高 | 未修复 |
| R3 | exec_command 失败后浪费 30s 超时才返回 | 中 | 未修复 |
| R4 | sidecar 流协议按 tool_name 配对在并发时可能错乱 | 中 | 未修复 |
| R5 | _agent_cache 无 LRU 淘汰机制，长时间运行存在内存泄漏风险 | 中 | 未修复 |
| R6 | TOFU 指纹验证引导未实现，首次连接未知主机体验不完整 | 低 | 未修复 |
| R7 | Python sidecar 长期运行稳定性仍需持续验证 | 中 | 持续优化中 |

#### 风险应对策略

- **R1/R2**：Strands 集成属于新增功能，当前基础流程可跑通，fix-loop 和路由问题计划在后续迭代中优先解决
- **R3**：可通过添加超时配置项缓解，不影响核心功能
- **R4**：并发场景下的小概率问题，当前单用户使用场景下风险可控
- **R5/R6**：属于健壮性优化，不影响功能演示
- **R7**：已添加 health 监控 + 指数退避重启机制，风险已大幅降低

### 3.5 技术架构与实现

#### 3.5.1 三进程架构详解

项目采用三进程隔离架构，每个进程职责明确、独立运行、通过 IPC 通信：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           TDSF Terminal Agent                               │
│                                                                             │
│  ┌───────────────────┐    IPC     ┌───────────────────┐    IPC     ┌───────────────────┐
│  │   前端渲染进程      │◀────────▶│   Rust 主进程       │◀────────▶│  Python Sidecar    │
│  │   (WebView2)       │          │   (Tauri 2)        │          │   (子进程)          │
│  │                    │          │                    │          │                    │
│  │  React 19 + Vite 6 │          │  PTY / SSH / SFTP  │          │  LangGraph Agent   │
│  │  TypeScript 5.7    │          │  文件系统 / Git     │          │  Strands Agent     │
│  │  Monaco Editor     │          │  Sidecar 管理      │          │  知识库 / 技能      │
│  │  xterm.js          │          │  进程管理 / IPC    │          │  工具调用引擎      │

```

**进程间通信机制：**

- **前端 ↔ Rust**：Tauri 2 内置 IPC，前端通过 `invoke()` 调用 Rust 命令，Rust 通过事件向前端推送消息
- **Rust ↔ Python**：Rust 以子进程方式启动 Python Sidecar，通过 stdin/stdout JSON-RPC 协议通信
- **前端 ↔ Python**：不直接通信，所有请求经 Rust 中转，保证安全隔离

#### 3.5.6 架构设计亮点

**1. rendererPool 终端渲染池**

终端实例创建开销较大，项目实现了渲染池复用机制。本地终端和 SSH 远程终端共享同一个渲染池，避免重复创建/销毁 xterm.js 实例，显著提升多 tab 场景下的性能。

**2. Sidecar 指数退避重启**

Python Sidecar 崩溃后，Rust 层 `sidecar.rs` 实现了 MAX_RETRY=5 的指数退避重启策略（1s → 2s → 4s → 8s → 16s），避免频繁重启导致的资源浪费。同时通过 `sidecar.health` RPC 实时推送健康状态。

**3. 多 Agent 协作体系**

11 个专职 Agent 各司其职，由 main_agent 通过 PAOR（Plan-Act-Observe-Route）模式统一调度。每个 Agent 有独立的工具集和上下文管理，支持任务交接（handoff_manager）和循环保护（fix_loop）。

**4. 安全多层防护**

- Tauri 能力模型限制前端可调用的 Rust 命令
- CSP 策略限制脚本来源
- keyring 系统密钥链存储 SSH 凭据
- Python Sidecar 进程隔离，无法直接访问文件系统
- RiskEngine 高危命令拦截（permissions.py）
- 沙箱执行环境（sandbox_proxy.py）

- **LangGraph**：多 Agent 编排，可视化状态流转
- **Strands Agents SDK v1.50.2**：轻量级单 Agent 执行

用户需自行配置 LLM API Key（已实测 DeepSeek 端到端通过）。支持流式响应、工具调用、reasoning 过程展示。

**5. 离线知识库**

基于 ChromaDB 0.5 本地向量数据库，支持知识文档导入与语义检索。内置 Linux + 编程术语词典，支持离线术语翻译。知识沉淀体系包含 4 层文档架构（KNOWLEDGE-INDEX.md + HANDOVER.md）。

**6. 技能系统**

内置 5 个技能，通过 skill.invoke RPC 调用。支持技能元数据统一转换（dictToMetadata），技能执行结果实时反馈。

**7. BackendPill 后端状态监控**

通过 sidecar.health RPC 推送 7 字段状态（包括 health、uptime、memory 等），前端以 Pill 组件实时显示后端健康状态。支持 MockLLM 告警提示。

### 7.3 已知问题和限制

**P1 级（Strands 相关新问题，4 项）：**

1. Strands 工具调用无 fix-loop 保护 —— 可能导致 Agent 陷入无限工具调用循环
2. Strands 模式下 main_agent PAOR 路由失效 —— 多 Agent 切换场景受影响
3. exec_command Failure 后浪费 30s 超时 —— 影响用户体验响应速度
4. sidecar 流协议按 tool_name 配对在并发时可能错乱 —— 高并发场景下的数据一致性风险

**P2 级（6 项）：**

5. TOFU 指纹验证引导未实现 —— 首次连接未知主机时缺少指纹确认引导
6. _agent_cache 无 LRU 淘汰机制 —— 长时间运行存在内存泄漏风险
7. Strands invoke 不推 agent_switch 事件 —— UI 无法感知 Agent 切换
8. 资源管理器按目录缓存性能优化 —— 大目录场景的体验优化
9. 远程 LSP over SSH —— 远程代码智能提示功能未实现
10. asciicast v2 会话录制（教学回放）—— 教学场景核心功能，尚未开发

# Agent 真实稳定性执行基线（2026-09-06）

> **地位**：这是当前可执行的工程基线，补充而不改写用户工作区中的 `docs/方案书-v2.0.md`。产品范围仍以 v2.0 为准；本文件只定义什么能够如实称为“完成”、以什么证据验收，以及下一步实现顺序。
>
> **核心原则**：没有真实输入、真实工具结果、真实终端退出状态或真实原生验收，就只能显示“未知/待验证”，不能由提示词、启发式文字或 UI 占位替代。

## 1. 已确认的当前架构

```text
React UI / Zustand
  -> Tauri IPC 与事件
    -> Rust SidecarManager、SSH/PTY、终端 OSC 生命周期
      -> Python JSON-RPC sidecar
        -> StrandsAgentAdapter（唯一 main Agent）
          -> TOOL_REGISTRY、risk / approval、知识库、Skill、RustBridge
```

- 当前运行链不是多 Agent 委派图：`main` 是唯一 Strands 会话 Agent；教学是模式约束和渲染协议，知识库是只读工具。
- 确认面板的唯一可执行来源是 sidecar `needs_you`；同一 SSH 会话通过 FIFO 一次只放行一个待确认命令。
- 教学命令卡的唯一结果来源是终端生命周期收集到的 `TerminalBlock`，而不是模型自述或从知识检索文本中猜测。
- 2026-09-06 已实际启动 Tauri 开发端：Vite、Rust 桌面进程和 Python sidecar 均进入 ready；sidecar 注册 121 个 RPC，知识库现有 3969 条官方条目。此证据只证明启动链健康，不等于已完成系统钥匙串、SSH、xterm 或 UI 的原生交互验收。

## 2. 不可违反的事实约束

| 领域 | 允许作为事实来源 | 禁止的替代品 |
|---|---|---|
| 命令已成功 | 同一 leaf 的终端块，非空命令且 `exitCode === 0` | 用户按下 Enter、模型说“已执行”、没有退出码的文本 |
| 命令失败 | 同一 leaf 的终端块，非零退出码 | 以失败输出写入预测或成功历史 |
| 命令结果未知 | 超时、缺块、空退出码、leaf 不匹配 | 将“可能已执行”渲染为成功 |
| 教学继续讲解 | 用户点击命令卡后，与该卡精确匹配的真实终端块 | 自动监听每条命令、最后一条命令全局变量、知识检索内容 |
| 知识库结论 | 实际 `knowledge_*` 工具事件、文档 ID 与已返回片段 | “似乎检索过”的模型说明或教学皮肤 |
| 历史会话 | 已保存 endpoint 配置实际连接成功后加载 | 仅凭 host 名称、跨 endpoint 猜测打开 |
| 写入操作完成 | durable operation 已记录状态与真实结果 | “批准过”或前端按钮已点击 |

## 3. 本轮已经落地的 W2 最小闭环

现有 `TerminalBlock` 是当前可信的终端协议载体：

```text
sessionId, command, cwd, exitCode, durationMs,
author, outputTail, startedAt
```

本轮将它接入两个边界明确的消费者：

1. `terminalBlocksStore` 仅在“非空命令 + `exitCode === 0`”时调用 `executionHistory.recordSuccessfulTerminalBlock`。
2. `executionHistory` 同时更新 Rust 交互历史和建议引擎的对应系统族历史；失败、空退出码和空命令都不会污染预测。
3. 删除旧的 OSC 7 自动教学触发器及其“最后提交命令”记忆。教学现在只由命令卡、精确命令匹配、用户点击和真实结果串联。
4. 设置页仅保留“手动错误讲解”入口，明确其不执行命令、不自动讲解、不生成教学历史。

这不是完整的 durable execution：`TerminalBlock` 尚未是可持久重放的 `CommandCompletion` 账本，也没有跨重启的 `operation_id`。因此 W2 状态为**局部完成**，W3 仍是 P0 稳定性工作。

## 4. 交付阶段与验收门槛

### W0：原生实测证据

目标是将当前“启动健康”扩展为真实桌面端取证。必须使用已保存 SSH profile，在不改变远端状态的命令上逐项记录：

1. 连接成功、缺失 profile、端口不匹配和历史会话重开。
2. 同一会话的确认 FIFO：批准、拒绝、超时、上一命令结束后才显示下一命令。
3. 只读命令的 `TerminalBlock`、exit code、输出归属和 leaf 隔离。
4. 教学卡在成功、失败、超时、不同 leaf、相同命令重试时的匹配结果。
5. 知识库工具 started/completed UI 与普通 Markdown/TeachCard 的分类。

验收产物：脱敏的开发日志、截图或录像、对应会话/命令 ID，以及失败时的可复现步骤。没有这些产物不得勾选 W0。

### W1：发行版感知

已完成安全的 `os_family` 解析、候选过滤及当前 SSH 会话状态显示；未完成真实 RHEL/Debian SSH 回归。验收必须验证未知系统不会被猜测为某个发行版。

### W2：执行事实与教学协议

已完成成功历史的最小闭环和教学自动触发删除。下一小步是把本节 `TerminalBlock` 固化成附加式 `CommandCompletion`：

- 为每个完成事件赋稳定 completion ID、规范化命令 hash、来源和时间；
- 明确 `succeeded / failed / unknown` 三态，禁止将 unknown 用作预测；
- 保留失败输出供“解释失败”教学使用，但不写入成功建议；
- 针对重复 OSC、乱序 block、跨 leaf 和重连后的 block 增加 fixture。

### W3：durable operation（最高稳定性优先级）

所有可能改变远端状态的请求应先写入最小 SQLite 账本：

```text
created -> awaiting_approval -> approved -> dispatching -> dispatched
       -> succeeded | failed | cancelled | indeterminate
```

- `operation_id` 与 `intent_id` 在批准前生成；记录目标 endpoint fingerprint、命令 hash、创建/批准/派发时间。
- Rust SSH 派发带同一 `operation_id`；Python 和前端只依据 ID 更新状态。
- 进程中断时，`dispatching/dispatched` 一律变为 `indeterminate`，只允许只读验证；绝不自动重发可能写入远端的命令。
- 先做 schema migration、状态机非法跳转测试、崩溃注入和重复 invoke 测试，再接入真实写操作。

### W4：回答与来源完整性

仅当工具事件返回可定位 source ID、文档 ID 或命令 completion ID 时，才可以把它绑定到回答/教学段落。缺来源、工具失败或来源冲突必须显示“未验证”，而非伪造置信度。

### W5：体验功能

ghost text、命令工作流、known-hosts、ssh_config、安装建议和教学广播只在 W0-W4 有稳定证据接口后推进；它们不能绕过 operation、evidence 或终端协议。

## 5. 开发顺序与停止条件

1. 保持本轮 W2 改动小而可测试，先提交可回滚变更。
2. 用 W0 的真实 SSH 读命令取证，发现协议不一致时先修复事实源，再改 UI。
3. 设计并测试 W3 SQLite 状态机；未通过崩溃/幂等测试不得接入写 SSH 路径。
4. 完成 W4 的来源绑定后再扩展回答、教学和知识库展示。
5. 每个阶段的停止条件都是：失败案例有自动测试，前端 typecheck/lint/Vitest 通过，受影响的 Python/Rust 门禁通过，且原生边界有实际日志证据。

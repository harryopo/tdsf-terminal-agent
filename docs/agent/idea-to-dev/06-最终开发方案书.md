## 2. 核心算法与技术贡献

### 2.1 算法1：知识图谱增强的因果推理（参考AetherLog）

**创新点**：将非结构化日志通过知识图谱转化为结构化知识，约束LLM推理，减少幻觉。

**算法流程**：
```
离线阶段：
  知识库（9个md文件） → LLM实体关系提取 → 嵌入聚类（KMeans） → Linux运维知识图谱

在线阶段：
  故障日志 → LLM实体提取 → 知识图谱语义检索（Top-K） → 上下文增强Prompt → LLM推理 → 结构化输出
```

**核心公式**：
```
相似度(q, e) = cos(embed(q), embed(e))

增强Prompt = BasePrompt + RetrievedEntities(top_k=10) + FaultLogs

预期效果：F1-score提升6-8%（参考AetherLog）
```

**技术实现**：
```python
class LinuxKnowledgeGraph:
    """Linux运维知识图谱"""
    
    def __init__(self):
        self.entities = {}       # 实体库
        self.relations = []      # 关系库
        self.embeddings = []     # 实体嵌入向量
    
    def build_from_knowledge_base(self, kb_dir: str):
        """从现有知识库构建知识图谱"""
        docs = load_knowledge_base(kb_dir)
        
        for doc in docs:
            # LLM提取实体和关系
            entities = llm.extract_entities(doc)
            relations = llm.extract_relations(doc)
            
            for entity in entities:
                self.entities[entity.name] = entity
                self.embeddings.append(entity.embedding)
            
            self.relations.extend(relations)
        
        # 嵌入聚类（归一化）
        kmeans = KMeans(n_clusters=100)
        clusters = kmeans.fit_predict(self.embeddings)
        self.graph = self.build_graph(self.entities, self.relations, clusters)
    
    def retrieve_similar(self, query_entities: list, top_k: int = 10) -> list:
        """检索语义相似的实体"""
        query_embedding = self.encode(query_entities)
        similarities = cosine_similarity(query_embedding, self.embeddings)
        top_indices = similarities.argsort()[-top_k:][::-1]
        return [self.entities[i] for i in top_indices]
```

### 2.2 算法2：Prompt自动优化 + 历史案例检索（参考eARCO）

**创新点**：利用Decision Library中的历史案例自动优化Prompt，结合RAG检索增强。

**算法流程**：
```
离线阶段：
  Decision Library → PromptWizard自动优化 → 最优Prompt模板

在线阶段：
  故障日志 → 向量检索相似案例（Top-3） → 构建增强Prompt → LLM推理
```

**核心公式**：
```
优化目标：max E[score(prompt, case)] over prompt ∈ PromptSpace

增强Prompt = OptimizedPrompt + SimilarCases(top_k=3) + FaultLogs

预期效果：准确率提升21%（参考eARCO）
```

**技术实现**：
```python
class PromptOptimizer:
    """Prompt自动优化器"""
    
    def __init__(self):
        self.wizard = PromptWizard()
        self.decision_library = DecisionLibrary()
    
    def optimize_prompt(self) -> str:
        """优化Prompt模板"""
        historical_cases = self.decision_library.load_all()
        
        base_prompt = """
        你是一个Linux运维专家。根据以下日志分析故障根因。
        
        要求：
        1. 输出证据链（每条锚定到具体日志行）
        2. 区分"时间先后"和"因果关系"
        3. 列出排除假设及排除依据
        4. 输出修复命令及风险评估
        """
        
        optimized = self.wizard.optimize(
            base_prompt=base_prompt,
            historical_examples=historical_cases,
            iterations=10
        )
        return optimized

class EnhancedRCA:
    """增强的RCA引擎"""
    
    def reason(self, logs: str) -> dict:
        # 1. 检索相似案例
        similar_cases = self.decision_library.search_similar(logs, top_k=3)
        
        # 2. 构建增强Prompt
        prompt = self.build_enhanced_prompt(logs, similar_cases)
        
        # 3. LLM推理
        result = self.llm.generate(prompt)
        return result
```

### 2.3 算法3：因果超图推理（参考CHASE）

**创新点**：使用超图神经网络建模多对多因果关系，突破传统因果链限制。

**算法流程**：
```
多源日志 → 异常检测（多头注意力） → 因果超图构建 → 根因得分计算 → Top-K根因定位
```

**核心公式**：
```
异常评分：score(l) = attention(Q=l, K=logs, V=logs)

超边定义：e = {n₁, n₂, ..., nₖ}  （一条超边可连接多个节点）

根因得分：RCA(n) = Σ_{e∈hyperedges(n)} weight(e) × anomaly_score(n)

预期效果：A@1提升36.2%（参考CHASE）
```

**技术实现**：
```python
class CausalHyperGraph:
    """因果超图推理引擎"""
    
    def __init__(self):
        self.nodes = []          # 异常事件节点
        self.hyperedges = []     # 因果超边
        self.attention = nn.MultiheadAttention(embed_dim=256, num_heads=8)
    
    def build_from_logs(self, logs: list) -> list:
        """从日志构建因果超图"""
        # 1. 异常检测（注意力机制）
        anomalies = self.detect_anomalies_with_attention(logs)
        
        # 2. 构建超边（因果关系）
        for anomaly in anomalies:
            hyperedge = self.infer_causal_relations(anomaly, anomalies)
            self.hyperedges.append(hyperedge)
        
        # 3. 根因定位
        root_causes = self.localize_root_causes()
        return root_causes
    
    def detect_anomalies_with_attention(self, logs: list) -> list:
        """使用多头注意力检测异常"""
        log_embeddings = self.encode_logs(logs)
        attention_output, _ = self.attention(
            log_embeddings, log_embeddings, log_embeddings
        )
        anomaly_scores = self.compute_anomaly_scores(attention_output)
        
        return [log for log, score in zip(logs, anomaly_scores) if score > 0.8]
    
    def localize_root_causes(self, top_k: int = 3) -> list:
        """根因定位"""
        root_cause_scores = {}
        for node in self.nodes:
            score = self.compute_root_cause_score(node)
            root_cause_scores[node] = score
        
        sorted_nodes = sorted(root_cause_scores.items(), key=lambda x: x[1], reverse=True)
        return sorted_nodes[:top_k]
```

### 2.4 算法4：安全RCA Agent（规避12种失败模式）

**创新点**：基于OpenRCA论文发现的12种AI Agent失败模式，设计安全约束机制。

**12种失败模式及对策**：

| 失败模式 | 对策 | 实现方式 |
|---------|------|---------|
| 幻觉数据解释 | 证据链锚定 | 每条推理必须引用具体日志行 |
| 不完整探索 | 强制多源收集 | min_sources=3 |
| 过早收敛 | 多假设生成 | min_hypotheses=3 |
| 因果混淆 | 因果验证 | Granger因果检验 |
| 信息丢失 | 结构化传递 | JSON Schema约束 |
| 语义不一致 | 统一术语表 | 知识图谱实体对齐 |
| 协调失败 | 状态同步 | 共享上下文 |
| 工具调用失败 | 重试+降级 | 3次重试+fallback |
| 环境状态误判 | 多源验证 | 交叉验证 |
| 权限不足 | 权限检查 | 预检查+提示 |
| 超时 | 超时控制 | 30s超时+异步 |
| 数据格式错误 | 格式校验 | Pydantic Schema |

**技术实现**：
```python
class SafeRCAAgent:
    """规避12种失败模式的安全RCA Agent"""
    
    def reason(self, logs: str) -> dict:
        # 1. 强制多源收集（防止"不完整探索"）
        evidence = self.collect_evidence(logs, min_sources=3)
        
        # 2. 多假设生成（防止"过早收敛"）
        hypotheses = self.generate_hypotheses(evidence, min_count=3)
        
        # 3. 逐一验证（防止"因果混淆"）
        for hypothesis in hypotheses:
            validation = self.validate_causality(hypothesis, evidence)
            
            if validation.confidence > 0.8:
                # 锚定到具体日志行（防止"幻觉"）
                self.evidence_chain.append({
                    "hypothesis": hypothesis,
                    "log_lines": validation.log_lines,
                    "confidence": validation.confidence
                })
            else:
                self.rejected_hypotheses.append(hypothesis)
        
        return self.build_safe_result()
    
    def validate_causality(self, hypothesis, evidence) -> ValidationResult:
        """因果验证（区分时间先后和因果关系）"""
        # 1. 时间顺序检查
        if not self.check_temporal_order(hypothesis, evidence):
            return ValidationResult(confidence=0.0, reason="时间顺序不符")
        
        # 2. Granger因果检验
        causal_score = self.granger_causality_test(hypothesis, evidence)
        if causal_score < 0.7:
            return ValidationResult(confidence=causal_score, reason="因果关系不显著")
        
        # 3. 锚定到具体日志行
        log_lines = self.anchor_to_log_lines(hypothesis, evidence)
        return ValidationResult(confidence=causal_score, log_lines=log_lines)
```

### 2.5 算法5：HITL合规实现（EU AI Act Article 14）

**创新点**：实现5级自主模型，满足EU AI Act合规要求。

**5级自主模型**：

| 风险等级 | 自主级别 | 人类角色 | 实现方式 |
|---------|---------|---------|---------|
| 低（查询类） | L3 执行+否决窗口 | 监督执行 | 30秒否决窗口 |
| 中（配置类） | L2 提案+审批 | 审批执行 | 弹窗确认 |
| 高（删除/格式化） | L2 提案+审批 | 审批执行 | 二次确认+密码验证 |

**技术实现**：
```python
class HITLCompliance:
    """EU AI Act Article 14 合规实现"""
    
    AUTONOMY_LEVELS = {
        'low': 'L3',      # 执行+否决窗口
        'medium': 'L2',   # 提案+审批
        'high': 'L2'      # 提案+审批
    }
    
    def execute_with_oversight(self, action: dict, risk_level: str) -> dict:
        required_level = self.AUTONOMY_LEVELS[risk_level]
        
        if required_level == 'L2':
            proposal = self.build_proposal(action)
            approval = self.request_human_approval(proposal)
            if approval:
                result = self.execute(action)
                return {"status": "approved", "result": result}
            else:
                return {"status": "rejected"}
        
        elif required_level == 'L3':
            result = self.execute(action)
            vetoed = self.wait_for_veto(seconds=30)
            if vetoed:
                self.rollback(result)
                return {"status": "vetoed", "rolled_back": True}
            return {"status": "executed", "result": result}
```

**功能**：支持多源日志输入，时间对齐，噪声去除。

**输入**：多源日志文本（syslog/nginx/mysql/dmesg/app.log）

**处理流程**：
```
原始日志 → 格式识别 → 时间戳提取 → 时间对齐 → 噪声过滤 → 结构化输出
```

**输出**：
```json

  "time_range": {"start": "2026-07-10T10:00:00Z", "end": "2026-07-10T10:30:00Z"},

      "timestamp": "2026-07-10T10:05:23Z",
      "source": "nginx/error.log",
      "line_number": 123,
      "content": "upstream timed out (110: Connection timed out)",
      "severity": "error"
    }
  ]
}
```

### 4.2 知识图谱模块（knowledge_graph.py）

**功能**：从现有知识库构建Linux运维知识图谱，支持语义检索。

**核心类**：
```python
class LinuxKnowledgeGraph:
    def build_from_knowledge_base(self, kb_dir: str) -> None:
        """离线构建知识图谱"""
    
    def retrieve_similar(self, query: list, top_k: int = 10) -> list:
        """在线语义检索"""
    
    def get_entity_relations(self, entity_name: str) -> list:
        """获取实体关系"""
```

**知识图谱Schema**：
```yaml

  name: str           # 实体名称
```

### 4.3 因果推理引擎（causal_engine.py）

**功能**：整合知识图谱增强、Prompt优化、因果超图、安全验证。

**核心类**：
```python
class CausalEngine:
    def __init__(self):
        self.kg = LinuxKnowledgeGraph()
        self.optimizer = PromptOptimizer()
        self.hypergraph = CausalHyperGraph()
        self.safe_agent = SafeRCAAgent()
    
    def reason(self, logs: list) -> dict:
        """端到端因果推理"""
        # 1. 知识图谱增强
        fault_entities = self.llm.extract_entities(logs)
        related_entities = self.kg.retrieve_similar(fault_entities, top_k=10)
        enhanced_context = self.build_context(related_entities)
        
        # 2. Prompt优化 + RAG
        similar_cases = self.decision_library.search_similar(logs, top_k=3)
        optimized_prompt = self.optimizer.get_optimized_prompt()
        prompt = self.build_enhanced_prompt(optimized_prompt, logs, similar_cases, enhanced_context)
        
        # 3. LLM推理
        raw_result = self.llm.generate(prompt)
        
        # 4. 因果超图验证
        hypergraph_result = self.hypergraph.build_from_logs(logs)
        
        # 5. 安全验证（规避12种失败模式）
        safe_result = self.safe_agent.validate(raw_result, hypergraph_result)
        
        return safe_result
```

**输出Schema**：
```json
{
  "evidence_chain": [
    {
      "id": "E001",
      "source": "nginx/error.log",
      "line": 123,
      "content": "upstream timed out (110)",
      "confidence": 0.95
    }
  ],
  "inference_chain": [
    {
      "from": "E001",
      "to": "E002",
      "relation": "causes",
      "explanation": "慢查询(45s) → 连接池耗尽 → 应用超时 → 502"
    }
  ],
  "rejected_hypotheses": [
    {
      "hypothesis": "Nginx配置错误",
      "reason": "error.log显示upstream timed out而非connection refused"
    }
  ],
  "root_cause": "MySQL慢查询导致连接池耗尽",
  "fix_commands": [
    {
      "command": "ALTER TABLE orders ADD INDEX idx_created_at (created_at);",
      "risk_level": "medium",
      "scope": "当前数据库",

}
```

### 4.5 交互策略模块（interaction_policy.py）

**功能**：三维矩阵动态决定展示详略。

**三维矩阵**：
```
维度1：操作风险等级 → low / medium / high
维度2：操作类型     → query / config / service / data / network
维度3：用户经验     → unknown(0次) / learning(1-2次) / familiar(3次+)

交互策略：
  low  + unknown  → detailed（完整展示）
  low  + learning → learning（关键证据+简化推理）
  low  + familiar → concise（只给结论+命令）
  medium + *      → detailed
  high + *        → detailed + 人工审批
```

## 7. 验证场景

### 7.1 场景1：Web 502故障（慢查询引发）

**故障描述**：Nginx返回502，MySQL慢查询日志显示大量全表扫描，应用日志显示连接超时。

**预期输出**：
```
证据链：
  1. [nginx/error.log:123] upstream timed out (110) → 可信度: 0.95
  2. [app.log:456] Connection to MySQL refused after 30s → 可信度: 0.90
  3. [mysql/slow.log:789] SELECT * FROM orders WHERE... (耗时 45s) → 可信度: 0.98

推理链：
  慢查询(45s) → 连接池耗尽 → 应用无法获取连接 → Nginx upstream超时 → 502

排除假设：
  - Nginx配置错误？→ 排除：error.log显示upstream timed out而非connection refused
  - 网络故障？→ 排除：应用日志显示连接建立成功但超时

修复命令：
  ALTER TABLE orders ADD INDEX idx_created_at (created_at);
  风险等级: medium
  影响范围: 当前数据库
  回滚方案: DROP INDEX idx_created_at ON orders;
```

### 7.2 场景2：磁盘满导致服务异常

**故障描述**：MySQL无法写入，df -h显示根分区100%，/var/log占用80%。

**预期输出**：
```
证据链：
  1. [df -h] /dev/sda1 100% → 可信度: 1.0
  2. [du -sh /var/log/*] /var/log/mysql 50G → 可信度: 0.98
  3. [mysql/error.log] Disk is full, can't write → 可信度: 0.99

推理链：
  /var/log/mysql日志未轮转 → 日志文件持续增长 → 根分区满 → MySQL无法写入

修复命令：
  find /var/log -name "*.log" -mtime +7 -delete
  风险等级: high（涉及日志清理）
  影响范围: 本机全部
  备份建议: 先打包归档重要日志
  回滚方案: 不可回滚（已删除文件无法恢复）
  
  HITL: 需要人工审批（L2级别）
```

### 7.3 场景3：OOM Killer误杀进程

**故障描述**：Redis进程消失，dmesg显示Out of memory: Kill process。

**预期输出**：
```
证据链：
  1. [dmesg] Out of memory: Kill process (redis-server) → 可信度: 0.99
  2. [free -m] Mem: 2048 total, 1980 used → 可信度: 1.0
  3. [ps aux | grep redis] 无结果 → 可信度: 1.0

推理链：
  内存不足(1980/2048MB) → OOM Killer触发 → 选择redis-server（内存占用最大）→ 进程被杀

修复命令：
  systemctl restart redis
  风险等级: low
  影响范围: Redis服务
  回滚方案: systemctl stop redis
  
  交互策略差异：
    初学者模式：详细解释OOM机制、vm.overcommit_memory参数含义
    专家模式：直接给结论+调整参数的命令
```

## 8. 风险评估与应对

### 8.1 技术风险

| 风险 | 概率 | 影响 | 应对策略 |
|------|------|------|---------|
| **LLM因果推理不准确** | 中 | 高 | Prompt Engineering反复调优 + 知识图谱约束 + 因果超图验证 |

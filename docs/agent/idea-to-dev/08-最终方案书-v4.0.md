## 一、项目概述

### 1.1 方案定位

当前 AIOps 赛道已有企业级成熟产品规模化落地。以焰龙AI（炎龙智能 AI天穹 V3.0）为例，其主打「全链路自主闭环 Agentic AIOps」——30 秒自愈、500+ 故障剧本、全栈 60+ 组件覆盖，核心叙事是「人退出执行环，AI 全权执行」。头部云厂商的 AIOps Agent 也已在数千家企业部署，将故障平均修复时间压缩到 15 分钟以内。

这意味着「风险分级 + 人机协同」这个思路本身已不算新鲜，团队级/学生项目如果正面复刻「自动化程度」这条叙事，很难在创新性上打动评审——企业级产品有 500+ 剧本、多智能体并发、GNN 因果推断等重资源投入，3 周、≤3 人团队不可能可信复现。

因此本方案的差异化定位不是与企业级平台比自动化程度，而是反其道而行：

- **企业级 AIOps**（如焰龙AI）面向规模化 SRE 团队，卖点是「减少人力依赖」「人退出执行环」；
- **TDSF-Linux** 面向个人开发者、初级运维和在校学生，卖点是「证据可核验、风险可感知、经验可沉淀」——帮助使用者在被 AI 辅助的同时，真正建立起独立诊断的判断力，而不是把判断力让渡给一个黑盒。

为了让「可信」不停留在口号，技术上只做扎实的事：

1. 让 AI 的每一条结论都能追溯到真实证据，而不是模型自己声称的一个置信度数字；
2. 让中高风险操作必须经过人工确认，且确认时看到的证据链是可核验、可核实的，不是摆设；
3. 让每一次诊断的经验都能反哺下一次诊断，系统随着使用而变得更准，而不是每次从零开始；
4. 简单问题快速回答省 Token，复杂问题深度推理保质量——把有限的算力花在刀刃上。

### 1.2 目标用户

| --- | --- | --- |
| 在校学生（Linux/运维课程） | 看懂 AI 为什么这么判断，而不是只拿到一个答案 | 证据链可展开、根因可追溯，把 AI 当成会「讲解」的助教 |

### 1.3 差异化优势（对比焰龙AI）

| 维度 | 焰龙AI（企业级） | TDSF-Linux（教学级） | 差异化锚点 |
| --- | --- | --- | --- |
| 设计哲学 | 人退出执行环，AI 全权执行 | 人始终在环，AI 辅助决策 | 不比自动化，比可解释 |

## 二、技术栈总览

选型的总原则：优先用成熟开源项目拼装，不重复造轮子；每一个组件都必须能在 3 周、≤3 人团队、Trae 辅助编码的条件下真正跑通，而不是停留在方案书里。

| 层次 | 组件 | 选型 | 选型理由 |
| --- | --- | --- | --- |
| 大模型服务 | 推理 / 工具调用 / 结构化输出 | 火山方舟 Doubao API（Function Calling + 结构化输出 + Context Cache） | 赛事指定生态，兼容 OpenAI SDK，原生支持工具调用与上下文缓存，避免自建推理层 |
| Agent 编排 | 状态机 + 人工确认断点 + 条件路由 | LangGraph（LangChain 生态） | 成熟度高、社区案例极丰富（Trae 生成代码命中率高），原生 interrupt / human-in-the-loop 机制天然匹配风险分级确认场景，conditional_edges 天然支持双推理模式路由 |
| 日志证据抓取 | 日志模板挖掘 | Drain3（IBM 开源，增量聚类算法） | 免训练、给出可计算的模板匹配度，用来替代「LLM 自称置信度」，是解决证据可信度问题的关键组件 |
| 检索增强存储 | 向量库（双 collection） | ChromaDB（本地嵌入式） | 零运维、pip 安装即用；支持多 collection 天然契合 4.6 知识双轨制 |
| 向量化 | Embedding | 火山方舟文本向量化 API（首选）／BGE-small-zh（开源兜底） | 优先复用赛事 Token 额度；断网或超预算时可切开源模型本地跑，双保险 |
| 结构化存储 | 元数据 / 用户画像 / 风险规则 / Decision Card | SQLite | 单文件零配置，够用且足够轻，无需额外部署数据库服务 |
| 风险规则 | 命令风险分级表 | YAML 静态规则库 | 可读、可改、可被评审现场追问，比写死在代码里更透明 |
| 故障模拟环境 | 容器化目标环境 | Docker Compose（Nginx + MySQL + 示例 App） | 可重复注入故障、便于反复录屏演示，环境可复现是评审「落地性」的加分项 |
| 交互界面 | Web UI | Streamlit | 纯 Python 一体化前后端，组件库对「展开证据链 / 风险徽标 / Decision Card 面板」原生支持，比手写 HTML/CSS/JS 省时数倍 |
| 远程执行（可选） | SSH | Paramiko | 若目标机与 Agent 分离部署时的成熟开源方案；同机演示可直接用 subprocess |
| 开发工具 | AI 辅助编码 | Trae（赛事指定） | 官方指定平台，前 200 支报名队伍提供免费 Token 额度覆盖代码生成环节 |

**与焰龙AI / ITOps 技术栈对比的取舍说明**：

- 焰龙AI 用「多 LLM 管理 + 实时切换」（GPT-4/Qwen/DeepSeek/豆包/Gemini），TDSF-Linux 只用火山方舟单模型——教学场景无需多模型权衡，单模型够用且省工程量；
- ITOps 用 TypeScript + Express + React 重型前后端 + 自研 Coordinator-Specialist 多 Agent 框架，TDSF-Linux 用 Python + Streamlit + LangGraph 轻量栈——单 Agent 状态图足够覆盖教学场景，多 Agent 并发是过度工程；
- ITOps 用关键词 + Jaccard 相似度做知识检索，TDSF-Linux 用 ChromaDB 向量检索——语义检索比关键词匹配更强，且 ChromaDB 零运维成本可接受。

## 四、核心算法与机制

这一节是整个方案里技术分量最重的部分，对应评审标准中「技术实现与复杂度」30% 的权重。六个机制环环相扣，核心思路是：把「可信」从一句口号变成可计算、可复现、可被追问的具体机制。

### 4.1 证据置信度：从「LLM 自称」到「可计算」

很多同类系统的「置信度」本质是让 LLM 在输出 JSON 时顺手编一个数字，这个数字和模型是否真的正确并没有稳定关系，一旦被评审追问「这个 0.95 是怎么算出来的」就很难自圆其说。TDSF-Linux 的置信度改为完全由可复现的规则计算：

```
confidence(evidence_i) = α · match_score_drain3 + (1-α) · source_prior

其中：
  match_score_drain3 ∈ [0,1]：Drain3 对该日志行相对模板库的匹配程度
    · 精确匹配已知故障模板           → 1.0
    · 匹配到日志级别/结构但参数不同   → 0.6~0.8
    · 无法匹配任何已知模板（全新日志）→ 0.3，标记为待补充模板

  source_prior：日志来源的固定先验权重（人工标定一次即可）
    例：{dmesg: 0.95, mysql/error.log: 0.90, app.log: 0.75}

  α 取 0.7 —— 更信任可计算的模板匹配，而非人工先验
```

这个数字不是模型编的，是 Drain3 的匹配结果和一张写死的先验表算出来的——全程可复现、可解释，评审现场可以当场追问、当场验证。

**Python 实现**：

```python
# core/confidence.py
from typing import Dict

# 日志来源先验权重表（人工标定一次，运行时只读）
SOURCE_PRIOR: Dict[str, float] = {
    "dmesg": 0.95,           # 内核日志，可信度高
    "mysql/error.log": 0.90, # 数据库错误日志
    "nginx/error.log": 0.85, # Web 服务器错误日志
    "journalctl": 0.80,      # systemd 日志
    "app.log": 0.75,         # 应用日志，可能含业务噪音
}

ALPHA = 0.7  # 模板匹配权重，0.3 给来源先验

def compute_confidence(match_score_drain3: float, source: str) -> float:
    """计算单条证据的置信度（4.1 公式）

    参数:
        match_score_drain3: Drain3 模板匹配度 ∈ [0,1]
        source: 日志来源键名（如 "dmesg"）
    返回:
        置信度 ∈ [0,1]
    """
    source_prior = SOURCE_PRIOR.get(source, 0.5)  # 未知来源给中位先验
    confidence = ALPHA * match_score_drain3 + (1 - ALPHA) * source_prior
    return round(confidence, 3)
```

### 4.2 证据溯源校验（Ground-Check）

Evidence Chain 里的每一条证据，在进入最终结论之前，必须先证明自己「确实来自某一次真实的工具调用」，而不是模型顺着上下文编出来的一句听起来很像证据的话：

```python
# core/grounding.py
from typing import List, Tuple

class Evidence:
    def __init__(self, raw_text: str, source_tool: str, claimed_output: str):
        self.raw_text = raw_text          # 证据原文
        self.source_tool = source_tool    # 声称来自哪个工具调用
        self.claimed_output = claimed_output  # 声称的工具输出片段

class ToolCallTranscript:
    def __init__(self, tool_name: str, output: str):
        self.tool_name = tool_name
        self.output = output

def ground_check(
    evidence_chain: List[Evidence],
    tool_call_transcripts: List[ToolCallTranscript],
    max_retry: int = 1,
) -> Tuple[List[Evidence], List[Evidence]]:
    """证据溯源校验（4.2 机制）

    每条证据必须在某次真实工具调用输出中能找到原文，
    否则视为疑似幻觉，不计入最终证据链。

    参数:
        evidence_chain: 待校验的证据链
        tool_call_transcripts: 本次诊断所有工具调用的完整输出记录
        max_retry: 校验失败时最多补采次数（控制成本）
    返回:
        (verified, rejected) 已验证证据 + 被拒证据
    """
    verified, rejected = [], []
    for ev in evidence_chain:
        # 证据声称的输出片段必须在某次工具调用真实输出中存在
        is_grounded = any(
            ev.claimed_output in t.output for t in tool_call_transcripts
        )
        if is_grounded:
            verified.append(ev)
        else:
            rejected.append(ev)  # 疑似幻觉，不计入最终证据链

    # 若存在 rejected 且重试次数未耗尽，回到 Perceive 补一次针对性工具调用
    # （如更精确的 grep），最多重试 max_retry 次以控制成本
    # 补采逻辑由 LangGraph 的条件边实现，此处仅返回校验结果
    return verified, rejected
```

若存在 rejected 证据且重试次数未耗尽，回到「证据采集」节点补一次针对性工具调用（如更精确的 grep），最多重试 1 次以控制成本。这一步是「用户可以验证 AI 判断依据」这句话真正成立的技术前提。

### 4.3 自适应自洽采样（Adaptive Self-Consistency）

多次独立采样、取多数一致结论作为置信度，是 Wang 等人（2022，Self-Consistency Improves Chain-of-Thought Reasoning）提出并被广泛验证的方法。考虑到 Token 预算有限，TDSF-Linux 只在证据本身不够扎实时才触发重采样，而不是每次都跑 3~5 遍：

```python
# core/sampling.py
from typing import List, Tuple, Any

def adaptive_confidence(
    evidence_chain: List[Any],
    threshold: float = 0.7,
    n_samples: int = 3,
) -> Tuple[float, Any]:
    """自适应自洽采样（4.3 机制）

    置信度 ≥ threshold：单次推理直接采用，省 Token
    置信度 < threshold：触发 n_samples 次重采样，取多数一致结论

    参数:
        evidence_chain: 已通过 Ground-Check 的证据链
        threshold: 触发重采样的置信度阈值
        n_samples: 重采样次数
    返回:
        (最终置信度, 最终结论)
    """
    # 1. 先算基础置信度（见 4.1 公式）
    base_conf = compute_confidence_from_chain(evidence_chain)

    if base_conf >= threshold:
        # 多数清晰场景（如 OOM、磁盘满）单次推理即可给出高置信度结论
        return base_conf, evidence_chain

    # 2. 证据模糊、模板匹配度低 → 触发 n_samples 次独立重采样
    samples = [reason_once(evidence_chain) for _ in range(n_samples)]
    root_cause, agree_ratio = majority_vote(samples)

    # agree_ratio 作为新的置信度（3 次中 2 次一致 → 0.67）
    return agree_ratio, root_cause

def majority_vote(samples: List[Any]) -> Tuple[Any, float]:
    """对多次采样结果做多数投票，返回(一致结论, 一致比例)"""
    from collections import Counter
    counter = Counter(samples)
    most_common, count = counter.most_common(1)[0]
    return most_common, count / len(samples)
```

绝大多数清晰场景（如 OOM、磁盘满）单次推理即可给出高置信度结论，只有证据模糊、模板匹配度低的情况才会触发 3 次重采样，在效果和成本之间做了明确取舍。

### 4.4 风险评分门控（v4.0 升级：4 层风险控制体系）

v3.0 的 4.4 只有单层风险评分。v4.0 整合焰龙AI 的分层安全控制思想（命令验证 → 安全控制 → 可配置询问 → 审计日志），升级为 4 层风险控制体系。每一层都有明确的技术落点和可演示的拦截行为。

#### 4.4.1 4 层风险控制总览

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 1: 命令语法检查（执行前，自动）                         │
│   → 检查命令是否合法、参数是否正确、是否在白名单内             │
│   → 不合法直接拦截，返回错误原因                              │
│   → 技术落点：shell语法解析 + 命令白名单 YAML                │
├─────────────────────────────────────────────────────────────┤
│ Layer 2: 风险评估（执行前，自动）                             │
│   → 评估命令风险等级（只读/低风险/中风险/高风险/危险）         │
│   → risk_score = max(command_pattern_risk, env_modifier)     │
│   → 高风险/危险需人工确认                                     │
│   → 技术落点：risk_rules.yaml + assets.yaml                  │
├─────────────────────────────────────────────────────────────┤
│ Layer 3: 证据展示 + 人工确认（执行前，交互）                  │
│   → 展示命令将做什么、影响什么、如何回滚                      │
│   → LangGraph interrupt() 暂停等待人工确认                    │
│   → 人选择「接受 / 拒绝 / 追问」                              │
│   → 技术落点：LangGraph interrupt + Streamlit 确认面板        │
├─────────────────────────────────────────────────────────────┤
│ Layer 4: 执行日志审计（执行后，自动）                         │
│   → 记录命令、输出、时间、执行人、结果                        │
│   → 支持回溯审计                                              │
│   → 技术落点：SQLite audit_log 表                             │
└─────────────────────────────────────────────────────────────┘
```

#### 4.4.2 风险评分公式（Layer 2 核心）

```
risk_score = max(command_pattern_risk, environment_criticality_modifier)

command_pattern_risk：
  查静态规则表（risk_rules.yaml），分 低 / 中 / 高 / 危险
  · 只读命令（grep/df/free/cat/journalctl/ss）→ low
  · 状态变更命令（systemctl restart/reload）  → medium
  · 数据修改命令（rm/mv/dd/chmod）            → high
  · 不可逆命令（rm -rf / dd if=/dev/zero）    → critical（禁止）

environment_criticality_modifier：
  目标资产若标记为「关键」，风险等级至少上调一档
  标签维护在 assets.yaml，demo 环境中人工设置
```

#### 4.4.3 交互门控（Layer 3，LangGraph conditional edge + interrupt）

```python
# core/risk_gate.py
from enum import Enum
from typing import List, Dict

class RiskLevel(str, Enum):
    LOW = "low"          # 只读，直接执行
    MEDIUM = "medium"    # 状态变更，需人工确认
    HIGH = "high"        # 数据修改，需人工确认 + 回滚方案
    CRITICAL = "critical"  # 不可逆，禁止执行

# 命令风险规则表（运行时从 risk_rules.yaml 加载）
COMMAND_RISK_RULES: Dict[str, RiskLevel] = {
    # 只读诊断命令（Layer 1 白名单 + Layer 2 低风险）
    "grep": RiskLevel.LOW, "df": RiskLevel.LOW, "free": RiskLevel.LOW,
    "cat": RiskLevel.LOW, "journalctl": RiskLevel.LOW, "ss": RiskLevel.LOW,
    "top": RiskLevel.LOW, "ps": RiskLevel.LOW, "du": RiskLevel.LOW,
    # 状态变更命令（中风险）
    "systemctl restart": RiskLevel.MEDIUM,
    "systemctl reload": RiskLevel.MEDIUM,
    "kill": RiskLevel.MEDIUM,
    # 数据修改命令（高风险）
    "rm": RiskLevel.HIGH, "mv": RiskLevel.HIGH, "chmod": RiskLevel.HIGH,
    "chown": RiskLevel.HIGH, "dd": RiskLevel.HIGH,
    # 不可逆命令（危险，禁止）
    "rm -rf /": RiskLevel.CRITICAL,
    "dd if=/dev/zero": RiskLevel.CRITICAL,
    "mkfs": RiskLevel.CRITICAL,
}

def assess_risk(command: str, asset_critical: bool = False) -> RiskLevel:
    """4 层风险控制 Layer 2：风险评估

    参数:
        command: 待执行的命令字符串
        asset_critical: 目标资产是否标记为关键（来自 assets.yaml）
    返回:
        风险等级
    """
    # 1. Layer 1 命令语法检查（简化版：检查是否在规则表或白名单内）
    cmd_base = command.strip().split()[0] if command.strip() else ""
    if not cmd_base:
        raise ValueError("空命令")

    # 2. Layer 2 风险评估：查规则表
    #    先匹配完整命令（如 "rm -rf /"），再匹配命令前缀（如 "rm"）
    if command in COMMAND_RISK_RULES:
        risk = COMMAND_RISK_RULES[command]
    elif cmd_base in COMMAND_RISK_RULES:
        risk = COMMAND_RISK_RULES[cmd_base]
    else:
        risk = RiskLevel.MEDIUM  # 未知命令默认中风险，强制人工确认

    # 3. 关键资产风险上调一档
    if asset_critical and risk == RiskLevel.LOW:
        risk = RiskLevel.MEDIUM
    elif asset_critical and risk == RiskLevel.MEDIUM:
        risk = RiskLevel.HIGH

    return risk

def risk_gate_decision(risk: RiskLevel) -> str:
    """4 层风险控制 Layer 3：门控决策

    返回 LangGraph 条件边的路由目标：
      - "execute"   直接执行（低风险）
      - "interrupt" 暂停等待人工确认（中/高风险）
      - "block"     禁止执行（危险）
    """
    if risk == RiskLevel.CRITICAL:
        return "block"
    elif risk == RiskLevel.LOW:
        return "execute"
    else:  # MEDIUM / HIGH → interrupt()
        return "interrupt"
```

### 4.5 【新增】双推理模式（整合焰龙AI：快速/深度条件路由）

#### 4.5.1 设计动机

焰龙AI 的「快速 or 思考自检 模式」是一个很实用的设计：简单问题用快速模式单步回答省 Token，复杂问题用深度模式多步推理保质量。TDSF-Linux 在 v4.0 引入这个机制，原因是：

- 教学场景中，大量问题是简单的命令查询（如「怎么看磁盘占用」），不需要走完整的多步推理 + 证据核验流程；
- Token 预算有限，把算力集中在真正复杂的故障诊断上；
- LangGraph 的 conditional_edges 天然支持条件路由，工程量极小。

#### 4.5.2 路由判定规则

```python
# core/router.py
from typing import Literal

def classify_query(
    log_content: str,
    drain3_match_score: float,
    has_historical_case: bool,
) -> Literal["quick", "deep"]:
    """双推理模式路由判定（4.5 机制）

    判定规则（满足任一即走深度模式）：
      1. Drain3 模板匹配度 < 0.6（未知日志模式，需深度分析）
      2. 日志内容长度 > 2000 字符（复杂日志，需多步推理）
      3. 无历史案例可召回（无先验，需从零推理）
      4. 日志中含多个错误级别关键词（ERROR + FATAL 同时出现）

    否则走快速模式。

    参数:
        log_content: 原始日志内容
        drain3_match_score: Drain3 模板匹配度
        has_historical_case: 是否检索到高相似度历史案例
    返回:
        "quick" 或 "deep"
    """
    # 规则 1：模板匹配度低 → 深度模式
    if drain3_match_score < 0.6:
        return "deep"

    # 规则 2：日志过长 → 深度模式
    if len(log_content) > 2000:
        return "deep"

    # 规则 3：无历史案例 → 深度模式（从零推理）
    if not has_historical_case:
        return "deep"

    # 规则 4：多个错误级别关键词 → 深度模式
    error_keywords = ["error", "fatal", "critical", "panic", "oom"]
    matched = sum(1 for kw in error_keywords if kw in log_content.lower())
    if matched >= 2:
        return "deep"

    # 默认走快速模式
    return "quick"
```

#### 4.5.3 LangGraph 条件路由实现

```python
# graph/build_graph.py
from langgraph.graph import StateGraph, END
from typing import TypedDict, Literal

class AgentState(TypedDict):
    log_content: str
    drain3_match_score: float
    has_historical_case: bool
    query_mode: Literal["quick", "deep"]
    evidence_chain: list
    root_cause: str
    confidence: float
    risk_level: str
    decision_id: str

def classify_node(state: AgentState) -> AgentState:
    """Classify 节点：判定双推理模式"""
    mode = classify_query(
        state["log_content"],
        state["drain3_match_score"],
        state["has_historical_case"],
    )
    state["query_mode"] = mode
    return state

def route_mode(state: AgentState) -> str:
    """条件路由：根据 query_mode 决定走快速还是深度"""
    return "quick_answer" if state["query_mode"] == "quick" else "deep_reason"

def build_graph():
    graph = StateGraph(AgentState)

    # 添加七节点
    graph.add_node("perceive", perceive_node)
    graph.add_node("classify", classify_node)
    graph.add_node("quick_answer", quick_answer_node)
    graph.add_node("deep_reason", deep_reason_node)
    graph.add_node("ground_check", ground_check_node)
    graph.add_node("risk_assess", risk_assess_node)
    graph.add_node("hitl", hitl_node)
    graph.add_node("archive", archive_node)

    # 边：perceive → classify
    graph.add_edge("perceive", "classify")

    # 条件路由：classify → quick_answer 或 deep_reason（双推理模式核心）
    graph.add_conditional_edges(
        "classify",
        route_mode,
        {"quick_answer": "quick_answer", "deep_reason": "deep_reason"},
    )

    # 两条路径都汇入 ground_check
    graph.add_edge("quick_answer", "ground_check")
    graph.add_edge("deep_reason", "ground_check")

    # ground_check → risk_assess → 条件路由
    graph.add_edge("ground_check", "risk_assess")
    graph.add_conditional_edges(
        "risk_assess",
        risk_gate_decision,  # 见 4.4.3
        {"execute": "archive", "interrupt": "hitl", "block": "archive"},
    )

    # hitl → archive（人工确认后归档）
    graph.add_edge("hitl", "archive")
    graph.add_edge("archive", END)

    graph.set_entry_point("perceive")
    return graph.compile()
```

#### 4.5.4 两种模式的差异

| 维度 | 快速模式（QuickAnswer） | 深度模式（DeepReason） |
| --- | --- | --- |
| 触发条件 | 模板匹配度高 + 有历史案例 + 日志简短 | 模板匹配度低 / 日志复杂 / 无历史案例 |
| 推理步数 | 单步推理 | 多步推理（排除假设 + 根因候选） |
| 证据核验 | 轻量（仅 Ground-Check） | 完整（Ground-Check + 自适应重采样） |
| Token 消耗 | 低（单次调用） | 高（可能 3 次重采样） |
| 输出 | 根因 + 建议命令 | 根因 + 证据链 + 排除假设 + 回滚方案 |
| 典型场景 | 「怎么看磁盘占用」「重启 nginx」 | OOM 根因分析、502 慢查询诊断 |

### 4.6 【新增】知识双轨制（整合焰龙AI + ITOps：command_skills + incident_cases）

#### 4.6.1 设计动机

焰龙AI 用了两套知识沉淀机制：Skills（能力包，标准化操作能力）+ 历史案例库（具体故障处理记录）。ITOps Agent Platform 的 KnowledgeEngine 也有类似思想。TDSF-Linux 在 v4.0 把这两个维度分离到 ChromaDB 的两个 collection：

- **command_skills**（操作能力包）：存「怎么做」——命令的最佳实践、使用场景、参数说明、常见错误。这是静态知识，预置 + 人工维护。
- **incident_cases**（故障案例库）：存「怎么修」——历史故障案例（症状 + 根因 + 解决方案 + 验证方法）。这是动态知识，每次诊断后自动沉淀。

分离检索的好处：操作能力（通用知识）与故障案例（具体经验）召回精度更高，不会互相污染。

#### 4.6.2 ChromaDB 双 collection 设计

```python
# core/decision_library.py
import chromadb
import json
from uuid import uuid4
from datetime import datetime

class DecisionLibrary:

            name="command_skills",

            root_cause → rootCause
```

#### 4.6.3 历史案例召回与推理先验注入

新故障进来时，DeepReason 节点先用当前症状做向量检索，取 Top-3 相似历史案例。若相似度超过阈值，作为推理先验注入 Prompt——但必须明确注明「该历史案例仅供参考，你仍必须基于当前证据独立验证，不得直接照搬历史结论」，这是为了防止历史偏见污染新判断（例如同一台机器换了根因，却被历史案例带偏）。

```python
# graph/deep_reason_node.py
def deep_reason_node(state: AgentState) -> AgentState:
    """深度推理节点：召回历史案例 + 多步推理"""

    # 1. 从 incident_cases 召回历史案例
    decision_lib = DecisionLibrary()
    historical_cases = decision_lib.search_cases(
        state["log_content"], top_k=3, min_success_rate=0.5
    )

    # 2. 从 command_skills 召回相关操作能力
    relevant_skills = decision_lib.search_skills(
        state["log_content"], top_k=3
    )

    # 3. 构造 Prompt，注入历史先验（带防偏见警示）
    prompt = f"""
你是一个 Linux 运维诊断专家。请基于以下证据进行根因分析。

【当前日志证据】
{state['log_content']}

【历史相似案例（仅供参考，你必须基于当前证据独立验证，不得直接照搬历史结论）】
"""
    for i, case in enumerate(historical_cases, 1):
        prompt += f"案例 {i}：{case['document']}\n"

    prompt += f"""
【相关命令能力包】
"""
    for i, skill in enumerate(relevant_skills["documents"][0], 1):
        prompt += f"能力 {i}：{skill}\n"

    prompt += """
请输出 JSON：
{
  "root_cause": "根因分析",
  "evidence_chain": [{"raw_text": "证据原文", "source_tool": "来源工具"}],
  "excluded_hypotheses": ["排除的假设1", "排除的假设2"],
  "commands": ["建议命令1", "建议命令2"],
  "rollback_commands": ["回滚命令1"],
  "verification": "验证方法"
}
"""
    # 4. 调用 LLM（火山方舟）
    result = call_llm(prompt)
    state["root_cause"] = result["root_cause"]
    state["evidence_chain"] = result["evidence_chain"]
    # ... 其他字段
    return state
```

这个设计让系统有一个真实、可演示的「越用越聪明」故事：处理过的故障越多，命中历史相似案例的概率越高，获得的先验信息质量也越高——但全程是可解释、可关闭、可审计的检索增强，不是黑箱的模型再训练，不需要 GPU 训练资源，符合预算限制。

```python
# core/decision_library.py（续）

class DecisionLibrary:
    """知识双轨制：command_skills + incident_cases 双 collection"""

    def __init__(self, persist_path: str = "./chroma_db", sqlite_path: str = "./decisions.db"):
        # ChromaDB 初始化
        self.client = chromadb.PersistentClient(path=persist_path)

        """初始化 SQLite 表结构（见 5.2 建表语句）"""
        import sqlite3
        conn = sqlite3.connect(self.sqlite_path)
        # 执行 5.2 中的所有 CREATE TABLE / CREATE INDEX 语句
        # ...（省略执行细节）

        conn.close()

    # ──────────────────────────────────────────────────────────
    # Collection 1：command_skills 操作
    # ──────────────────────────────────────────────────────────

    def add_command_skill(
        self,
        command: str,
        purpose: str,
        usage: str,

    ):
        """添加操作能力包

        参数:
            command: 命令名称（如 "df -h"）
            purpose: 用途说明
            usage: 用法示例
            common_errors: 常见错误与避坑
            risk_level: 风险等级
        """
        doc = f"命令：{command}\n用途：{purpose}\n用法：{usage}\n常见错误：{common_errors}"
        self.command_skills.add(
            documents=[doc],
            metadatas=[{
                "command": command,
                "purpose": purpose,
                "risk_level": risk_level,
                "type": "skill",
            }],
            ids=[str(uuid4())],
        )

    def search_skills(self, query: str, top_k: int = 3):
        """检索操作能力包（语义检索，比 ITOps 的 Jaccard 更强）"""
        return self.command_skills.query(
            query_texts=[query],
            n_results=top_k,

    # ──────────────────────────────────────────────────────────
    # Collection 2：incident_cases 操作
    # ──────────────────────────────────────────────────────────

    def add_incident_case(
        self,
        symptom: str,
        root_cause: str,
        evidence_chain: list,
        commands: list,
        rollback_commands: list,
        verification: str,
        risk_level: str,
        success: bool,
        log_pattern: str = "",
    ):
        """故障处理后自动沉淀案例

        整合 ITOps KnowledgeSolutions 结构：
            root_cause → rootCause
            commands → commands
            rollback_commands → rollbackCommands
            verification → verificationResult
            success → success
        整合焰龙AI 历史案例库思想
        """
        case_doc = json.dumps({
            "symptom": symptom,
            "root_cause": root_cause,
            "evidence_chain": evidence_chain,
            "commands": commands,
            "rollback_commands": rollback_commands,
            "verification": verification,
        }, ensure_ascii=False)

        case_id = str(uuid4())

        # 写入 ChromaDB（向量检索）
        self.incident_cases.add(
            documents=[case_doc],
            metadatas=[{
                "symptom": symptom,
                "root_cause": root_cause,
                "log_pattern": log_pattern,
                "risk_level": risk_level,
                "success": success,
                "success_rate": 1.0 if success else 0.0,
                "usage_count": 0,
                "source": "hitl",
                "created_at": datetime.now().isoformat(),
                "type": "case",
            }],
            ids=[case_id],
        )

        # 同步写入 SQLite（精确查询 + 审计关联）
        import sqlite3
        conn = sqlite3.connect(self.sqlite_path)
        conn.execute("""
            INSERT INTO decisions
                (id, title, symptom, log_pattern, root_cause, evidence,
                 commands, rollback_commands, verification,
                 risk_level, source, success_rate, success_count, total_count)
            VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
        """, (
            case_id,
            symptom[:80],  # title 取症状前 80 字
            symptom,
            log_pattern,
            root_cause,
            json.dumps(evidence_chain, ensure_ascii=False),
            json.dumps(commands, ensure_ascii=False),
            json.dumps(rollback_commands, ensure_ascii=False),
            verification,
            risk_level,
            "hitl",
            1.0 if success else 0.0,
            1 if success else 0,
            1,
        ))
        conn.commit()
        conn.close()

        return case_id

    def search_cases(self, symptom: str, top_k: int = 3, min_success_rate: float = 0.5):
        """检索历史故障案例

        借鉴 ITOps AlertProcessor：successRate >= 0.8 的案例优先复用
        借鉴焰龙AI 历史案例智能匹配
        """
        results = self.incident_cases.query(
            query_texts=[symptom],
            n_results=top_k * 2,  # 多取一些再过滤
        )

        filtered = []
        for i, meta in enumerate(results["metadatas"][0]):
            if meta.get("success_rate", 0) >= min_success_rate:
                filtered.append({
                    "id": results["ids"][0][i],
                    "document": results["documents"][0][i],
                    "metadata": meta,
                    "distance": results["distances"][0][i],
                    "similarity": 1 - results["distances"][0][i],
                })

        # 按相似度降序
        filtered.sort(key=lambda x: -x["similarity"])
        return filtered[:top_k]

    def update_case_success(self, case_id: str, success: bool):
        """更新案例成功率（借鉴 ITOps successRating 追踪）

        success_rate = success_count / total_count
        """
        import sqlite3
        conn = sqlite3.connect(self.sqlite_path)

        # 读取当前值
        row = conn.execute(
            "SELECT success_count, total_count FROM decisions WHERE id = ?",
            (case_id,)
        ).fetchone()

        if row:
            success_count, total_count = row
            success_count = (success_count or 0) + (1 if success else 0)
            total_count = (total_count or 0) + 1
            new_rate = success_count / total_count

            conn.execute("""
                UPDATE decisions
                SET success_count = ?, total_count = ?, success_rate = ?,
                    updated_at = CURRENT_TIMESTAMP
                WHERE id = ?
            """, (success_count, total_count, new_rate, case_id))
            conn.commit()

            # 同步更新 ChromaDB metadata
            self.incident_cases.update(
                ids=[case_id],
                metadatas=[{
                    "success_rate": new_rate,
                    "success_count": success_count,
                    "total_count": total_count,
                }],
            )

        conn.close()
```

### 6.2 一次完整交互的时序

| 步骤 | 参与方 | 动作 |
| --- | --- | --- |
| 1 | 用户 | 在 Streamlit 输入框粘贴日志（如 dmesg 的 OOM 记录） |
| 2 | Perceive | 调用 `dmesg | grep -i oom`、`free -m` 采集证据；Drain3 匹配 OOM 模板（match_score=0.95） |
| 3 | Classify | 模板匹配度高 + 有历史案例 → 判定 quick 模式 |
| 4 | QuickAnswer | 单步推理：根因 = 内存不足触发 OOM Killer；命令 = `dmesg -T | grep -i oom` |
| 5 | GroundCheck | 证据溯源通过（dmesg 输出确实存在）；置信度 = 0.7×0.95 + 0.3×0.95 = 0.95 ≥ 0.7，无需重采样 |
| 6 | RiskAssess | `dmesg` 是只读命令 → low 风险 → 直接执行 |
| 7 | Archive | 写入 Decision Card 到 SQLite + ChromaDB |
| 8 | Streamlit | 展示根因 + 证据链（可展开）+ low 风险徽标 |

若步骤 6 判定为 high 风险（如建议 `rm /var/log/large.log`），则：

| 步骤 | 参与方 | 动作 |
| --- | --- | --- |
| 6' | RiskAssess | `rm` 是高风险命令 → interrupt() 暂停 |
| 7' | HITL | Streamlit 弹出确认面板：展示命令、影响（删除日志文件）、回滚方案（无法回滚，需备份） |
| 8' | 用户 | 查看证据链后选择「接受」 |
| 9' | 执行 | 执行 `rm /var/log/large.log`，输出写入 audit_log |
| 10' | Archive | 沉淀 Decision Card，success=True |

## 八、验证场景

3 个验证场景覆盖三类典型 Linux 运维故障，每个场景都能端到端演示「证据采集 → 双推理路由 → 证据校验 → 风险门控 → 归档」完整闭环。

### 8.1 场景一：OOM（内存不足触发 OOM Killer）

**故障注入**：在 Docker 容器中运行内存压力测试工具，触发 OOM Killer 杀进程。

**预期流程**：

| 节点 | 动作 | 输出示例 |
| --- | --- | --- |
| Perceive | `dmesg | grep -i oom` + `free -m` | 捕获 "Out of memory: Killed process 1234 (java)" |
| Drain3 | 匹配 OOM 模板 | match_score = 0.95（精确匹配已知模板） |
| Classify | 有历史案例 + 模板匹配高 → quick 模式 | query_mode = quick |
| QuickAnswer | 单步推理 | 根因 = 内存不足触发 OOM Killer，建议检查内存占用最高的进程 |
| GroundCheck | dmesg 输出确实存在该行 | confidence = 0.95 ≥ 0.7，无需重采样 |
| RiskAssess | 建议命令 `ps aux --sort=-%mem | head` | low 风险，直接执行 |
| Archive | 沉淀 Decision Card | 写入 incident_cases |

**可演示的差异化**：证据链可展开，展示 dmesg 原文 + Drain3 模板匹配度计算过程。

### 8.2 场景二：502 慢查询（Nginx 502 + MySQL 慢查询）

**故障注入**：在示例 App 中注入慢 SQL（sleep 30s），Nginx 代理超时返回 502。

**预期流程**：

| 节点 | 动作 | 输出示例 |
| --- | --- | --- |
| Perceive | `journalctl -u nginx` + `cat /var/log/mysql/slow.log` | 捕获 "upstream timed out" + 慢查询记录 |
| Drain3 | 匹配 502/超时模板 | match_score = 0.7（匹配结构但参数不同） |
| Classify | 模板匹配中 + 日志复杂 → deep 模式 | query_mode = deep |
| DeepReason | 召回历史案例 + 多步推理 | 根因 = MySQL 慢查询导致 Nginx 代理超时；排除假设 = 网络抖动 |
| GroundCheck | 校验慢查询日志确实存在 | confidence = 0.8 ≥ 0.7 |
| RiskAssess | 建议命令 `systemctl restart mysql` | medium 风险，触发 HITL |
| HITL | 展示证据链 + 命令影响 + 回滚方案 | 用户确认 |
| Archive | 沉淀 + 更新 success_rate | 写入 incident_cases |

**可演示的差异化**：多步推理排除假设过程可见；中风险命令强制人工确认；回滚方案展示。

### 8.3 场景三：磁盘满（/var/log 塞满）

**故障注入**：在 Docker 容器中生成大量日志文件填满 /var/log 分区。

**预期流程**：

| 节点 | 动作 | 输出示例 |
| --- | --- | --- |
| Perceive | `df -h` + `du -sh /var/log/*` | 捕获 "/var/log 100% 使用" |
| Drain3 | 匹配磁盘满模板 | match_score = 0.9 |
| Classify | 首次无历史案例 → deep 模式 | query_mode = deep |
| DeepReason | 无历史先验，从零推理 | 根因 = 日志文件未轮转导致 /var/log 塞满 |
| GroundCheck | df 输出确实显示 100% | confidence = 0.85 |
| RiskAssess | 建议命令 `rm /var/log/app.log.10` | high 风险（rm 命令），触发 HITL |
| HITL | 展示影响（删除旧日志）+ 回滚方案（无法回滚，建议先备份） | 用户确认 |
| Archive | 沉淀 success=True | 下次同类故障可召回 |

**可演示的差异化**：高风险命令的回滚方案明确标注「不可逆」；第二次注入同类故障时能召回本次案例，体现「越用越聪明」。

### 8.4 三场景的差异化卖点覆盖矩阵

| 差异化卖点 | OOM 场景 | 502 慢查询场景 | 磁盘满场景 |
| --- | --- | --- | --- |
| 证据可核验（4.1+4.2） | ✓ dmesg 原文可追溯 | ✓ 慢查询日志可追溯 | ✓ df 输出可追溯 |
| 风险可感知（4.4 4层） | ✓ low 直接执行 | ✓ medium HITL 确认 | ✓ high HITL + 回滚警示 |
| 经验可沉淀（4.6 双轨制） | ✓ 沉淀后可召回 | ✓ 沉淀后可召回 | ✓ 首次无先验→沉淀→二次召回 |
| 双推理模式（4.5） | ✓ quick 模式 | ✓ deep 模式 | ✓ deep 模式（无历史案例） |
| 自适应采样（4.3） | — 置信度高无需 | — 置信度够 | 可构造低置信度触发 |

## 十一、附录一：评估但未采纳的技术方向（供团队内部参考）

团队内部曾讨论过引入知识图谱构建、因果超图神经网络、Granger 因果检验、Prompt 自动优化器等更「学术」的方向，这里记录清楚为什么最终没有采纳，避免团队成员在答辩时被问到相关问题时说法不一致：

- **知识图谱 + 因果超图神经网络**：背后对应的研究工作（如 AetherLog, ISSRE 2025）是真实存在的高质量论文，焰龙AI 也用了「大模型因果推断 + 图神经网络」构建故障传播路径。但完整复现需要训练数据、评估基准和数周的调参验证，不是 3 周可信复现的规模。没有真实训练过程的神经网络模块等同于零信息量的装饰代码，一旦被评委追问「训练数据是什么、准确率怎么测的」会直接露怯，比不做还伤——因此本方案只保留了「检索增强」这个真正轻量可行的部分（见第五节），去掉了需要训练的神经网络部分；

- **Granger 因果检验**：该方法适用于有足够重复观测的时间序列，直接套用在单次故障、样本极少的日志片段上统计上并不成立，容易被内行看出是「拿一个听起来很科学的词包装」，因此改用更朴实但可解释的证据溯源校验（4.2节）；

- **「EU AI Act Article 14 五级自主模型」**：经核查，欧盟《人工智能法案》第14条本身只要求监督措施与风险、自主程度相称，并未定义任何「L2/L3」式的分级框架；用它包装人工确认机制是对法规的误用，且该法规本身也不适用于部署在境内校园的演示项目。本方案改为直接、诚实地描述为「基于风险分级的 4 层人工确认机制」（4.4节），不做不准确的合规性声称。焰龙AI 的 4 级权限模型（Level 1-4）也是企业自定标准而非法规分级，本方案不套用其 Level 编号；

- **Prompt 自动优化器（10 轮迭代）**：需要一个可靠的历史案例评估集和大量额外 Token 开销才能生效，与「预算有限」的约束冲突，且优化效果难以在演示中直观证明，本方案改为人工迭代 Prompt，成本更可控；

- **自动化自愈执行**：焰龙AI 主打「30 秒自愈」「500+ 修复剧本」，ITOps Agent Platform 也有 AARS 自动告警响应系统。但自动执行与 TDSF-Linux「人机协同」定位冲突——教学场景的核心价值是让学习者「学会判断」，而不是让 AI 替学习者干活。本方案只做到「人确认后执行」，不做自动执行；

- **多智能体并发协同**：焰龙AI 标注「多智能体并发协同」，ITOps 用 Coordinator-Specialist 11 个专家 Agent。但多 Agent 协同技术栈过重，Streamlit + LangGraph 单 Agent 状态图足够覆盖教学场景，多 Agent 是过度工程；

- **500+ 故障剧本**：焰龙AI 预置 500+ 故障场景修复剧本。教学场景不需要全覆盖，聚焦 3 个核心知识点（OOM/502/磁盘满）做透比铺 500 个浅剧本更有价值；

- **全栈 60+ 组件支持**：焰龙AI 覆盖 17 大类 60+ 组件（数据库/中间件/K8s/网络设备/IoT）。TDSF-Linux 聚焦 Linux 运维教学，不做数据库/中间件/K8s 全覆盖。

总的原则是：**宁可少做一个听起来炫的模块，也不做一个自己讲不清楚原理、经不起追问的模块**——评委真正认可的「深度」，是每个设计选择背后都能讲出令人信服的原理，而不是术语的密度。

| Granger 因果检验 | 学术方向 | 单次故障样本太少，统计上不成立 |
| EU AI Act 五级模型 | 包装话术 | 法规未定义 L2/L3 分级，误用法规 |

| 多租户 | 焰龙AI / ITOps | 个人/教学场景无需多租户 |
| 等保合规 | 焰龙AI | 教学产品无需等保认证 |
| 可视化拖拽工作流编排 | ITOps @xyflow/react | LangGraph 代码式编排足够，拖拽式过度工程 |

| 告警 Webhook 接入 | ITOps Prometheus/Zabbix | 教学场景用日志输入，无需告警系统集成 |

| TypeScript/Node.js 技术栈 | ITOps | Python 生态更适合 AI/教学，且团队更熟 |

### 12.4 借鉴原则总结

> **底线**：借鉴工程实践，不借鉴技术栈；借鉴设计模式，不借鉴实现细节；借鉴闭环思想，坚守可信定位。

具体而言：

1. **借鉴数据结构，不借鉴存储实现**：ITOps 的 KnowledgeSolutions 字段结构很好，但我们用 SQLite + ChromaDB 双存储实现，不用他们的 better-sqlite3 + 关键词检索；
2. **借鉴设计模式，不借鉴编排框架**：焰龙AI 的双推理模式思想很好，但我们用 LangGraph conditional_edges 实现，不用他们的自研多 Agent 框架；
3. **借鉴闭环思想，不借鉴自动化执行**：焰龙AI 的感知→推理→执行→学习闭环很好，但「执行」环节我们改为「人确认后执行」，坚守人机协同定位；
4. **借鉴分层理念，不借鉴企业级安全**：焰龙AI 的 4 层安全控制理念很好，但我们简化为教学场景够用的 4 层风险控制，不做等保/JWT/多租户。

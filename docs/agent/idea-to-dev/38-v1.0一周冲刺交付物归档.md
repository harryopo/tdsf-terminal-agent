## 3. 关键决策（v1.0 一周冲刺）

| 决策 | 内容 | 依据 |
|------|------|------|
| **DEC-1** | 端口 7931 → 19000 | Windows 上 7931-8080 段被系统服务保留，19000 段空闲 |
| **DEC-2** | 进程隔离：Python Sidecar | 多依赖解耦，避免主进程 Electron 受 Python 版本影响 |
| **DEC-3** | HTTP 通信（非 stdio） | FastAPI + uvicorn 开发速度比 stdio JSON-RPC 快 3 倍 |
| **DEC-4** | 规则匹配 MVP（暂不调 LLM） | OpenDerisk 真实实现需 Docker + 大模型（v1.5 升级） |
| **DEC-5** | examples 客户端补全 | drain3 0.9.11 cluster 无 sample_log / logs 属性 |
| **DEC-6** | 置信度公式：base + min(match_count, 5) * 0.02 | 避免原 `score/50` 导致 0.05 极低值 |
| **DEC-7** | 不持久化（v1.0 简化） | 避免 FilePersistence 兼容性问题（v1.1 升级） |

## 8. 问答归档

### Q1: 为什么用 Python Sidecar 而非 Node.js？
A: Drain3（logpai 出品）和 OpenDerisk（derisk-ai 出品）都是 Python 原生，工业部署广泛。Node 重写算法工作量大、bug 多。Sidecar 架构隔离 Python 依赖，避免污染 Electron 主进程。

### Q2: 为什么端口 19000 而不是 7931？
A: Windows 上 7931-8080 端口段被系统服务保留，bind 时报 WinError 10013。19000 段空闲且数字大不易冲突。

### Q3: 为什么规则匹配而非直接调 LLM？
A: OpenDerisk 真实实现需要 Docker + 大模型 + MCP 生态（v1.5 升级）。v1.0 阶段规则匹配可保证 0 网络依赖 + 100ms 响应 + 100% 透明推理链（用户能审计每一步）。

### Q4: Drain3 examples 字段为什么空？
A: drain3 0.9.11 的 `LogCluster` 类只有 `cluster_id / get_template / log_template_tokens / size` 四个属性，无 `sample_log / logs`。v1.0 在 `drain3_adapter.py` 客户端维护 `_examples: { cluster_id: [raw_line, ...] }`，每个 cluster 最多 3 个样例。

### Q5: Sidecar 进程崩溃了怎么办？
A: SidecarManager 自动重启（最多 3 次，间隔 2s）。若仍失败，状态变 `crashed`，UI 侧 SrePipelinePanel 顶部 Tag 显示 `crashed` 状态，需用户手动重启（`sidecar:stop` + `sidecar:start`）。

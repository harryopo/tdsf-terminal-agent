## 一、调研背景与目标

### 1.1 TDSF-Linux Desktop 项目特征

| 维度 | 说明 |
|---|---|
| **技术栈** | Electron + React + TypeScript（主）+ Python（核心引擎子进程）|
| **核心机制** | TDSF（Trusted Decision Support Framework）可信决策支持框架 |
| **特色机制** | Ground-Check（地面验证）+ 风险引擎 + 信心评估 + 审计日志 |
| **目标用户** | Linux 运维工程师 + Linux 学习者 |
| **参赛场景** | 2026 火山杯 Agent 创新大赛 |
| **核心能力** | 解析日志 → 生成诊断假设 → 提供修复建议（带证据链）|

### 1.2 调研重点方向

1. **LLM 驱动的运维 Agent**：能解析日志、生成诊断假设、提供修复建议
2. **Root Cause Analysis (RCA) 工具**：基于 AI 的根因分析
3. **日志异常检测**：Drain3 / DeepLog / LogReduce 等日志模板提取与异常检测
4. **可解释 AI 运维**：带证据链的运维决策（与 TDSF 的 Ground-Check 机制匹配）
5. **命令行 AI 助手**：类似 shell-genie / aichat / langchain-cli
6. **可信 AI / 可观测 AI**：带审计日志的 AI 决策框架

### 1.3 评估维度

对每个项目输出：
- 名称、URL、Star、License、技术栈
- 核心功能
- 可借鉴点
- 是否适合集成到 Electron 桌面应用

最终 Top 5 评估维度：
1. **集成难度**（高/中/低）
2. **与 TDSF-Linux 技术栈匹配度**（Electron/Node.js/TypeScript）
3. **是否需要后端服务**
4. **学生项目可控性**
5. **参赛差异化价值**

- ✅ 可参考其 Agent 编排架构和安全护栏设计
- **结论**：参考架构 > 直接集成；适合借鉴 LangGraph Agent 设计模式

  3. Trace 故障检测（Isolation Forest + 状态码双重检测）
  4. Metric 故障汇总（统计对称比过滤 + 两阶段 LLM 分析）
  5. 多模态 RCA（跨模态 Prompt 深度融合）

1. **Drain3 + LLM 的混合架构** — 与 TDSF 计划的日志处理流程完美匹配
2. **结构化 reasoning_trace 输出** — 直接对应 TDSF 的 Ground-Check 证据链
3. **两阶段 LLM 分析策略**（先粗筛再细判）— 可降低 Token 成本
4. **松耦合模块化设计** — 便于在 Electron 主进程中按需调用
5. **CCF 比赛验证过的方案** — 学术 + 工程双重背书，参赛差异化价值极高
6. **跨模态 Prompt 设计** — 可直接借鉴到 TDSF 的 Prompt 模板

**集成到 Electron 桌面应用评估**：
- ✅ Python 实现，可通过 child_process 启动子进程
- ✅ Docker 化部署，便于打包
- ✅ 模块化设计，可逐模块集成
- ⚠️ License 未明确，需联系作者确认
- ⚠️ 偏向微服务场景，需适配单机 Linux 运维
- **结论**：**强烈推荐参考架构 + 借鉴 Drain3 集成模式**，是参赛差异化的核心借鉴对象

### 8.1 调研关键发现

1. **LLM RCA 仍是开放问题**：OpenRCA 评测显示 Claude 3.5 仅 5.37% 准确率，**TDSF 的 Ground-Check 机制有强差异化价值**。
2. **Drain3 是事实标准**：MicroRCA-Agent、ClickStack、TDSF 都用 Drain3，技术路线已被多方验证。
3. **TypeScript 生态成熟**：Langfuse 31K Star、Opik 20K Star，TS/JS SDK 丰富，与 Electron 技术栈匹配度高。
4. **CCF AIOps 挑战赛方案可借鉴**：MicroRCA-Agent Top 5 方案架构清晰，模块化设计可直接参考。
5. **OpenTelemetry 成为主流**：Langfuse、TruLens、AGNTCY 都采用 OTel 标准，TDSF 审计日志应向其靠拢。
6. **MCP 协议兴起**：Opik-MCP、Aurora MCP 支持，可作为 TDSF 桌面端的扩展点。

### 8.2 TDSF-Linux Desktop 推荐集成路线图

  - 输出：JSON 模板 + 模板 ID

  - 位置：同上
  - 调用：CLI 子进程

  - 位置：`tdsf-linux-desktop/src/main/services/llm/client.ts`
  - 自托管轻量版（SQLite 存储）
  - 与 TDSF 现有 `audit-log.ts` 协同
- ✅ **TruLens 集成**（Python 端）— Groundedness 量化评估
  - 位置：`tdsf-linux/src/tdsf/core/grounding.py`
  - 输出：RAG Triad 三指标

#### 阶段 3：架构借鉴与优化（2-3 周）

  - 两阶段 LLM 分析（成本控制）

| Langfuse 后端服务重 | 仅用 SDK 端，本地 SQLite 存储，不走完整后端 |
| MicroRCA-Agent License 未明确 | 仅参考架构，不直接复制代码；联系作者确认 |
| Drain3 中文日志支持 | 使用 DeepSeek-R1 微调，或自定义正则预处理 |
| LLM API 成本 | Cordon 日志降维 + MicroRCA 两阶段分析 + Prompt 缓存 |

### 8.4 参赛差异化价值总结

TDSF-Linux Desktop 相比上述开源项目的核心差异化：

1. **桌面化**：唯一面向 Linux 运维的 Electron 桌面应用（其他都是 Web/CLI）
2. **Ground-Check 机制**：独有的"地面验证"环节，对应 TruLens Groundedness
3. **教学 + 运维双场景**：既可学 Linux 又可做运维，参赛作品应用面广
4. **可信决策框架（TDSF）**：审计日志 + 风险引擎 + 信心评估三位一体
5. **本地优先**：完整可离线运行，符合火山杯对桌面 Agent 的期待

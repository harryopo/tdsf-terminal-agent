# 创意澄清

## 一句话定义

> **TDSF-Linux**：面向Linux运维场景的人机协同可信决策支持框架（Trusted Decision Support Framework for Linux Operations），通过证据驱动的决策镜像、风险感知的交互策略和结构化决策库，让运维Agent的每一步推理都可追溯、可验证、可复盘。

## 使用场景

### 场景1：Web 502故障排查（慢查询引发）

```
用户输入：
  "Nginx返回502，MySQL慢查询日志显示大量全表扫描，应用日志显示连接超时"

系统输出：
  证据链：
    1. [nginx/error.log] upstream timed out (110) → 可信度: 0.95
    2. [app.log] Connection to MySQL refused after 30s → 可信度: 0.90
    3. [mysql/slow.log] SELECT * FROM orders WHERE... (耗时 45s) → 可信度: 0.98
  
  推理链：
    慢查询(45s) → 连接池耗尽 → 应用无法获取连接 → Nginx upstream超时 → 502
  
  排除假设：
    - Nginx配置错误？→ 排除：error.log显示upstream timed out而非connection refused
    - 网络故障？→ 排除：应用日志显示连接建立成功但超时
  
  修复命令：
    1. 优化慢查询SQL（添加索引）
    2. 临时：重启MySQL释放连接
  
  风险评估：
    风险等级: medium
    影响范围: 当前服务
    回滚方案: 索引可删除（DROP INDEX）
```

### 场景2：磁盘满导致服务异常

```
用户输入：
  "MySQL无法写入，df -h显示根分区100%，/var/log占用80%"

系统输出：
  证据链 → 推理链 → 修复命令 → 风险评估
  
  风险评估：
    风险等级: high（涉及日志清理）
    影响范围: 本机全部
    备份建议: 先打包归档重要日志
    回滚方案: 不可回滚（已删除文件无法恢复）
```

### 场景3：OOM Killer误杀进程

```
用户输入：
  "Redis进程消失，dmesg显示Out of memory: Kill process"

系统输出：
  证据链 → 推理链 → 修复命令 → 风险评估
  
  交互策略差异：
    初学者模式：详细解释OOM机制、vm.overcommit_memory参数含义
    专家模式：直接给结论+调整参数的命令
```

## 平台形态

**Web应用（前后端分离）**

```
前端：HTML + CSS + JavaScript（轻量，无框架依赖）
  ├── 日志输入区（多行文本框，支持粘贴多源日志）
  ├── 模式切换（初学者/专家）
  ├── 结果展示区（证据链、推理链、排除假设、修复命令、风险评估）
  └── 决策卡片浏览区（历史Decision Card列表+详情）

后端：Python FastAPI
  ├── main.py（路由与主流程）
  ├── log_collector.py（日志采集与预处理）
  ├── causal_engine.py（因果推理引擎）
  ├── risk_assessor.py（风险评估）
  ├── interaction_policy.py（交互策略决策）
  ├── user_model.py（用户知识档案）
  └── decision_card.py（决策卡片生成与存储）

LLM：火山引擎API（OpenAI兼容接口）
  ├── 因果推理调用
  ├── 风险评估调用
  └── 决策卡片生成调用

存储：
  ├── 文件系统（YAML）：Decision Card存储
  ├── JSON文件：用户知识档案
  └── SQLite（可选）：Decision Library索引
```

## 竞品认知

### 现有方案

| 方案 | 长处 | 弊端 |
|------|------|------|
| **通用LLM（ChatGPT/Claude）** | 通用能力强，开箱即用 | 无证据链、无风险评估、不可追溯 |
| **运维AIOps平台（如阿里云ARMS）** | 企业级，功能全面 | 闭源、昂贵、不透明 |
| **开源运维工具（如Ansible/Puppet）** | 自动化能力强 | 无智能诊断、无因果推理 |

### 本项目的差异化

| 维度 | 本项目 | 竞品 |
|------|------|------|
| **证据链** | ✅ 每条推理锚定到具体日志行 | ❌ 黑盒输出 |
| **排除假设** | ✅ 列出考虑过但排除的其他原因 | ❌ 只给一个答案 |
| **风险评估** | ✅ 每条命令标注风险等级+回滚方案 | ❌ 无风险感知 |
| **交互策略** | ✅ 根据用户经验动态调整详略 | ❌ 千篇一律 |
| **决策追溯** | ✅ Decision Card可复盘 | ❌ 对话历史难以检索 |
| **开源可控** | ✅ 纯开源，可二次开发 | ❌ 闭源或昂贵 |

## 我补充的优化方向

### 1. 演示视频策略（线上评审关键）

线上评审的核心是**演示视频**，建议：
- 3分钟视频，覆盖三个验证场景
- 先展示"传统LLM"的黑盒输出（对比）
- 再展示TDSF-Linux的证据链+风险评估（亮点）
- 最后展示Decision Library的检索和复盘（加分项）

### 2. 前端轻量但专业

2周时间紧张，前端建议：
- 不用React/Vue框架，纯HTML+CSS+JS
- 使用Tailwind CSS快速美化
- 重点做好证据链的可视化展示（这是核心亮点）

### 3. 验证场景数据准备

三个验证场景的真实日志是演示的关键，建议：
- Week 1就开始在虚拟机中制造故障、采集日志
- 不要等到最后才准备数据
- 准备多组数据，避免演示时翻车

### 4. 文档质量决定评审印象

线上评审没有现场答辩，文档质量至关重要：
- README.md要专业（架构图、快速开始、核心特性）
- 技术方案文档要完整（可直接复用论文内容）
- 代码注释要清晰（评委可能看代码）

## 3. Agent 架构核心设计

### 3.1 Supervisor-Subagent 模式（借鉴 Grok Build + Claude Code）

**借鉴来源**：
- Grok Build 的 Plan-Search-Build 三阶段 + 8 并行 subagent（每独立 Git worktree 隔离）
- Claude Code 的四层多 Agent 编排（Task / Background / Agent Teams / Coordinator）
- Mastra v1.34 的 supervisor agents + ACP（Agent Client Protocol）
- Cline 的 Plan/Act 双模式

**设计要点**：

1. **Supervisor Agent**（主协调器）：
   - 接收用户原始任务
   - **Plan 阶段**：拆解任务为子任务（用 Mastra `WorkflowAgent`）
   - **Dispatch 阶段**：将子任务分发给对应 Subagent
   - **Aggregate 阶段**：汇总各 Subagent 结果
   - **Reflect 阶段**：评估结果质量，决定是否重试或结束
   - 输出最终决策 + 可信度评分（v1.1）

2. **8 个特化 Subagent**（对应 6 模块 + 用户额外要求）：

| # | Subagent | 职责 | 主要工具 |
|---|---------|------|---------|
| 1 | **编程 Subagent** | 代码生成、修改、重构 | sftpReadFile / sftpWriteFile / Monaco diff |
| 2 | **思考 Subagent** | 推理、规划、方案设计 | chain-of-thought prompting + Self-Consistency |
| 3 | **运行 Subagent** | 命令执行、结果观察 | ssh:exec / ssh:shell / 沙箱（v1.3） |
| 4 | **搜索 Subagent** | 联网搜索、文档抓取 | WebSearch / WebFetch / agent-reach skill |
| 5 | **Skill Subagent** | Trae/Claude skill 调用 | MCP skill 协议 |
| 6 | **方法论 Subagent** | 运维方法论应用 | 故障排查方法论 / SH 安全指南 / 最佳实践库 |
| 7 | **历史回溯 Subagent** | 历史决策调研调用 | Dexie（IndexedDB）历史检索 |
| 8 | **知识库 Subagent** | RAG 检索 + 数据清洗 | 向量检索 + 命令步骤抽取 |

3. **并行执行策略**：
   - 独立子任务 → 并行（最多 8 路，借鉴 Grok Build）
   - 依赖子任务 → 串行（用 Mastra `WorkflowAgent` 状态机）
   - 每条 Agent 执行必须经过**人工审批闸门**（Hard Constraint，运维安全底线）

4. **沙箱隔离**：
   - **v0.9**：进程级 + 权限白名单（借鉴 Trae/Claude Code 的 auto-allow）
   - **v1.3**：Docker 容器（借鉴 OpenHands 的 REST API 沙箱）
   - **红线命令拦截**：`rm -rf /` / `dd if=/dev/zero` / `mkfs` 等高危命令必须用户确认

### 3.2 Plan-Act-Observe-Reflect 循环（PAOR）

```
用户输入
   ↓
[Plan]  ──→ Supervisor 拆解任务 + 选择 Subagent + 预估 Token
   ↓
[Act]   ──→ Subagent 执行（并行/串行）+ 工具调用 + 人工审批
   ↓
[Observe] ─→ 收集工具返回 + 解析输出 + 计算可信度（v1.1）
   ↓
[Reflect] ─→ 评估质量 + 决策：完成 / 重试 / 升级 / 终止
   ↓
最终输出（带可信度评分 + 证据链）
```

**与 Grok Build Plan-Search-Build 的差异**：
- Grok Build：Plan → Search → Build（三阶段）
- 本方案：Plan → Act → Observe → Reflect（四阶段，多了 Observe 和 Reflect）
- **理由**：运维场景对"观察结果"和"反思质量"要求更高，不能盲执行

### 3.3 上下文管理（借鉴 Claude Code 5 层 compaction）

| 层级 | 触发条件 | 处理策略 |
|------|---------|---------|
| L1 | 单条消息 > 4K tokens | 摘要压缩（Mastra memory `summarize`） |
| L2 | 会话 > 50K tokens | 滑动窗口 + 历史摘要 |
| L3 | 会话 > 100K tokens | 重要节点抽取 + Dexie 持久化 |
| L4 | 会话 > 150K tokens | 用户确认清空 + 归档 |
| L5 | 跨会话 | 长期记忆（vector + Dexie） |

## 6. 思考强度调节

### 6.1 三档思考强度

| 档位 | 适用场景 | 实现 | Token 消耗 |
|------|---------|------|-----------|
| **快速** | 简单问答、查文档 | 单次 LLM 调用，无 Subagent | 低 |
| **标准** | 运维决策、命令生成 | Supervisor + 1-2 Subagent + 1 轮 Reflect | 中 |
| **深度** | 复杂故障排查、方案设计 | Supervisor + 8 Subagent 并行 + 多轮 Reflect + Self-Consistency | 高 |

### 6.2 实现机制

```typescript
type ThinkingStrength = 'fast' | 'standard' | 'deep'

interface AgentOptions {
  strength: ThinkingStrength
  maxSubagents: number      // fast=0, standard=2, deep=8
  reflectRounds: number     // fast=0, standard=1, deep=3
  selfConsistency: boolean  // fast=false, standard=false, deep=true
  costBudget?: number      // 可选：成本预算上限（¥）
}
```

用户在设置页选择档位，Agent 执行时根据档位调整 Subagent 数量和 Reflect 轮数。

## 7. 可信度算法预告（v1.1 实施，v0.9 预留接口）

### 7.1 6 源证据（论文支撑）

| 源 | 论文 | Mass 函数定义 |
|----|------|--------------|
| 日志证据 | D-S 证据理论（Dempster 1967 / Shafer 1976） | 关键词匹配数 / 日志条数 |
| 知识库匹配 | RAG Confidence（Lewis 2020） | 向量相似度 + 检索 Top-K 平均 |
| AI 模型置信度 | Verbalized Confidence（SaySelf 2024 / ConfTuner 2025） | LLM 自评 + Temperature Scaling 校准（0.85 折扣） |
| 人工决策 | Active Learning（Settles 2009） | 标注者一致率 + 标注历史成功率 |
| 历史对话 | Self-Consistency（Wang 2022） | 多次采样一致率 |
| 最佳实践 | Domain Rules | 规则匹配数 / 规则总数 |

### 7.2 融合公式（PCR5 自适应）

```
冲突度 K = Σ m_i(A) × m_j(B), A ∩ B = ∅
if K < 0.3:
    m_fused = Dempster_combination(m_1, m_2, ..., m_6)  // 经典 Dempster 规则
else:
    m_fused = PCR5_combination(m_1, m_2, ..., m_6)      // 高冲突时用 PCR5
```

### 7.3 透明化与可视化

- **公式展示**：每个决策卡片显示 6 源证据的 mass 值 + 融合公式
- **DAG 图**（React Flow）：6 源 → 融合节点 → 决策节点
- **冲突提示**：K > 0.3 时高亮警告"证据冲突，建议人工复核"

### 7.4 v0.9 预留接口

```typescript
// src/main/core/evidence-fusion/types.ts（v0.9 预留，v1.1 实施）
export interface Evidence {
  source: 'log' | 'kb' | 'model' | 'human' | 'history' | 'practice'
  mass: Record<string, number>  // mass 函数：hypothesis → mass
  confidence: number            // 证据自身置信度
  meta?: Record<string, unknown>
}

export interface ConfidenceResult {
  decision: string
  mass: Record<string, number>   // 融合后 mass
  belief: number                // belief 函数值
  plausibility: number         // plausibility 函数值
  conflict: number              // 冲突度 K
  rule: 'dempster' | 'pcr5'    // 使用的规则
  evidences: Evidence[]         // 6 源证据明细
}
```

## 10. Hard Constraints（v0.9 追加）

1. **不反编译 Claude Code**：法律风险高，用官方 SDK 合法集成
2. **不引入 Gemini CLI / Roo Code**：已闭源化 / 已归档（21 号报告红线）
3. **不引入 Python 进程**：Agent 必须用 TS 原生框架（Mastra），避免 IPC 跨语言
4. **每条 Agent 执行必须有人工审批闸门**：运维安全底线
5. **所有网络请求必须 UI 可见**：借鉴 Grok Build 数据丑闻教训，禁止静默上传
6. **敏感文件默认 redact**：`.env` / `.ssh/` / `*_key` 等发送前自动脱敏
7. **本地优先**：默认本地 Ollama / 国内 Provider，海外 API 需用户显式开启
8. **Token 消耗必须透明**：每次 Agent 执行后展示 token 消耗 + 成本

## 12. Lessons Learned（v0.9 预判）

1. **开源调研必须查最新动态**：Gemini CLI 2026-05-19 闭源化、Roo Code 2026-05-15 归档——半年前的调研可能已失效
2. **数据丑闻是最好的反面教材**：Grok Build 静默上传 .env 事件直接促成本方案"所有网络请求必须 UI 可见 + 敏感文件 redact"的 Hard Constraint
3. **论文支撑是可信度算法的底线**：D-S + PCR5 有 1976 / 2004 年原始论文 + 43 篇近期论文，避免"拍脑袋"
4. **官方 SDK 优先于反编译**：Claude Code 反编译法律风险高，官方 `@anthropic-ai/claude-agent-sdk` 是合法路径
5. **TS 原生 vs Python**：Electron 项目坚持 TS 原生（Mastra），避免 Python 进程通信复杂性
6. **并行 subagent 不是越多越好**：Grok Build 最多 8 路，但运维场景多数任务 2-3 路足够，思考强度三档调节
7. **DirectChatTransport 是 Electron 集成的杀手级能力**：Renderer 直持 Agent 跳过 HTTP，性能与 UX 双赢

## Q1：为什么不直接集成完整 DoWhy / smolagents？

**背景**：调研时发现 DoWhy (120MB) + smolagents (180MB) 总计 300MB+ 依赖。

**答**：分两阶段集成，v1.5 先把架构和 UI 跑通，v1.6 再上真实依赖。

**理由**：
1. **风险隔离**：先验证多 Sidecar 架构是否稳定，避免一上来就背 300MB 包袱导致排查复杂
2. **质量优先**：v1.5 占位实现能保证 IPC 协议稳定（schema 已确定），v1.6 集成真实算法时只换 adapter 即可
3. **体积可控**：v1.5 共享 venv 增加 ~0MB，v1.6 拆分后单 sidecar 增加 120-180MB
4. **业务驱动**：smolagents 的 2 行范式只有在 SidecarManager 多进程管理稳定后才值得集成

**关键决策（DEC-1）**：Sidecar-B/C 共享 Sidecar-A 的 venv
- ✅ v1.5：仅 fastapi/uvicorn/pydantic
- ✅ v1.6：拆分独立 venv（按需加载重依赖）

## Q2：LLM 增强诊断会不会拖慢响应时间？

**背景**：担心 LLM 调用 5-10s 延迟影响 SRE 诊断实时性。

**答**：双阶段 + 10s 超时 + 优雅降级，UI 不会卡。

**实现**：
```python
def diagnose(self, log_templates, llm_config=None):
    # 阶段 1：规则匹配（0.1s 内完成）
    rule_result = self._rule_match(log_templates)
    
    # 阶段 2：LLM 增强（可选，10s 超时）
    if llm_config:
        try:
            llm_result = self._call_llm(rule_result, llm_config, timeout=10)
            return self._merge(rule_result, llm_result)
        except TimeoutError:
            rule_result["source"] = "rule-based-llm-timeout"
            return rule_result
```

**理由**：
1. **规则 baseline 永远可用**：先给用户一个稳定结果
2. **LLM 增强可选**：UI toggle，用户主动开关
3. **超时降级**：10s 内 LLM 不返回就降级到规则
4. **标记透明**：`source` 字段（rule-based / llm-enhanced / llm-timeout / llm-failed）用户能看清来源

**关键决策（DEC-2）**：OpenDerisk 双阶段诊断
- ✅ 用户体验：永远秒级响应
- ✅ 质量提升：复杂场景 LLM 兜底
- ✅ 可观测：source 字段透明

## Q3：为什么用 RRF 而不是直接加权求和分数？

**背景**：FTS5 分数是负值（-10 ~ 0），余弦距离是正值（0 ~ 2），量纲不同。

**答**：RRF 只关心排名，对分数尺度不敏感，工业级方案。

**核心公式**：
```
score(d) = Σ_i  w_i / (k + rank_i(d))
```
- `k=60`（Cormack 2009 论文经验值）
- `w_i` 默认 1.0（可按场景调）

**理由**：
1. **量纲无关**：BM25 负值 + 余弦距离正值，无法直接相加
2. **鲁棒性强**：只关心排名，对分数绝对值不敏感（某一路异常不会主导结果）
3. **无训练**：vs LambdaMART 等 supervised 方法，RRF 是无参的
4. **效果相当**：Cormack 2009 论文证明 RRF 在多种任务上优于 Condorcet 和单独 rank learning

**测试验证**（npx tsx verify-hybrid-search.ts）：
- 双路命中 a.rrfScore=0.03252 > 单路 c.rrfScore=0.01587 ✓
- 排名首位为双路命中条目 ✓
- c（仅 FTS）和 d（仅 vec）source 正确标记 ✓

**关键决策（DEC-7）**：RRF k=60
- ✅ 论文经验值
- ✅ 工业级主流方案（ElasticSearch / OpenSearch 默认）

## Q4：多 Sidecar 共享 venv 会不会导致依赖冲突？

**背景**：Sidecar-B 后续要装 dowhy + statsmodels，Sidecar-C 要装 torch + transformers。

**答**：v1.5 共享 OK，v1.6 拆分。共享 venv 增加 0 体积，独立 venv 增加 300MB。

**v1.5 共享 venv 依赖**（极简）：
- fastapi>=0.110（HTTP server）
- uvicorn>=0.29（ASGI runtime）
- pydantic>=2.0（数据模型）

**v1.6 拆分计划**：
| Sidecar | v1.5 依赖 | v1.6 新增 | 体积 |
|---------|---------|----------|------|
| A (SRE) | fastapi + uvicorn + pydantic + drain3 + openai | 不变 | ~30MB |
| B (Analytics) | 同上（共享） | + dowhy + econml + statsmodels | +120MB |
| C (Agent) | 同上（共享） | + smolagents + torch + transformers | +180MB |

**理由**：
1. **v1.5 阶段**：B/C 仅占位，重依赖未集成，共享 venv 无冲突
2. **v1.6 阶段**：分别建 venv-sidecar-b 和 venv-sidecar-c，通过 SidecarConfig.pythonPath 指定
3. **SidecarManager 已支持**：每 sidecar 独立 `pythonPath` 字段，共享/独立 venv 切换零代码改动

**关键决策（DEC-1 重申）**：v1.5 共享 + v1.6 拆分
- ✅ v1.5 部署体积最小化
- ✅ v1.6 用户可按需启用（默认共享，配置切独立）
- ✅ 架构无侵入，配置驱动

## 二、桌面软件 vs Docker 部署：优劣对比分析

### 2.1 对比矩阵

| 维度 | **桌面软件（TDSF v6.0）** | **Docker 部署（如 databuff/焰龙AI）** | TDSF 优势 |
|------|------------------------|----------------------------------|-----------|
| **部署门槛** | 双击安装即用，零配置 | 需 Docker 环境 + docker-compose | ⭐⭐⭐⭐⭐ |
| **网络要求** | 离线可用，仅 LLM 调用需网络 | 需拉镜像、依赖镜像源 | ⭐⭐⭐⭐⭐ |
| **SSH 密钥安全** | 本地 safeStorage 加密，不走云端 | 私钥需上传到服务器，有泄露风险 | ⭐⭐⭐⭐⭐ |
| **LLM Key 安全** | 用户本地持有，不上传 | 服务端存储，多租户隔离复杂 | ⭐⭐⭐⭐⭐ |
| **教学场景适配** | 学生本地装、即开即用 | 需准备服务器，与"装系统"教学冲突 | ⭐⭐⭐⭐⭐ |
| **离线可用性** | 部分功能（SSH/终端/监控）离线可用 | 整体依赖容器编排 | ⭐⭐⭐⭐ |
| **多服务器管理** | 单机管理多服务器 | 集中式管理 | ⭐⭐⭐ |
| **可扩展性** | 单机性能瓶颈 | 横向扩展容易 | ⭐⭐ |
| **数据持久化** | 本地 SQLite，简单可靠 | 需 Volume 挂载，备份复杂 | ⭐⭐⭐⭐ |
| **更新机制** | electron-builder 自动更新 | docker pull 重启 | ⭐⭐⭐ |
| **资源占用** | 100-300MB 内存 | 容器+镜像 1-3GB | ⭐⭐⭐⭐ |
| **跨平台一致** | Win/Mac/Linux 三端 | 仅 Linux 服务器 | ⭐⭐⭐⭐ |
| **学生可控性** | 学生完全掌握代码与数据 | 黑盒容器，调试困难 | ⭐⭐⭐⭐⭐ |
| **运维门槛** | 无需运维 | 需懂 Docker/K8s | ⭐⭐⭐⭐⭐ |
| **大赛演示效果** | 现场安装演示，评委直观 | 需预置环境 | ⭐⭐⭐⭐⭐ |

### 2.2 关键洞察

#### 2.2.1 桌面软件的"五杀"优势

1. **教学场景天然契合**：学生学 Linux 就是因为本地装不上，桌面软件装在 Windows/Mac 上连接 Linux 服务器，正是教学标准姿势
2. **凭证安全第一**：SSH 私钥是运维命脉，桌面端 safeStorage 加密本地存储，比上传到 Docker 服务端安全得多
3. **零运维负担**：学生项目 3 周开发周期，没有时间运维服务器，桌面软件"装即用"是唯一可行路径
4. **现场演示震撼**：评委双击 exe/dmg，30 秒内看到 AI 运维助手工作，Docker 部署需要 5-10 分钟环境准备
5. **代码可读性**：学生项目要展示代码质量，桌面软件代码结构清晰，Docker 黑盒难讲清原理

#### 2.2.2 Docker 部署的适用场景（TDSF 不适用）

- 企业级多租户 SaaS（TDSF 是单机教学）
- 需要弹性扩缩容（TDSF 单用户）
- 微服务架构天然分布式（TDSF 是单体）
- 已有 K8s 集群可复用（学生没有）

#### 2.2.3 混合模式建议（小范围 Docker）

TDSF 可在**故障模拟环境**中使用 Docker：
- `docker-compose.yml` 启动一个故障 Linux 容器（OOM/磁盘满/502）
- 桌面端 SSH 连接该容器做诊断
- 这样既保留桌面优势，又能用 Docker 做故障演练

**建议**：在 `tdsf-linux-desktop/docker/` 下新增 `fault-simulation/` 目录，提供 3 个故障模拟容器（OOM/磁盘满/慢查询）。

### 2.3 结论

**TDSF 桌面软件路线 100% 正确**，无需改 Docker。Databuff 的 Docker 路线适合企业 APM 场景，但与 TDSF 的"教学+可信决策"定位不匹配。

| 风险控制 | 事后审计 | 事前 4 层拦截 |

| 教学价值 | 命令生成器 | 让学生看到 AI 推理过程 |

#### 3.2.3 演示差异化（必做）

1. **现场让评委操作**：评委自己输入故障描述，看 AI 推理

3. **故障注入**：用 Docker 现场注入 OOM 故障，TDSF 实时诊断
4. **代码可读**：评委可现场看 TypeScript 源码，结构清晰

## 七、关键结论

### 7.1 技术路线 100% 正确

TDSF v6.0 的技术栈选型（Electron + React + TS + ssh2 + xterm.js + Ant Design + better-sqlite3 + sqlite-vec + safeStorage）与调研发现的最佳实践**完全一致**，无需大改。

### 7.2 桌面软件路线 100% 正确

对比 Docker 部署，桌面软件在 TDSF 场景下有"五杀"优势（教学契合/凭证安全/零运维/演示震撼/代码可读），无需切换。

### 7.3 参赛差异化核心

**TDSF 不是"AI 替代运维"，而是"AI 让运维可解释"**。这个叙事要贯穿方案书、PPT、演示视频。

### 7.4 新增技术栈价值

| 新增 | 价值 |
|------|------|
| Vercel AI SDK 7 | TS 原生 Agent，简化 workflow |
| Langfuse | LLM trace 可视化，评委爽点 |
| MCP TS SDK | 让 Claude Code 调用 TDSF，差异化 |
| Drain3 (Python) | 学术深度，论文引用 |

### 7.5 databuff 借鉴清单

| 借鉴点 | 集成难度 | 价值 |
|--------|---------|------|
| Tool Calling 替代 RAG | 中 | ⭐⭐⭐⭐⭐ |
| Brain+Experts 多智能体 | 中 | ⭐⭐⭐⭐⭐ |
| Skill 包分层文件系统 | 低 | ⭐⭐⭐⭐⭐ |
| Agent 可观测 | 低（用 Langfuse） | ⭐⭐⭐⭐ |
| MCP Server 暴露 | 中 | ⭐⭐⭐⭐⭐ |

### 7.6 最终决策

- ✅ 保持 Electron 桌面软件路线
- ✅ 集成 Vercel AI SDK 7（不替换，补充）
- ✅ 集成 Langfuse SDK（可观测性）
- ✅ 集成 MCP TS SDK（差异化）
- ✅ 集成 Drain3 Python 子进程（学术深度）
- ✅ 撰写方案书 v7.0
- ❌ 不切换 Docker 部署
- ❌ 不复制 databuff 代码（AGPL-3.0）
- ❌ 不引入 LangGraph.js（Vercel AI SDK 更轻量）
- ❌ 不引入 LlamaIndex.TS（已废弃）

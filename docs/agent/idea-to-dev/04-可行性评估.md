## 5. 风险评估与应对

### 5.1 风险矩阵

| 风险 | 概率 | 影响 | 风险等级 | 应对策略 |
|------|------|------|---------|---------|
| **LLM因果推理不准确** | 中 | 高 | 🔴 高 | Prompt Engineering反复调优 + DoWhy验证 + 人工校验 |
| **开发周期超出预期** | 中 | 高 | 🔴 高 | MVP策略 + 优先级排序 + 缓冲时间 |
| **验证场景数据获取困难** | 中 | 中 | 🟡 中 | 利用现有项目文档 + 快速复现 + 备用场景 |
| **LLM API调用超时** | 中 | 中 | 🟡 中 | 超时设置 + 重试机制 + 降级方案 |
| **大赛时间调整** | 低 | 高 | 🟡 中 | 密切关注通知 + 灵活调整 + 优先核心功能 |
| **前端页面开发延迟** | 低 | 低 | 🟢 低 | 使用UI框架 + 优先核心功能 + 可先用命令行 |
| **火山引擎API额度不足** | 低 | 高 | 🟢 低 | 已有额度 + 优化Prompt + 备用LLM |

### 5.2 风险应对策略总结

**核心策略**：
1. **MVP策略**：先实现最小可行产品（3个核心模块），再迭代优化
2. **优先级驱动**：P0（核心机制）→ P1（Decision Card）→ P2（前端优化）
3. **快速验证**：每完成一个模块立即测试验证，不积累问题
4. **缓冲预留**：每个阶段预留1天缓冲时间
5. **降级方案**：前端延迟可先用命令行，LLM超时可用缓存

### 5.3 最坏情况分析

**最坏情况**：因果推理Prompt调优失败，无法生成准确的证据链

**影响**：核心功能无法实现，大赛失败

**应对策略**：
1. 提前准备3套Prompt模板（简单版/标准版/复杂版）
2. 在Day 3-5集中测试，快速迭代
3. 如果LLM方案失败，降级为规则引擎（基于现有error_reference.py）
4. 最坏情况下，可展示"规则引擎+简单因果链"的MVP

**剩余风险**：低（有降级方案）

## Q1：为什么不直接用 logprobs 计算熵，而是用 text-feature proxy？

**背景**：调研时发现 Anthropic Claude API 不暴露 logprobs，OpenAI API 暴露但 Vercel AI SDK v7 默认不开启。

**答**：分 3 优先级降级（trace source priority），用 text-feature entropy 作为 fallback 信号。

**理由**：
1. **API 兼容性**：Anthropic 不暴露 logprobs，强行用 logprobs 会把 Claude 排除在外（而 Claude 是高质量 reasoning model）
2. **成本**：Zhao 2026 论文使用 per-step answer-distribution entropy（每个 step 重新问 LLM），成本 ×N 不现实
3. **论文验证**：Zhao 2026 §4 明确验证了"即便用 text-feature proxy，**形状单调性**仍有预测力"
4. **降级兜底**：3 优先级 thinking → turn → text-fallback，覆盖所有主流模型

**关键决策（DEC-1）**：3 优先级降级策略
- ✅ 源 A：Anthropic Claude with `thinking: { type: 'adaptive' }`（最高质量，LLM 自标 step 边界）
- ✅ 源 B：DeepSeek-R1 / o1 reasoning model（turn 边界明确）
- ✅ 源 C：text-feature entropy（任何文本输出，字符级 Shannon 熵归一化到 [0, 1]）

## Q2：为什么 3 优先级互斥，而不是叠加？

**背景**：thinking block + turn text + fallback 切分是否可以同时进入 trace？

**答**：互斥设计，thinking 一旦记录就不再 fallback 切分。

**理由**：
1. **避免重复计算**：同一段推理被 thinking 记录后，再 fallback 切分会双计（trace 长度虚高）
2. **保护 step 边界**：Zhao 2026 的 trace 是 per-step answer-distribution，每个 step 一个点；thinking block 是最接近的代理，叠加会扭曲单调性分析
3. **降低 trace 噪声**：fallback 启发式切分（按标点）远不如 LLM 自标 step 准，叠加会让弱信号污染强信号
4. **简化分析**：cot-trace-signal.ts 的 `analyzeCotEntropyTrajectory` 输入是单源 trace，互斥设计避免归并逻辑

**关键决策（DEC-2）**：CotTraceCollector 状态机互斥
- ✅ `recordThinkingBlock` / `recordTurnText` 一旦调用，`finalize()` 就不再切分 fallback
- ✅ `accumulateFinalText` 仅在前两者未调用时才在 finalize 时切分

## Q3：splitBySentences 阈值为什么是 4 而不是 8？

**背景**：原代码用 8 字符阈值，导致中文 4 字短语被全部合并成 1 段，测试失败。

**答**：阈值 4 字符 + "只在上一句也过短时合并" 约束。

**理由**：
1. **中文 4 字符是合理粒度**：4 个汉字已能稳定计算 Shannon 熵（字频分布够丰富）
2. **英文 4 字符过滤垃圾**：3 字符 "OK." / "Yes." 几乎无信息量，需合并；4 字符 "Yes!" 已能稳定算熵
3. **"只在上一句也过短时合并" 避免反复吸入**：否则短句会不断合并到下一句再被合并到再下一句，trace 长度虚低
4. **测试验证**：4 字中文短句（如"第一句。"）现在能保留为独立 trace point

**踩坑教训**：
- 原方案「阈值 8 + 无条件合并」→ 4 字中文"反复吸入"到 1 段，测试 expected 1 to be ≥ 3 失败
- 修复方案「阈值 4 + 只在前一句也过短时合并」→ 中英文均能稳定切分

**关键决策（DEC-3）**：splitBySentences 合并规则
- ✅ 阈值 4 字符（常量 `MIN_SENTENCE_LEN = 4`，便于文档化）
- ✅ 合并条件：`s.length < 4 && last.length < 4`（两个都过短才合并）
- ✅ 长句不参与合并（避免反复吸入）

## Q4：ChatResult.cotEntropyTrajectory 为什么要放在共享类型？

**背景**：是否应该把 trace 放在 main 进程内部状态，不暴露到 IPC？

**答**：放在 shared/agent-types.ts 共享，三端都可见。

**理由**：
1. **渲染层需要透传**：渲染层 `buildCredibilityInputs` 把 trajectory 传给 `credibility:assess` IPC，需要类型支持
2. **Preload 类型一致性**：preload 暴露的 `credibility:assess` channel 必须接受 `number[]` 字段
3. **审计可追溯**：trajectory 是决策元数据，审计报告（EU AI Act 12 类风险）需要可重建
4. **避免类型漂移**：三端独立定义会导致 IPC structured clone 失败（类型不匹配抛错）

**关键决策（DEC-4）**：cotEntropyTrajectory 放在 ChatResult 共享类型
- ✅ `ChatResult.cotEntropyTrajectory?: number[]`（可选，向后兼容）
- ✅ `CredibilityEvidenceInput.fields: Record<string, number | boolean | number[]>`（类型扩展 + IPC 字段约束）
- ✅ 新增 `getOptionalNumberArray` 辅助函数做运行时类型守卫

## Q5：textShannonEntropy 归一化基数为什么用 36？

**背景**：候选值 log₂(26)（26 字母）/ log₂(36)（26 字母 + 10 数字）/ log₂(text.length)（严格信息论）

**答**：用 log₂(36) = 26 字母 + 10 数字，覆盖可观察英文/数字字符集。

**理由**：
1. **26 字母过窄**：数字（0-9）和标点是常见字符，26 字母归一化会让含数字文本熵虚高
2. **text.length 不稳定**：完全均匀短文本（如 4 字符全不同）会让熵爆炸到 1.0 之外
3. **36 是经验值**：26 字母 + 10 数字 ≈ ASCII 可打印子集；中文字符按 36 上界做保守归一化
4. **跨语言鲁棒**：中英混排（如 "CPU 95% 持续 5 分钟"）归一化后熵仍稳定在 [0, 1]

**关键决策（DEC-5）**：textShannonEntropy 归一化基数
- ✅ `maxEntropy = log₂(min(uniqueCount, 36))`
- ✅ 中文/特殊字符超出 36 时按 36 上界保守归一化（避免熵虚高）
- ✅ NaN/Infinity/越界兜底：clamp 到 [0, 1]

## Q6：v0.9.7+ 还有什么优化空间？

**背景**：P2 M5+ 采集层完成，但仍有 2% 优化空间。

## Q7：CoT-shape 失败时如何兜底？

**背景**：trace 数据可能缺失 / 非法 / 边界值，需要优雅降级。

**答**：3 层兜底，保证 `llm_conf` 始终在 [0, 1]。

| 场景 | shapeConf | 实际效果 |
|------|-----------|---------|
| 不传 `cotEntropyTrajectory` | 跳过 | 保持 P1 行为（向后兼容）|
| 传 `undefined` | `null` | 跳过 |
| 传 `[]`（空数组） | 0.5（中性默认）| 0.7·llm_conf + 0.3·0.5 = 略偏移 |
| 传单步 `[0.7]` | 0.6 | 略偏移 |
| 传合法单调链 | 0.85 | 拉高 |
| 传合法非单调链 | 0.10/0.30/0.55 | 拉低 |
| 传非法值（NaN/Inf/越界）| 由 `analyzeCotEntropyTrajectory` 兜底为 [0, 1] | 优雅降级 |

**安全保证**：所有非法输入都不会让 `llm_conf` 越界到 [0, 1] 之外，因为 `cotEntropyTrajectoryConfidence` 的返回值已经在 [0, 1]。

**关键决策（DEC-7）**：CoT-shape 失败兜底
- ✅ 类型层：`cotEntropyTrajectory?: number[]` 可选
- ✅ 运行时层：`analyzeCotEntropyTrajectory` 边界检查（空/单步/NaN/Infinity/越界）
- ✅ 融合层：`createAiParamMassFunction` 检查 `cotEntropyTrajectoryConfidence` 返回 null 时跳过

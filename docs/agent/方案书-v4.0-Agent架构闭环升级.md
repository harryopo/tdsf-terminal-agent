# 方案书 v4.0 — Agent 架构闭环升级（感知 → 思考 → 行动 → 记忆）

> 定位：**精简有力，聚焦闭环**。不重做已达标的模块（安全 4/5、UI 4/5、todo UI 链路 4/5），
> 只修断点、只接现成资产、只补真缺的能力。
> 参照：DeepSeek Harness（一切皆插件 / PTC 程序化工具调用 / Model+Harness=Agent）、
> Claude Code（TodoWrite 驱动循环 / 迭代预算）、strands SDK 1.53.0 原生能力清单。
> 调研依据：`docs/agent/` 既有调研报告 + 2026-08-31 全项目 12 项差距盘点。

---

## 0. 一个公式

```
真正的 Agent = LLM（思考） + Harness（手脚）
              感知 → 思考 → 行动 → 记忆 → 再感知……直至完成
```

现状诊断（12 项差距盘点结论）：**循环本体不缺**（strands SDK 自带完整 agentic loop +
并行工具执行 + LLM 重试退避，全是白得的），缺的是**四层闭环的断点**：

| 断点 | 症状 | 根因 |
|------|------|------|
| **感知→思考断裂** | 切模式/开教学 = 对话历史全丢 | Agent 实例缓存 key 卷入了 mode/teach/perm |
| **思考→行动断裂** | 多步任务靠 LLM 即兴，清单不驱动执行 | todo 是"显示用清单"，loop 不读不校验 |
| **行动→无护栏** | 工具失败风暴无上限 | ToolCallLimitHook 写了但 `hooks=[]` 没挂 |
| **行动→记忆断裂** | 记忆只等 LLM 主动想起来查 | 无首轮 RAG 召回注入 |

另有一批**"写了没接线"的资产**：fix_loop 熔断（只接了 LangGraph 死路径）、
long_context.py（独立服务未入链）、SDK `conversation_manager="auto"`（一行未用）。
本方案第一原则：**先接线，再造轮子**。

## P0 — 闭环修复（把断的接上，1 个迭代）

> 目标：四层闭环物理连通。全部是接线/迁移级改动，无新架构。

### T1 上下文连续性（感知→思考）
**问题**：`adapter.py` 实例缓存 key = (session, perm, mode, teach)——任何切换即重建
Agent 实例 = messages 全丢。
**方案**：
1. **messages 与 Agent 实例解耦**：会话消息历史独立存储（per-session），Agent 实例
   重建时把历史重新装载（strands 支持 messages 注入）。
2. 模式/教学只影响**系统提示词与工具集**，不再影响历史——切换模式后 agent 仍记得
   之前说过什么。
3. 顺手接线：`conversation_manager="auto"`（SDK SummarizingConversationManager：
   0.85 阈值自动摘要压缩 + ContextOffloader 离线存储）——上下文压缩零成本获得。
**验收**：对话中切 observe→confirm→auto，历史连续；超长对话自动压缩不报错。

### T2 循环护栏（行动）
**问题**：ToolCallLimitHook 已实现（max=12/连续失败 3 熔断）但 `hooks=[]` 被摘。
**方案**：重新挂载，参数调整为**熔断保命 + 上限放开**：
- 连续失败 ≥3 → 熔断停止并向用户报告（保命）
- 单轮任务工具调用上限放开到 50（规划长任务的自由度）
- 每轮把「第 N 轮 / 已用工具 M 次」写入 agent_log + 前端状态条（循环进度可见）
**验收**：故意让工具持续报错 → 3 次后熔断并出解释；正常长任务不受 12 上限误杀。

### T3 规划-执行回环（思考→行动）
**问题**：todo_write 全链路（工具→rust_bridge→TodoStrip UI）已通，但 loop 不读它。
**方案**（prompt 层 + 收尾校验层，轻量）：
1. 系统提示规划段升级：**多步任务（≥3 步）必须先 todo_write 建清单再动手**；
   每完成一项立即更新状态。
2. invoke 收尾钩子：循环结束时检查 todo——存在未完成项 → 追加一轮提示
   "清单还有 N 项未完成，继续或向用户说明原因"（一次机会，防死循环）。
3. TodoStrip 显示实时进度（已有 UI，补 per-item 完成时间戳）。
**验收**：给一个 5 步运维任务（查状态→改配置→重启→验证→记录），agent 主动建清单
逐项打勾，收尾时全部 completed。

### T4 记忆主动召回（记忆→感知）
**问题**：session-memory 沉淀后，只靠 LLM 想起来调 search_history。
**方案**：**每轮**（非仅首轮）在上下文组装时检索：query=当前用户消息，top-3 相关
历史案例/技能注入 `<recalled-memory>` 区（区分首轮的 session-memory 注入：那个是
会话级摘要，这个是任务级案例）；3s 超时静默跳过。
**验收**：让 agent 处理过一个 samba 故障 → 新会话问类似故障 → 回答引用上次经验。

## P1 — 真实能力开发（长出工具，1-2 个迭代）

> 目标：从"能对话"到"能干活"。参考我自己开发时用到的工具类比。

### T5 PTC：Python 工具（行动层质变）
**类比**：我（开发 agent）日常用 RunCommand 跑脚本、用多工具并行交叉验证——
人类工程师不会一次只问一个工具。dsh 的 PTC 模式证明了这是效率核心。
**方案**：新工具 `python_run`：
1. 受控执行：SDK 原生 `sandbox` 参数（agent.py 已支持未启用）+ 超时 30s +
   输出截断 10KB + 工作目录锁定 workspace。
2. 用途明确写进提示词：**多文件交叉统计、复杂解析、批量操作**——写一段 Python
   串起 grep/读文件/算结果，比逐工具往返快 10 倍。
3. 审批策略：observe 模式 schema 裁剪（自动不可用）；confirm 模式需审批；
   auto 模式免审（代码在沙箱内，无网络无持久写）。
**验收**："统计 /etc 下所有 .conf 文件里含 bind 的行并汇总" → agent 写 python 一次完成。

### T6 Skill 剧本化（思考→行动的复用）
**问题**：7 个内置 skill 大多是"知识卡"（返回资料），不是"剧本"（驱动流程）。
**方案**：SKILL.md 格式扩展 `steps:` 段（有序步骤清单，每步=工具调用意图+成功判据）：
1. skill_invoke 命中带 steps 的技能 → 把剧本注入对话（agent 按步骤驱动工具序列）
2. 优先改造 2 个高价值技能做样板：`systemd-troubleshoot`（查状态→看日志→定位→
   修复→验证 五步剧本）、`selinux-baseline`（查模式→看上下文→策略调整→audit 验证）
3. 步骤进度同步到 TodoStrip（与 T3 共用 UI）
**验收**：触发 systemd-troubleshoot 技能 → agent 按剧本走五步，每步有工具调用证据。

### T7 执行后验证回环（审查机制）
**问题**：改完配置不验证服务是否正常（Harness 的 verify-before-done 缺失）。
**方案**：系统提示行动段加约束 + 收尾校验：
1. **凡改动系统状态（写文件/执行命令/改配置），必须用只读工具验证结果**
   （systemctl status / cat / test）才能宣告完成。
2. 收尾钩子（与 T3 共用）：检测到"有写操作但无验证操作"→ 追加提示补验证。
**验收**：让 agent 改 nginx 配置 → 自动 `nginx -t` 验证后才说"完成"。

## P2 — 稳定性与测试基建（1 个迭代）

### T8 回放测试（利用日志后端）
agent_log JSONL 已落盘六类事件——补 `replay` 测试工具：读日志 → 重放 user_msg/
tool_result 序列 → 断言 agent 行为（工具选择/顺序/是否验证）。**行为回归从此有据可依**。
沉淀 5 个真实场景回放集（模式切换连续性/熔断/todo 长任务/验证回环/记忆召回）。

### T9 稳定性补强
1. LLM 调用显式超时（model_adapter 加 timeout，SDK 支持）+ invoke 整体 watchdog
   （10 分钟无输出 → 超时报告）。
2. LLM 不可用降级：报错卡 → **只读问答模式**（提示用户当前仅能咨询，不能执行）。
3. 工具并行利用：提示词鼓励"独立信息收集类操作一次发出多个工具调用"
   （SDK ConcurrentToolExecutor 白得）。

### T10 置信度与证据链深化
1. 置信度标准固化为三档+明确判据（高：有工具证据+知识库佐证；中：其一；
   低：纯推理）——低档必附原因（已做），高档也展示依据来源。
2. 证据链 UI：证据区按"收集→执行→验证"分组展示（与 T7 呼应）。

## 不做什么（防大杂烩）

| 提议 | 决定 | 理由 |
|------|------|------|
| 迁移到 Cordis 插件内核 | ❌ | 重写级工程，Tauri+Rust+Python 三层架构不适用"一切皆插件"哲学；注册表模式已够用 |
| MCP 客户端（T13） | ⏸️ 顺延 | PTC/剧本/验证回环价值更高且是内生能力；MCP 是外延生态，P3 再说 |
| 子 Agent 委派 | ❌ 暂不 | §37.81 已删（4 子 agent 架构被用户否定）；单 agent + 工具并行够当前规模 |
| 前端 agent_log 查看器 | ⏸️ | debug.agent_log_tail RPC 已够我诊断；UI 化等用户提出 |
| RAG 引擎升级（cross-encoder/bge-m3） | ⏸️ | 检索质量已满足；优先把钱和时间花在闭环上 |

```
P0（闭环修复）──────→ P1（真实能力）──────→ P2（稳定+测试）
```

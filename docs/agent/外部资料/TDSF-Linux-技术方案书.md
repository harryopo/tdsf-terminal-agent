# 一、  方案定位

当前 AIOps 赛道已有企业级成熟产品规模化落地——公开信息显示，头部云厂商的 AIOps Agent 已在数千家企业部署，将故障平均修复时间压缩到 15 分钟以内，核心叙事正是「低风险任务自动化、重要操作保留人机协同决策」。这意味着「风险分级 + 人机协同」这个思路本身已不算新鲜，团队级/学生项目如果正面复刻这一叙事，很难在创新性上打动评审。

因此本方案的差异化定位不是与企业级平台比自动化程度，而是反其道而行：企业级 AIOps 面向规模化 SRE 团队，卖点是「减少人力依赖」；TDSF-Linux 面向个人开发者、初级运维和在校学生，卖点是「证据可核验、风险可感知、经验可沉淀」——帮助使用者在被 AI 辅助的同时，真正建立起独立诊断的判断力，而不是把判断力让渡给一个黑盒。

为了让「可信」不停留在口号，技术上只做三件事，但要做扎实：

▪ 让 AI 的每一条结论都能追溯到真实证据，而不是模型自己声称的一个置信度数字；

▪ 让中高风险操作必须经过人工确认，且确认时看到的证据链是可核验、可核实的，不是摆设；

▪ 让每一次诊断的经验都能反哺下一次诊断，系统随着使用而变得更准，而不是每次从零开始。

# 四、  核心推理与决策算法

这一节是整个方案里技术分量最重的部分，对应评审标准中「技术实现与复杂度」30% 的权重。四个机制环环相扣，核心思路是：把「可信」从一句口号变成可计算、可复现、可被追问的具体机制。

## 4.1　证据置信度：从「LLM 自称」到「可计算」

很多同类系统的「置信度」本质是让 LLM 在输出 JSON 时顺手编一个数字，这个数字和模型是否真的正确并没有稳定关系，一旦被评审追问「这个 0.95 是怎么算出来的」就很难自圆其说。TDSF-Linux 的置信度改为完全由可复现的规则计算：

| confidence(evidence_i) = α · match_score_drain3 + (1-α) · source_prior   match_score_drain3 ∈ [0,1]：Drain3 对该日志行相对模板库的匹配程度   · 精确匹配已知故障模板           → 1.0   · 匹配到日志级别/结构但参数不同   → 0.6~0.8   · 无法匹配任何已知模板（全新日志）→ 0.3，标记为待补充模板   source_prior：日志来源的固定先验权重（人工标定一次即可）   例：{dmesg: 0.95, mysql/error.log: 0.90, app.log: 0.75}   α 取 0.7 —— 更信任可计算的模板匹配，而非人工先验 |
| --- |

这个数字不是模型编的，是 Drain3 的匹配结果和一张写死的先验表算出来的——全程可复现、可解释，评审现场可以当场追问、当场验证。

## 4.2　证据溯源校验（Ground-Check）

Evidence Chain 里的每一条证据，在进入最终结论之前，必须先证明自己「确实来自某一次真实的工具调用」，而不是模型顺着上下文编出来的一句听起来很像证据的话：

| def ground_check(evidence_chain, tool_call_transcripts):     verified, rejected = [], []     for ev in evidence_chain:         if any(ev.raw_text in t.output for t in tool_call_transcripts):             verified.append(ev)         else:             rejected.append(ev)   # 疑似幻觉，不计入最终证据链     return verified, rejected |
| --- |

若存在 rejected 证据且重试次数未耗尽，回到「证据采集」节点补一次针对性工具调用（如更精确的 grep），最多重试 1 次以控制成本。这一步是「用户可以验证 AI 判断依据」这句话真正成立的技术前提。

## 4.3　自适应自洽采样（Adaptive Self-Consistency）

多次独立采样、取多数一致结论作为置信度，是 Wang 等人（2022，Self-Consistency Improves Chain-of-Thought Reasoning）提出并被广泛验证的方法。考虑到 Token 预算有限，TDSF-Linux 只在证据本身不够扎实时才触发重采样，而不是每次都跑 3~5 遍：

| def adaptive_confidence(evidence_chain, threshold=0.7, n_samples=3):     base_conf = compute_confidence(evidence_chain)      # 见4.1公式     if base_conf >= threshold:         return base_conf, evidence_chain                # 单次推理直接采用，省Token     samples = [reason_once() for _ in range(n_samples)]     root_cause, agree_ratio = majority_vote(samples)     return agree_ratio, root_cause |
| --- |

绝大多数清晰场景（如 OOM、磁盘满）单次推理即可给出高置信度结论，只有证据模糊、模板匹配度低的情况才会触发 3 次重采样，在效果和成本之间做了明确取舍。

## 4.4　风险评分与人工确认门控

| risk_score = max(command_pattern_risk, environment_criticality_modifier)   command_pattern_risk         ：查静态规则表（YAML），分 低 / 中 / 高 environment_criticality_modifier：目标资产若标记为「关键」，风险等级至少上调一档                                  标签维护在 assets.yaml，demo 环境中人工设置   交互门控（LangGraph 的 conditional edge + interrupt）：   低风险   → 直接输出 + 一键执行   中/高风险 → interrupt()，暂停等待人工在 UI 中查看证据链后              选择「接受 / 拒绝 / 追问」 |
| --- |

选择 LangGraph 而不是手写状态机的关键原因是它把「暂停等待人工确认」做成了框架级的一等公民（interrupt / human-in-the-loop），不需要自己维护一套暂停-恢复的状态持久化逻辑，这部分工程量对 3 周工期的小团队是实打实的节省。

# 五、  Decision Library：检索增强的自我进化机制

每次诊断完成后（无论是否执行修复），系统将 {问题描述、证据链、根因、排除假设、修复命令、风险等级} 序列化为一张 Decision Card：结构化字段写入 SQLite 便于精确查询，「问题描述」做向量化后写入 ChromaDB 便于语义检索。

新故障进来时，「历史检索」节点先用当前日志的简要描述做向量检索，取 Top-3 相似历史 Decision Card。若相似度超过阈值，会作为推理先验注入「因果推理」节点的 Prompt——但必须明确注明「该历史案例仅供参考，你仍必须基于当前证据独立验证，不得直接照搬历史结论」，这是为了防止历史偏见污染新判断（例如同一台机器换了根因，却被历史案例带偏）。

这个设计让系统有一个真实、可演示的「越用越聪明」故事：处理过的故障越多，命中历史相似案例的概率越高，获得的先验信息质量也越高——但全程是可解释、可关闭、可审计的检索增强，不是黑箱的模型再训练，不需要 GPU 训练资源，符合预算限制。

# 六、  成本与工程简化设计

针对「AI 开发预算和时间有限」的现实约束，方案里的每一处设计都优先考虑用最少的工程量换取最多的可信度提升，具体的省钱/省时机制：

▪ 日志压缩：Drain3 把原始日志转成「模板 + 参数」，喂给 LLM 的是压缩后的模板摘要而非原始日志全文，大幅降低输入 Token；

▪ 上下文缓存：火山方舟提供 Context Cache 能力，把不变的 system prompt、工具定义、术语表做缓存，重复调用只需为变化部分的 Token 付费；

▪ 自适应采样：见 4.3，仅在置信度不足时才触发多次重采样，多数场景单次推理即可；

▪ 检索命中降级：Decision Library 命中高相似度历史案例时，可降级为「确认式」轻量推理，不必每次都从零展开完整因果链；

▪ 只读优先：诊断阶段的工具调用（grep / df / free / journalctl / ss）全部只读、无副作用，可以放心重复调用与重试，不必担心额外风险。

# 十、  附：评估但未采纳的技术方向（供团队内部参考）

团队内部曾讨论过引入知识图谱构建、因果超图神经网络、Granger 因果检验、Prompt 自动优化器等更「学术」的方向，这里记录清楚为什么最终没有采纳，避免团队成员在答辩时被问到相关问题时说法不一致：

▪ 知识图谱 + 因果超图神经网络：背后对应的研究工作（如 AetherLog, ISSRE 2025）是真实存在的高质量论文，思路有参考价值，但完整复现需要训练数据、评估基准和数周的调参验证，不是 3 周可信复现的规模。没有真实训练过程的神经网络模块等同于零信息量的装饰代码，一旦被评委追问「训练数据是什么、准确率怎么测的」会直接露怯，比不做还伤——因此本方案只保留了「检索增强」这个真正轻量可行的部分（见五节），去掉了需要训练的神经网络部分；

▪ Granger 因果检验：该方法适用于有足够重复观测的时间序列，直接套用在单次故障、样本极少的日志片段上统计上并不成立，容易被内行看出是「拿一个听起来很科学的词包装」，因此改用更朴实但可解释的证据溯源校验（4.2节）；

▪ 「EU AI Act Article 14 五级自主模型」：经核查，欧盟《人工智能法案》第14条本身只要求监督措施与风险、自主程度相称，并未定义任何「L2/L3」式的分级框架；用它包装人工确认机制是对法规的误用，且该法规本身也不适用于部署在境内校园的演示项目。本方案改为直接、诚实地描述为「基于风险分级的人工确认机制」（4.4节），不做不准确的合规性声称；

▪ Prompt 自动优化器（10 轮迭代）：需要一个可靠的历史案例评估集和大量额外 Token 开销才能生效，与「预算有限」的约束冲突，且优化效果难以在演示中直观证明，本方案改为人工迭代 Prompt，成本更可控。

总的原则是：宁可少做一个听起来炫的模块，也不做一个自己讲不清楚原理、经不起追问的模块——评委真正认可的「深度」，是每个设计选择背后都能讲出令人信服的原理，而不是术语的密度。

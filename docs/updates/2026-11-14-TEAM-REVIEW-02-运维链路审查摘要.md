## OPS-01 读取/解析异常被归为“未知主机”

- 相关路径与行号
  - `src-tauri/src/modules/ssh/known_hosts.rs:90-147`：`check()` 的返回值约定为 `Ok(true)` 已知且匹配、`Ok(false)` 未知、`Err(KeyMismatch)` 已知但不匹配、`Err(other)` 其他错误。
  - `known_hosts.rs:129-145`：除 `NotFound` 外的 `Err(e)` 记录 `warn`（注释自述“TOFU 防 MITM 保护降级，但仍不阻断连接”）后返回 `Ok(false)`。
  - `src-tauri/src/modules/ssh/handler.rs:212-235`：调用方把 `Ok(false)` 一律当作“未知主机”，`is_mismatch = false`，进入首次连接确认流程。
  - `known_hosts.rs:164-199`：`learn()` 先调 `forget_host_lines()` 清理该 `host:port` 旧行；清理失败（`Err(e)`）只告警并退回 `russh` 追加写入（`:194-197`）。
  - `known_hosts.rs:218-247`：`forget_host_lines()` 为读-过滤-整文件重写，只在该路径可写时执行。
- 已证明：读取/解析异常与“主机未知”共用同一返回值和同一 UI 分支，用户看到的是“未知主机，是否信任”，而不是“无法校验主机密钥”。这是异常分类上的 fail-open 边界，成立。
- 未普遍成立、已收窄：不能断言“确认后旧行必被删除并写入新键”。`forget_host_lines` 可能因同一读取/解析错误失败而退回追加；`russh` 的追加本身也可能失败（权限、磁盘、并发）。因此持久化结果至少存在“旧行被清 + 新键写入”“旧行保留 + 新键追加”“清理与追加均失败”等分支。
- 影响（仅限可证明部分）：已知主机可能被当作首次连接处理，用户可能在缺少“密钥变更”告警的情况下做出信任决定。旧记录是否被清除、文件是否出现重复/残留，取决于上述失败分支，需合成文件逐一验证。
- 状态：异常分类与 UI 分流源码可证明；清理/追加/持久化影响待验证。
- 建议（另行立项，由 ROOT 主导）
  1. `check()` 区分“未知”与“无法判定”，后者 fail-closed 或至少进入显式告警，不返回 `Ok(false)`。
  2. `learn()` 对“将覆盖已有记录”给出显式确认与审计记录。
  3. 补反例：损坏文件、权限拒绝、`forget` 失败、追加失败四类，分别断言返回值与文件内容，不把未复现结果写成必然。
- 未验证：真实服务器密钥变更；Windows 文件权限导致的读取失败；并发连接下的文件竞争。

## OPS-02 远端重命名/移动缺少同名冲突提示

- 相关路径与行号
  - `src-tauri/src/modules/fs/mutate.rs:42-44`：本地 `fs_rename` 在目标已存在时返回错误，并有 `rename_moves_and_never_overwrites` 测试。
  - `src-tauri/src/modules/fs_backend/sftp.rs:159-166`：`SftpFs::rename` 直接转调会话 `rename`，无目标存在检查。
  - `src-tauri/src/modules/ssh/sftp.rs:377-388`：`rename` 直接发 `SSH_FXP_RENAME`。
  - `src/modules/explorer/lib/useFileTree.ts:498-536`：`commitRename` 只判空与同名，未检查目标存在。
  - `useFileTree.ts:557-570`：`movePath` 仅在目标目录 `status === "loaded"` 时检查同名；未展开目录不检查。
- 协议与依赖事实（ROOT 复核）：当前锁定的 `russh-sftp 2.3.0` 在 `client rename` 调用中使用 rawsession 的普通 `Rename`，不是 `posix-rename` 扩展；SFTP v3 草案 §6.5（<https://www.ietf.org/archive/id/draft-ietf-secsh-filexfer-02.txt>）规定目标已存在应报错。
- 收窄后的结论：缺少前端前置检查不能证明“静默覆盖”；前置 `stat` 也不是原子防覆盖保证。当前可证明的是：远端路径没有同名冲突提示，与本地行为不一致；实际报错或覆盖取决于服务端实现与协商（例如 OpenSSH 对普通 `RENAME` 的处理），需要具体服务端与调用证据。
- 影响：用户可能在无提示的情况下遇到冲突失败或非规范覆盖；这是兼容性与 UX 风险，不作为“必然数据丢失”主张。
- 状态：前端缺少冲突提示源码可证明；覆盖结果待验证。
- 建议（另行立项）
  1. 前端在重命名/移动前查询目标并显式提示冲突，不依赖服务端语义。
  2. 若要原子不覆盖，需明确依赖 `posix-rename` 扩展或声明不支持；不在缺少证据时改协议假设。
  3. 测试用假 SFTP 覆盖“冲突提示”路径；服务端覆盖语义留到受控测试环境验证。
- 未验证：具体服务端（OpenSSH/第三方）的普通 `RENAME` 实际返回与覆盖行为；目录与文件互相覆盖的边界。

## OPS-04 同会话多标签 cwd 共享——待验证假设

- 可达链核查（ROOT 复核，已核对源码）
  - `src/app/App.tsx:1580-1600`：SSH 工作区的新标签走 `openSshShellForEnv(env)`，并为该标签创建独立会话/PTY。
  - `src/modules/spaces/lib/openSpaceShell.ts:26-44`：`openSshShellForEnv` 调 `connectWithSaved(profile, { origin: "tab" })`；`App.tsx:1591` 以返回的 `sessionId` 绑定新标签。
  - `src/modules/ssh-explorer/sshStore.ts:730-781`：`connectWithSaved` 每次调用创建新会话，Rust `ssh_connect` 分配新 id 与新 PTY（`openSpaceShell.ts:20` 注释）。
  - `src/modules/terminal/PaneTreeView.tsx:170-177`：OSC 7 只写会话级 `setCurrentPath(sessionId, cwd)`，leaf 的 cwd 槽位留给本地 shell。
- 修订后的结论：不能仅凭 `currentPathBySession` 以 `sessionId` 为键就判定“两个独立标签共享目录”。按现有入口，SSH 新标签各自创建独立会话；要证明共享，需要列出能让两个终端持有同一 `sessionId` 的真实创建/绑定入口（例如会话恢复、同一工作区首个标签与后续标签、异常回退的 `sessionId` 复用），并说明 OSC 来源与活动标签的消费方。
- 状态：待验证假设；未证明前不作为要求用户接受共享目录的产品决定。
- 若后续确认存在共享路径：属可用性设计权衡，建议在界面上标注“文件树跟随本会话最近目录”，或按活动标签映射 cwd。
- 未验证：同一 `sessionId` 的真实复用路径；恢复/重连后的绑定关系；OSC 7 来源与实际活动标签的一致性。

## OPS-05 低风险边界（分条）

- 5a legacy 技能执行日志：`src-tauri/sidecar/skills/registry.py:693-695` 在 legacy `invoke` 的执行 helper 中记录 `cmd` 与 `input` 前 80 字符。当前 RPC/Agent 已绕开该 helper，因此不能等同“当前技能 UI 已产生此日志”。若未来硬化，`full_cmd` 会包含插值后的完整 input，仅删除 80 字符预览不足；建议改为记录命令类别与长度，不记录输入原文。

# TDSF Agent 架构优化建议 · 开源借鉴（2026-09-03）

> 响应用户"调研开源 agent 架构（pi/qoder/其他 SDK）看如何优化"。基于 WebSearch 调研 + TDSF 现状对照，聚焦用户实测痛点：**超时稳定性** + **工具风险门控**。

|---|---|---|

## 二、长任务超时/稳定性的生产最佳实践（调研精华）

### 1. 分层超时体系（不要单一超时控制一切）
```
用户请求超时 (300s)
  └── Agent 循环超时 (240s)
        ├── 单次 LLM 调用超时 (60s，含重试)
        └── 单次工具调用超时 (30s)
```
每层独立，**内层 < 外层**，留缓冲做超时后清理。

### 2. ⚠️ 关键陷阱：单纯调大超时是反模式
> "Raising timeout thresholds turns a clean error into a silent one."（Augment Code）

客户端超时后 agent 仍在跑 → 客户端重试 → **两个 agent 实例执行同一任务** → 副作用（写库/发消息/执行命令）**重复触发**。这正是 TDSF 红线9（ssh_command 双重执行）担心的同类问题。

### 3. 活动感知心跳（而非总时长超时）
Cloudflare `keepAliveWhile()`：长任务用心跳**重置 inactivity timer**——有进展（token/工具事件）就不超时，真卡死（无活动）才超时。

### 4. Checkpoint 断点续跑 + 幂等键
- 长任务定期保存进度（working memory / active execution state / long-term memory 三类状态）
- 崩溃/超时从最后 checkpoint 恢复，不从头重跑
- **副作用操作加幂等键**（唯一 intent id），防恢复/重试重复执行
- 数据：chat-only 恢复仅 8-13% 正确率，semantics-aware checkpoint 达 100%（Crab 论文）

### 5. 任务状态机 + 熔断
`CREATED→PLANNED→EXECUTING→VERIFYING→SUCCEEDED`，状态机约束合法迁移；连续失败熔断转人工（可解释失败原因）。

## 三、TDSF 现状对照

| 维度 | TDSF 现状 | 差距 |
|---|---|---|
| LLM 调用超时 | DeepSeek API timeout=300s（model_adapter） | ✅ 有 |
| 工具调用超时 | SSH exec timeout=30s | ✅ 有 |
| Agent 无活动超时 | Python watchdog `_wait_with_watchdog` 600s（活动感知，有 token/工具重置） | ✅ 有（活动感知） |
| **前端 invoke 超时** | **总时长 300s（本次从 60s 调大）** | ⚠️ **总时长而非活动感知，与 Python watchdog 不一致** |
| 事件流真源 | agent_log/*.jsonl（append-only，10类事件） | ✅ 有（dsh 同款雏形） |
| Checkpoint 断点续跑 | ❌ 无（超时/崩溃=全丢，从头再来） | ❌ 缺 |
| 幂等键 | ❌ 无（工具调用无 intent id） | ❌ 缺（红线9 双重执行隐患同源） |
| 风险门控 | command_impact 命令级 risk 分级 + denylist + HITL 审批 | ✅ 有（本次修只读误判 L3） |
| Guardrails（输出审核） | ❌ 仅命令输入审核，无 LLM 输出审核 | ⚠️ 可补 |
| 熔断 | fix_loop（连续失败熔断）+ ToolCallLimitHook（50次） | ✅ 有 |
| tracing | agent_log 有工具事件，但无耗时统计 | ⚠️ 可补工具级耗时 |

**核心结论**：TDSF 已有分层超时雏形（LLM 300s / 工具 30s / watchdog 600s 活动感知）+ 事件流真源（agent_log）+ 熔断。**最大短板**：① 前端 invoke 是总时长超时（与 Python 活动感知 watchdog 不一致）② 无 checkpoint 断点续跑 ③ 无幂等键。

## 四、优化建议（分优先级）

### P0 · 前端 invoke 改"活动感知超时"（快速落地，直接提升稳定性）
**问题**：本次把前端 invoke 超时 60s→300s 缓解了，但仍是**总时长**超时。若 agent 任务 >300s 但一直有进展（token/工具事件流），仍会误超时；而 Python watchdog（600s 活动感知）还没触发 → 前后端超时语义不一致。

**方案**：前端 `runSidecarStream` 已监听事件流（`sidecar:agent_message` token / tool_call）。把 `Promise.race([invoke, setTimeout(300s)])` 改为**活动感知**：每收到一个事件就重置计时器（有进展不超时），只有 300s **无任何事件**（真卡死）才超时。与 Python watchdog 语义对齐。

**收益**：长任务只要有进展就不误超时；真卡死才失败。比单纯调大超时更稳、更省（避免"静默错误 + 重试重复执行"陷阱）。

**改动**：`sidecar-adapter.ts` 的超时逻辑（event 回调重置 timer），~20 行。风险低。

### P1 · 工具级 tracing 耗时（快速，定位慢工具）
借鉴 OpenAI Agents SDK tracing：agent_log 的 tool_call/tool_result 事件补 `duration_ms`，运行日志面板（B3）显示每个工具耗时 → 定位哪个工具/LLM 轮慢。改动小（agent_log 埋点 + B3 面板显示）。

### P2 · Checkpoint 断点续跑 + 幂等键（架构级，中等工程）
借鉴 LangGraph/dsh：
- agent 长任务每完成一个工具调用/LLM 轮，把状态写入 checkpoint（复用 agent_log 事件流）
- 超时/崩溃后从最后 checkpoint 恢复（不从头）
- 副作用工具（ssh_command 写/edit/write_file）加幂等键（intent id），恢复/重试时去重
- **同时根治红线9**（ssh_command 双重执行）：幂等键确保同一 intent 只执行一次

这是较大重构，但对"稳定性"是质变（生产级 durable execution）。建议决赛后作为专项。

### P3 · Guardrails 输出审核（可选）
借鉴 OpenAI Agents SDK Guardrails：除命令输入审核（command_impact），补 LLM 输出审核（如检测幻觉命令/敏感信息泄露）。教学场景可选。

## 五、推荐路线

1. **立即（本次）**：P0 前端活动感知超时（直接提升稳定性，低风险，~20行）+ 已修的只读误判 L3 + 超时 300s
2. **近期**：P1 工具级 tracing 耗时（配合 B3 运行日志面板，定位慢点）
3. **决赛后专项**：P2 checkpoint 断点续跑 + 幂等键（生产级 durable execution，根治红线9）
4. **可选**：P3 Guardrails 输出审核

**关于本次 300s 调参的再评价**：调大超时是"止血"（缓解误超时），但调研表明**活动感知超时（P0）才是治本**——建议 P0 落地后，300s 作为"无活动上限"兜底（而非总时长硬限），稳定性最优。

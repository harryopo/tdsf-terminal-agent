## 主题一：Agent 感知当前终端（上下文注入）

### 1.1 Shell Integration 生态：命令边界的"行业协议栈"

#### 1.1.1 历史渊源：FinalTerm → OSC 133 → 各家扩展

- **OSC 133（FinalTerm）** 是一切的现代源头。FinalTerm 终端（已停维护）最早定义了 4 个语义标记，被 iTerm2 采纳并扩展，如今已成为事实标准。字节形式（全部等价）：
  ```
  \x1b]133;A\x07   prompt 开始（PS1 渲染前）
  \x1b]133;B\x07   命令行开始（prompt 之后、用户输入之前）
  \x1b]133;C\x07   输出开始（回车后、stdout/stderr 前）
  \x1b]133;D[;exit]\x07  命令结束（可选 exit code 0-255，终端可据此红/绿标 decoration）
  ```
  实践中出现的子参数：`aid=<unique>`（Warp/kitty 用于区分并发 shell 会话）、`cl=m`（A 序列上，多行 prompt 提示）、`k=i / k=r / k=c / k=s`（主 prompt / 右侧 prompt / 续行 prompt / PS2）。
  - 来源：https://ansicode.eversources.app/en/sequence/osc-prompt-marks （含 14 个终端支持矩阵：iTerm2/kitty/WezTerm/Ghostty/tmux/screen=yes；Windows Terminal/GNOME Terminal/Konsole=partial；xterm/alacritty/ConPTY=no）
  - 语义化 Prompt 完整提案（Per Bothner，freedesktop.org）：还定义了 `133;L`（fresh-line）、`133;N`（可隐式结束上一个命令的 A 变体）、`133;P;k=i/r/c`（显式 prompt 分段）、`133;I`（行内输入结束）。https://gitlab.freedesktop.org/Per_Bothner/specifications/blob/master/proposals/semantic-prompts.md
- **协议无关要点**：协议是 opt-in 的——不认识的终端只是丢弃这些字节，**所以注入端应无条件发送**，不会破坏任何不认识 133 的下游。

#### 1.1.2 iTerm2：OSC 133 + OSC 1337 扩展族

- 在 133 基础上通过 `OSC 1337` 上报结构化元数据，全部是"键=值"风格，ST 结尾：
  ```
  OSC 1337 ; SetUserVar=<name>=<base64值> ST    ← shell → 终端上报任意自定义变量（最重要的通道）
  OSC 1337 ; CurrentDir=<dir> ST                 ← cwd
  OSC 1337 ; RemoteHost=<user>@<host> ST         ← 主机（SSH 场景关键）
  OSC 1337 ; ShellIntegrationVersion=<n>[;脚本] ST
  OSC 1337 ; ClearCapturedOutput ST
  ```
- FTCS 命令序列约束（官方文档）：若 `D` 之前没有 `A`/`C`，`D` 应被忽略——**解析器要做状态机**，不能只看单条序列。
  - 来源：https://iterm2.com/documentation-escape-codes.html
- 2026 年有人把 iTerm2 Shell Integration 整理成了正式 RFC 风格规范（含状态机、Ctrl-C 处理、tmux/screen 排除、`ITERM2_SQUELCH_MARK` 等），可直接当实现参考读：https://gist.github.com/tep/e3f3d384de40dbda932577c7da576ec3

#### 1.1.3 VS Code：OSC 633 超集（含"精确命令行文本"上报——我们最需要的）

VS Code 的 `OSC 633` 是 `OSC 133` 的严格超集，关键增量是 **E 序列（命令行原文）和 P 序列（属性 KV）**：

```
OSC 633 ; A ST                       prompt 开始
OSC 633 ; B ST                       prompt 结束 / 命令输入开始
OSC 633 ; C ST                       命令执行开始（pre-exec）
OSC 633 ; D [; <exitcode>] ST        命令结束 + 退出码
OSC 633 ; E ; <commandline> [; <nonce>] ST   ★ 显式上报"shell 实际解释的完整命令行"（可含转义）+ nonce 防错配
OSC 633 ; P ; <Property>=<Value> ST  属性上报（Cwd=... 即 OSC 7 等价物）
```
- E 序列的意义：终端不再需要从屏幕 buffer 反解用户输入（转义/换行/回显歧义全避开），**这就是"agent 感知输入回显"的标准答案**。nonce 用于把 E 和相邻的 C/D 绑定，防长命令乱序错配。
- 各 shell 的 hook 落点（VS Code shellIntegration 脚本实现，可直接抄结构）：
  | shell | 初始化 | 命令开始（preexec） | 命令结束（precmd） |
  |---|---|---|---|
  | bash | `PROMPT_COMMAND` | `trap DEBUG`（DEBUG trap 触发 preexec） | `PROMPT_COMMAND` |
  | zsh | `precmd` | `preexec` | `precmd` |
  | pwsh | `prompt` 函数 | `PSConsoleHostReadLine`（读入命令行文本，发 E 序列） | `prompt` |
  | fish | `fish_prompt` 事件 | `fish_preexec` | `fish_prompt` |
  - 来源：https://code.visualstudio.com/docs/terminal/shell-integration ；hook 对照表：https://curiousbox.ai/docs/prode/troubleshooting/shell-integration
- **pwsh 长命令乱码案例**（VS Code issue #281461）展示了 633;E 的实现位置：`PSConsoleHostReadLine` 内部先调原函数拿命令行文本再拼 633;E 返回——bash/zsh 侧同理：**命令行文本要从 readline/line editor 钩子拿，不能从屏幕猜**。https://github.com/Microsoft/vscode/issues/281461

#### 1.1.4 WezTerm / kitty：注入机制与 user vars

- **WezTerm**：`OSC 7`（cwd）+ `OSC 133`（分区）+ `OSC 1337` user vars。默认 shell 集成定义 `WEZTERM_PROG`（**正在执行的完整命令行**）、`WEZTERM_USER`、`WEZTERM_HOST`、`WEZTERM_IN_TMUX`，每次显示 prompt 前和执行命令前更新——"用 user var 携带运行时状态"是比解析屏幕更干净的通道。tmux 下需 `set -g allow-passthrough on`。https://wezterm.org/shell-integration.html
- **kitty**：注入机制按 shell 分路——zsh 改 `ZDOTDIR`、fish 前置 `XDG_DATA_DIRS`、bash 用 `--posix` + `ENV` 加载 `kitty.bash`；**bash 是唯一"没有健壮的代码注入通道"的 shell，只能写 .bashrc 末尾三行**（kovidgoyal 原话）。协议细节：PS2 前发 `133;A;k=s`、扩展参数 `redraw=0`（prompt 不随 resize 重绘）、`click_events=1`；kitty 的 zsh 脚本有状态机（`_ksi_state`），还会补发孤儿的 `133;D` 修复未闭合 C——**健壮实现必须处理"上次命令没等到 D 就来了新 A"的情况**。https://sw.kovidgoyal.net/kitty/shell-integration/ ；源码导读：https://deepwiki.com/kovidgoyal/kitty/8.4-shell-integration ；RFC 讨论（bash 需写 rc 的原因）：https://github.com/kovidgoyal/kitty/issues/3948

#### 1.1.5 fish 4.0：原生集成（零脚本）

- fish 4.0（2024-12 beta / 2025-02 正式，Rust 重写）**内置** OSC 133 prompt/output 标记 + 无条件 OSC 7 + OSC 0，不再需要任何集成脚本；后续版本还把**命令行文本直接随 133 B 序列一起发送**（`fish now sends the commandline along with the OSC 133 semantic prompt command start sequence`）——fish 用户天然获得"命令边界+命令文本"。
- 兜底开关：`set -Ua fish_features no-mark-prompt` 可关闭（为不解析 OSC 的烂终端准备）。
- 来源：https://fishshell.com/docs/4.0b1/relnotes.html 、https://fishshell.com/docs/4.0/relnotes.html 、https://github.com/ariasuni/fish-shell/blob/master/CHANGELOG.rst

**对项目的适配性**：我们本地已有 133 A/B/C/D 注入与 Rust 解析，向 **633 E（命令行文本）+ 633 P（cwd）** 扩展是最低成本高收益路径；SSH 远端注入脚本同样升级到 133 全套 + 633 E，即可让"本地终端"与"SSH 终端"共用同一套语义通道与解析器（单一代码路径）。fish 4.0 用户在远端天然发 133（我们的 Rust 解析器自动受益，无需注入）。

### 1.2 命令历史 + exit code 的精确捕获方案

#### 1.2.1 bash-preexec（zsh 式 preexec/precmd 在 bash 的标准实现）

- 机制（源码级）：bash 没有原生 preexec 钩子，bash-preexec 用两根支柱合成：
  1. **`trap ... DEBUG`**：每条简单命令执行前触发，读 `$BASH_COMMAND` 拿命令文本（这就是 bash 侧"输入回显"的可靠来源；但 DEBUG trap 对复合命令/函数会多次触发，bash-preexec 用状态机去重）；
  2. **`PROMPT_COMMAND` 前插 `__bp_precmd_invoke_cmd`**：prompt 显示前触发，此时 `$?` 是刚执行完命令的 exit code。
  - 提供 `preexec_functions+=` / `precmd_functions+=` 数组，多插件共存；会保护已有 DEBUG trap（包装成 `__bp_original_debug_trap` 再回放）；`extdebug` 开启时拒装。
  - iTerm2 的 bash 集成就是内嵌 bash-preexec 实现的（MIT，作者 Ryan Caloras，akinomyoga 长期维护，2026-04 仍在发版）。
  - 来源：https://github.com/rcaloras/bash-preexec ；iTerm2 内嵌版实况：https://github.com/kabel/dotfiles/blob/master/iterm2_shell_integration.bash
- 对我们的意义：SSH 注入脚本对 bash 用"DEBUG trap 捕获命令行 + PROMPT_COMMAND 发 133;D;$? 与 633;E"的组合，正是业界验证过的最稳做法；防复合命令重复触发直接内嵌/参考 bash-preexec 的去重逻辑。

#### 1.2.2 atuin（≈31k star）：历史条目的完整字段设计 + Agent Hooks

- **捕获层**：每个 shell 通过 `atuin init bash/zsh` 注入 preexec/precmd 钩子，记录：命令全文、cwd、开始时间、**时长**、**exit code**、session、hostname。
- **存储层**（SQLite `~/.local/share/atuin/history.db`，表结构实测）：
  ```sql
  CREATE TABLE history (
    id text primary key, timestamp integer not null,  -- UTC 纳秒
    duration integer not null, exit integer not null,
    command text not null, cwd text not null,
    session text not null, hostname text not null,
    deleted_at integer, author text, intent text, shell text,
    unique(timestamp, cwd, command));
  ```
- **Agent Hooks（2026 新功能，与我们场景高度同构）**：`atuin hook install claude-code/codex/opencode/pi` 后，AI agent 的 Bash 工具调用走 **PreToolUse（记录命令/cwd/时间戳=history start）/ PostToolUse（记录 exit code/duration=history end）** 双钩子，且每条记录带 `author=<agent名>` 标签，可与人类命令区分（`atuin search --author '$all-agent'`）。
- 隐私面：本地明文 SQLite、同步前端到端加密；命令可被用户篡改删除（取信度注意）。
- 来源：https://github.com/atuinsh/atuin/blob/main/docs/docs/guide/agent-hooks.md ；表结构取证：https://buaq.net/go-433682.html ；架构综述：https://dibi8.com/resources/dev-utils/atuin/ 、http://einverne.github.io/post/2023/06/atuin-sync-shell-history.html
- 对我们的意义：①历史条目字段集（command/cwd/duration/exit/session/author）就是我们 Agent 侧"命令历史上下文"的**标准 schema**，可直接采用；②"agent 执行的命令打上 author 标签进同一历史流"是很好的产品化思路（教学场景可回放"本轮 AI 都执行了什么"）。

### 1.3 SSH 远程端注入：最佳实践与防双重注入

- **iTerm2 三层策略**（官方文档）：
  1. *自动加载*：v3.5+ 对 `Command=SSH` 的 profile 自动装载集成脚本（终端侧注入，非远端配置）；
  2. *手动安装*：curl 下载 per-shell 脚本 source 到 rc 文件，**明确要求放在 rc 末尾**——"Put it at the end because other scripts may overwrite the settings it needs, such as PROMPT_COMMAND"（注入顺序红线）；
  3. *Triggers 兜底*：无法改远端 rc 时（root/一次性机器），用终端侧正则 trigger 从 prompt 字面提取 user/host/dir（Report User & Host / Report Directory / **Prompt Detected**，需开 Instant）——**"解析 prompt 正则"是语义注入不可用时的最后兜底，而非首选**。
  - 来源：https://iterm2.com/documentation-shell-integration.html
- **kitty ssh kitten**：`kitten ssh` 把 shell 集成自动带到远端（远端零配置），配合 `no-cwd/no-prompt-mark` 等可关子项；容器内用 `kitten run-shell` 兜底。证明"连接时由客户端把集成脚本送进会话"是成熟模式。https://sw.kovidgoyal.net/kitty/shell-integration/
- **防双重注入 / 环境兼容检查**（iTerm2 bash 脚本实测写法，可直接抄）：
  - 幂等 guard：`[[ "$ITERM_SHELL_INTEGRATION_INSTALLED" = "" ]]` 再装，装完立即置位；
  - 交互式检查：`[[ "$-" == *i* ]]`；排除 `TERM=linux/dumb`；tmux/screen 下默认关闭（`TERM=screen*` 检查）；
  - 保留既有钩子：bash 用 `PROMPT_COMMAND+='__xxx_prompt_command'` 追加而非覆盖；zsh 用 `precmd_functions+=(__xxx_precmd)`；prepend 既有 PROMPT_COMMAND 的方向（先发 D;$? 再跑用户原有逻辑）是另一个可行序（Taviraq epic 采用 prepend 保序：`PROMPT_COMMAND (prepend, preserve existing): emit 133;D;$?, 633;P;Cwd, prompt start`）。
  - 来源：https://github.com/kabel/dotfiles/blob/master/iterm2_shell_integration.bash ；https://github.com/Doka-NT/Taviraq/issues/183
- **同类产品怎么"感知 SSH 会话上下文"**：
  - **Chaterm**（开源 AI 运维终端，与我们定位最像）：AI Sidebar（Ctrl/Cmd+L）打开时**自动捕获当前终端上下文** = "output history + scrollback + 当前工作目录 + session 环境"，一次性喂给模型做多轮排障；移动端 Term/Chat 双模式**共享同一 session 上下文**（Term 里跑的 `journalctl -n 50`，切 Chat 直接问"上面的报错什么意思"，无需复制粘贴）；Command/Agent 模式执行前默认逐命令审批（approval mode）+ Explain 面板。未开源的部分（注入细节）不可考，但其"session 级上下文共享 + 审批"交互范式值得直接借鉴。https://chaterm.ai/docs/terminal/chattoai/ 、https://chaterm.ai/docs/mobile/ai-agent/
  - **Warp**：Agent 读"current directory、recent commands、last command's stdout/stderr、env(filtered)"，用户可把任意历史 block 附件化（Blocks as Context，CMD+UP 附加/CMD+DOWN 移除）；上下文超限报错并引导开新会话（GPT-4o 上限 123,904 token/请求）。Warp 对 SSH 场景的短板（agent 本地执行、驱动远端 shell 弱）也被用户实评点名——这正是我们"SSH 原生"的差异化空间。https://docs.warp.dev/features/warp-ai/agent-mode 、https://docs.warp.dev/agents/using-agents/agent-context/blocks-as-context 、https://www.openaitoolshub.org/en/blog/warp-ai-agent-real-week
  - **auto-copilot-cli / Copilot CLI / Terminal Chat**：命令补全类上下文=当前输入片段+cwd+git 状态+最近几条历史+OS/环境信息；Windows Terminal 的 Terminal Chat 极端保守——只随请求附上"active shell 名称 + 对话历史"，**不**主动送命令输出/文件，防过度采集。上下文预算优先级：显式引用 > 光标附近 > 当前文件 > 自定义指令 > 打开的 tab > 关联文件。https://www.itechguides.com/microsoft-brings-chatgpt-ai-to-windows-11s-command-line-what-terminal-chat-really-does/ 、https://github.com/vib795/copilot-howto/blob/main/copilot_concepts_guide.md
- **解析侧架构范式**（Taviraq epic，2026-06，与我们同为 xterm.js + AI 终端）：把"启发式猜 prompt/block"全面替换为 OSC 133/633 语义标记 + **`terminal.parser.registerOscHandler(133/633)` + `terminal.registerMarker(0)`（IMarker）作为唯一坐标系**（resize/reflow/scrollback 裁剪时 xterm 自动重定基），所有消费者（高亮、复制、Ask AI、重跑）读同一 marker 区间；明确结论：**xterm.js 生态没有现成的 OSC-133 block addon，VS Code 也是自己 registerOscHandler + registerMarker 实现的**。曾经的血泪：启发式 prompt 正则 + 字节偏移 + 逻辑行三坐标系互相打架，"copy 给 LLM 的 block 里混进了隐藏 prompt"。https://github.com/Doka-NT/Taviraq/issues/183

**对项目的适配性**：①我们的 scrollback 尾部 30 行 = 最粗糙的"输出上下文"，升级方向明确：**本地 + SSH 统一注入 133 全套 + 633 E/P，Rust 解析进 block 流水账（command/cwd/exit/duration/author），Agent 上下文从"尾部 30 行"升级为"最近 N 个 block"**；②SSH 注入沿用方案 A（会话建立时静默注入），但按 iTerm2/VS Code 的成熟写法补齐：幂等 guard、交互式/TERM 检查、PROMPT_COMMAND 追加保序、DEBUG trap 去重、孤儿 D 状态机；③"环境感知"用 wezterm/kitty 式 user-var/1337 SetUserVar 思路按需扩展（如 `SSH_CONNECTION`、`$SHELL`、发行版），避免往 prompt 里塞内容（用户钦定红线：禁止改写用户 prompt）。

## 主题二：Agent 命令执行的可视化教学演示（打字机效果）

### 2.1 asciinema / asciicast v2：时间轴重放参考

- **格式**：newline-delimited JSON。首行 header（version/width/height/…可选 `idle_time_limit`/`command`/`env`/`theme`），其后每行一个事件：`[<float 秒>, "<code>", "<data>"]`。事件码：`o`=写到终端的输出、`i`=用户键入（需 `rec --stdin`，默认关闭）、`m`=marker、`r`=resize。增量写盘（断电不丢）、天然流式（命名管道/netcat 实时直播）。
  - 来源：https://docs.asciinema.org/manual/asciicast/v2/ ；2.0 发布文：https://blog.asciinema.org/post/two-point-o/
- **调速语义**：`idle_time_limit`（录制期=cap 空闲段；回放期=player 把所有帧间隔压到 ≤ 该值）——**"时间轴上做速度缩放/空闲压缩"的标准做法**；play 还有暂停（space）与逐帧步进（`.`）用于演示。
- **回放器生态**：asciinema 3.0 已全 Rust 重写；`castsvg`（Rust，`portable-pty` + `vte` + `crossterm`）把 cast 渲染成自包含动画 SVG，其 render 参数即调速范式：`--min-frame-ms 40`（合并输出突发）、`--idle-cap-ms 1000`（长停顿钳制）、`--end-pause-ms 1500`。https://docs.rs/crate/castsvg/0.1.0
- **对项目的适配性**：我们的打字机是**交互式实时注入**而非录制回放，asciicast 不直接可用；但其两个思想值得吸收：①"事件时间轴 + 空闲上限"抽象——若未来做"教学回放"（把 agent 一次任务录成 cast 供学生重看/调速），asciicast v2 是现成格式（xterm.js 有第三方 asciinema-player 可播）；②`i` 事件（键入流）证明"把输入也当成时间轴事件记录"是行业通行做法。

### 2.2 gsc（guided shell scripts）——与需求几乎同构的教学演示工具

- **机制**（README + 演化史）：创建 PTY，把脚本逐行喂给它"仿佛用户亲手敲"：
  - **逐字符发送**（one character at a time）→ 整行发完后**等用户按 Enter 才发送回车**（防止提前执行，讲完再跑）——与我们要的"教学演示 + 人控节奏"完全一致；
  - 三模式：Insert（按任意键逐字取脚本字符，想多快就多快）/ Command（Esc 进入，q 退出）/ **Pass-through（'p' 把键盘直通给真 shell，Ctrl-D 退回）**——"演示中临时接管手动操作"的交互范式；
  - auto 无人值守模式：`--auto-pause 100`（每次按键间隔 ms）用于录制/测试；
  - **血泪经验（原文）**：早期版本"每字符固定暂停"，实测**"等间隔打字完全不自然"**，于是改成**随机时长暂停（用户可调 min/max）**，最终版本干脆改成按键驱动。→ 直接结论：打字机必须带随机抖动 + 每字符延迟可配。
  - 其余特性：`%var%` 模板替换（`mkdir %semester%-%year%`）、setup/cleanup 脚本、monitor 端口；能驱动 vim/gnuplot 等任意全屏程序（因为打的是真 PTY）。
  - 来源：https://github.com/CD3/gsc （Python 续作：https://github.com/CD3/pygsc ）
- **对项目的适配性**：gsc 证明了"逐字写 PTY 做教学演示"可行且体验良好；它的**Enter 门控**（字符打完不自动回车）和 **pass-through 接管**建议进入我们的交互设计；**随机抖动**是硬要求。

### 2.3 ★ expect `send -h`（send_human）/ `send -s`（send_slow）算法详述（实现打字机的最直接参考）

> 以下全部取自 expect 官方源码 `exp_command.c`（Debian 打包仓库原文件），代码级确认，非文档转述。
> 来源：https://salsa.debian.org/tcltk-team/expect/-/raw/master/exp_command.c ；参数语义旁证：pexpect issue #714（`set send_human {.1 .3 1 .05 2}; send -h "..."` / `set send_slow {10 .1}; send -s "..."`）https://github.com/pexpect/pexpect/issues/714 ；用法实例：https://www.wiki.ciscolinux.co.uk/index.php?title=Linux_TCL_Expect&oldid=5756

#### send_slow（定速分块）——`slow_write()` 实现

```c
struct slow_arg { int size; double time; };   // send_slow = {size, time} 两元组，如 {10 .1}
// 校验：size>0，time>0
static int slow_write(...) {
    while (rembytes > 0) {
        charlen = min(arg->size, rembytes);        // 每次取 size 个 UTF-8 字符
        ... 按 UTF8 字符边界取字节 ...
        expWriteChars(esPtr, buffer, bytelen);      // 写这一块
        if (rembytes > 0)                           // ★ 最后一块后不再 sleep
            exp_dsleep(interp, arg->time);          // 块间固定延迟 time 秒
    }
}
```
- 语义：**每 N 个字符为一块，块间固定 sleep time 秒，末块不睡**。用途：慢速/丢失输入的设备（老串口、网络终端）——"like turning on flow control"。force_conservative 模式即 `send_slow {1 .1}`（每 0.1s 一字符）。

#### send_human（人味打字）——`human_write()` 实现，Weibull 分布逆变换采样

```c
struct human_arg {
    float alpha;      // 平均字符间隔（秒）
    float alpha_eow;  // 词尾转换时的平均间隔（end-of-word）
    float c;          // 形状参数（variability；代码内取倒数：x->c = 1/x->c）
    float min, max;   // 单次延迟下/上限（秒）
};                    // send_human = {alpha alpha_eow c min max} 五元组，如 {.1 .3 1 .05 2}

/* Don Libes 注释：这是我的 Weibull 分布实现。加了 max 截断，
   以及捕捉打字员在"词尾转换"时轻微但可察觉的迟疑的 alpha_eow。 */
for (sp = buffer; *sp; sp += size) {
    size = UtfToUniChar(sp, &ch);                       // 逐 UTF-8 字符
    if (in_word && (IsPunct(ch) || IsSpace(ch)))        // ★ 从"词内"跨到"标点/空格"
        alpha = arg->alpha_eow;                          //   → 用词尾平均间隔（更大，模拟词尾停顿）
    else alpha = arg->alpha;
    in_word = !(IsPunct(ch) || IsSpace(ch));

    t = alpha * pow(-log(unit_random()), arg->c);       // ★★ 核心采样公式（Weibull 逆变换）
    if (t < arg->min) t = arg->min;                     // min/max 截断
    else if (t > arg->max) t = arg->max;
    if (sp != buffer) exp_dsleep(interp, t);            // ★ 首字符前不延迟
    expWriteChars(esPtr, sp, size);                     // 每次写一个字符
}
```
- **算法本质**：`U ~ Uniform(0,1)`，`t = alpha·(-ln U)^(1/c)` 服从 **Weibull(scale=alpha, shape=c)**（代码先把用户传入的 c 取倒数，`c=1` 时退化为指数分布，即"泊松到达"的纯随机打字）。对比 `{.1 .3 1 .05 2}`：快打平均 0.1s、词尾平均 0.3s、形状 1（指数随机）、最短 0.05s、最长 2s——文档评价该组参数"emulates fast and consistent typist"。
- **设计精髓四条**（我们要照搬的）：
  1. 延迟是**随机分布**而非等间隔（Weibull 的 shape>1 可产生"burst+pause"的人味节奏）；
  2. **词尾（空格/标点转换处）用更长的平均延迟**——人打完一个词会自然迟疑，这是"像人"的关键细节；
  3. min/max 截断防极端值（min 保证不快到假、max 保证卡壳不至于停太久）；
  4. **首字符零延迟**（立刻开始，别让用户等）。
- 随机源：`unit_random()` = `(1 + rand()%99991)/99991`（0-1 均匀），我们 Rust 侧用 `rand` crate 即可。
- **对项目的适配性**：直接移植成 Rust `human_type(ws: &mut SshChannel/PTY, cmd: &str, cfg: TypingCfg)`：`TypingCfg { alpha, alpha_eow, shape, min, max, alpha_scale }`；用户"速度滑杆"映射 `alpha_scale`（0.2×~5× 缩放 alpha/alpha_eow/min/max），"逐字/整段开关"切换 `human_write` 与单次 `write_all`。

### 2.6 xterm.js 生态：无现成 typing effect；write 背压要点

- **没有可用的"xterm.js typing effect 库"**：市面打字机库（TypeIt、typed.js、Console Typer、TypeWriting.js、TypeMorph 等）全部是 **DOM 文本动画**库，操作的是 HTML 元素，与 xterm.js 的 buffer/PTY 管线无关。→ 结论：**打字机必须在数据层（写入 PTY/channel 的节奏）实现，而不是渲染层伪造**。这也与"用户看到的是真实回显"的要求一致。（库清单佐证：https://www.cssscript.com/best-text-animation-libraries/ 、https://www.cssscript.com/terminal-typing-effect/ ）
- **xterm.js write 流控**（官方指南）：
  - `write()` 非阻塞：数据进内部 WriteBuffer，按事件循环分片处理（单帧预算 ~16ms），总吞吐仅 5–35 MB/s；缓冲上限 50MB，**超出直接丢弃**；
  - 背压标准姿势：`term.write(chunk, cb)` 回调 + 上下游 pause/resume；进阶用**高低水位线**（HIGH ≤ 500KB 保键盘手感）+ 回调按字节数降频；
  - 同类 Tauri 项目（codemux）的教训：只节流消费者不通知生产者 = ring buffer 无限增长/静默丢数据，需要 producer 侧 pause/resume 命令 + 迟滞水位（HIGH 16MiB / LOW 4MiB），且必须保证 detach/close 时自愈 resume。
  - 来源：https://xtermjs.org/docs/guides/flowcontrol/ ；https://github.com/Zeus-Deus/codemux/issues/73
- **对项目的适配性**：我们若走"逐字写 PTY（低速）"，前端 xterm 只是正常接收远端 echo，**不触发背压问题**；若未来做"本地视觉打字机"（前端伪造），才需要 write 回调串行 + 水位线。

### 2.7 风险调研：向交互式 shell PTY 逐字注入命令的坑

结合 expect/gsc/共享终端方案与 shell 行为，风险全景与对策：

| # | 风险 | 机理 | 对策（已被业界验证） |
|---|---|---|---|
| 1 | **残留行内容拼接** | 用户当前输入行非空时逐字追加 → 命令被污染 | 注入前先发 `Ctrl-C`（新 prompt，安全可靠，exit 130）或 `Ctrl-U` 清行；gsc 用"等用户确认再回车"同源思想 |
| 2 | **history expansion（`!`）** | 交互式 bash 的 `!string` 在逐字输入时真实触发（`exec_command` 不触发，交互注入会触发） | 教学命令含 `!` 时单引号包裹或 `set +H`；或注入前检测 `!` 前缀告警 |
| 3 | **Tab 补全/菜单被误触发** | 只有显式 `\t` 才触发 readline 补全 | 只发可打印字符 + 末尾 `\r`，永远不发 `\t`；fzf/atuin 只在 Ctrl-R 特定序列激活，我们不含控制字符即安全 |
| 4 | **bracketed paste 误解** | 若把多字符包进 `\x1b[200~…\x1b[201~` 会被 shell 当粘贴（zsh 会把其中 `\r` 当字面量！） | 逐字注入**不要**包裹 paste 标记；整段模式注意用户 shell 若有 bracketed-paste，`\r` 语义变化 → 整段模式也应发裸字节（现行 visible 模式即如此） |
| 5 | **远端 echo 关闭**（`stty -echo`/`read -s`/sudo 密码） | 打字机"隐形"，视觉教学失效 | 打字模式只在检测到 prompt（我们自有 OSC 133 A 标记）后开始；密码类命令禁用打字机 |
| 6 | **用户中途敲键竞争** | agent 打字与用户输入交错 → 混乱 | gsc pass-through 思路：打字期间用户按键 = 中断演示（停 pump）；或 UI 层提示"演示中"状态条 |
| 7 | **SSH channel 背压** | russh channel 有窗口/流量控制，整段大写入可能 EAGAIN | 逐字低速模式天然无压力；整段模式沿用现有写入路径的背压处理 |
| 8 | **孤儿子命令/未闭合状态** | 上条命令未结束（无 133;D）又注入新命令 | agent 执行器等待 D 标记（或 prompt 空闲超时）再开始下一条；kitty 的"补发 D"修复逻辑可参考 |
| 9 | **控制字符时序** | 逐字写入时延迟插在字节间，readline 按键超时类行为（如 multibyte 序列拆分） | 延迟只插在**完整 UTF-8 字符**之间（expect 按 UniChar 逐个写即此意），多字节字符一次写完 |

- **共享/广播终端的同步参考**（涉及"学生围观 agent 打字"场景）：
  - **ttyd Shared PTY 模式（-Q）**：新客户端加入 → 服务端发 `SNAPSHOT`（每行含 ANSI 的全屏内容 + cursor_x/y）→ 客户端 `SNAPSHOT_ACK` 后才开始收输出流（防乱序）→ `SESSION_RESIZE` 由服务端统一尺寸、客户端禁用 FitAddon、RESIZE 消息被忽略；输出广播到所有 viewer，输入任一 viewer 可写。https://github.com/eastlondoner/ttyd/blob/main/SHARED_PTY_PROTOCOL.md
  - **Rust 生态 term-session-server**：网关进程广播 PTY 输出给多订阅者、接受任一客户端按键、**PTY 几何取所有客户端最小尺寸**、流式不预缓冲、输入 FIFO 保序。https://docs.rs/term-session-server/0.10.4-alpha/term_session_server/
  - **tmux + ttyd 双轨**：AI 经 SSH 在 tmux 会话里 `send-keys` 执行，用户浏览器实时围观——"AI 执行 + 用户观察"的零改造方案。https://blog.csdn.net/weixin_46801290/article/details/161524771
  - 多 viewer 反模式教训：单连接 kick 互踢造成重连风暴；正确做法是 viewers Set 广播 + 只读 follower + 环形缓冲供中途加入者 catch up（如 100KB ring buffer）。
- **小众相关项目清单**：gsc/pygsc（教学演示逐字喂 PTY）、castsvg（Rust asciicast→动画）、term-session-server（Rust 共享终端网关）、atuin agent hooks（agent 命令入历史流）、ttyd -Q（共享 PTY 协议）、Taviraq #183（xterm.js OSC 语义 block 架构 epic）。

## 可行性结论

### 结论一：Agent 感知终端（主题一）——**完全可行，且是行业收敛中的标准做法**

- 技术路线（OSC 133 全套 + 633 E/P + user-var 类通道）在 iTerm2/VS Code/kitty/WezTerm/fish/Warp/atuin/Chaterm 中已被反复验证；xterm.js 侧有 VS Code 同款实现范式（registerOscHandler + registerMarker），无需新协议发明。
- 我们项目的特殊优势：已有本地 133 解析 + SSH 方案 A 注入地基，本次升级是"补全序列 + 统一解析 + 上下文结构化"，属增量改造，无破坏性变更；且符合方案 A 红线（远端行为交给远端注入脚本，前端不做命令改写）。
- 主要工作量：注入脚本健壮性（防双重注入/多 shell 兼容）+ Rust 解析状态机（孤儿 D、续行 prompt k=s）+ block 流水账与 IPC。

### 结论二：打字机逐字注入交互式 shell——**安全可靠，业界 30 年成熟实践，但必须遵守注意事项清单**

- 可行性依据：expect 的 `send -h` 是 1990 年代起 30 年的 PTY 逐字注入标准实现（Weibull 算法至今未变）；gsc 是教学场景专用同类工具（作者用于大学课程实况演示多年）；SSH 终端里逐字写入 = 等价于"一个非常慢的打字员"，远端 readline/shell 完全按真实用户输入处理，回显天然逐字出现——**这正是教学演示需要的"真"**。
- 它与我们现行 visible 整段注入的关系：整段 = `send`，逐字 = `send -h`，两者是同一通道的两种节奏，开关实现成本低；整段模式必须保留（长命令/专家模式/低延迟场景）。
- **注意事项清单（硬性）**：
  1. 打字前必须清行（Ctrl-C 或 Ctrl-U）并等待 prompt（OSC 133 A / 空闲信号）；
  2. 只发可打印字符 + `\r`；禁止 `\t`、禁止 bracketed-paste 包裹；多字节字符整块写、延迟只插字符间；
  3. 随机延迟（Weibull + min/max 截断 + 词尾 alpha_eow），禁止等间隔；首字符零延迟；
  4. 含 `!` 的命令需转义/告警（交互式 history expansion）；密码/sudo 提示场景禁用打字机（echo 关闭，视觉无效）；
  5. 打字期间用户按键策略必须明确（建议：任意用户输入 → 停止 pump，交给用户）；提供"确认后回车"教学开关；
  6. 等待上条命令 OSC 133;D 后再注入下条（防孤儿命令）；
  7. 整段模式注意 SSH channel 背压（russh 窗口），逐字模式无此问题；
  8. 逐字模式总时长 = Σ延迟，默认参数下 ~80 字符命令约 10-15s，速度滑杆需覆盖 0.2×~5×，超长命令自动建议整段。

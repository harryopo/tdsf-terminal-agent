# 教学模式工具调用终端化 + 步步确认 · 方案（2026-09-04）

> 本文档整理用户 2026-09-04 的思考，供交接与持续实施。**截至 2026-09-04，四个阶段的代码链路与定向自动化测试已落地；真实桌面 + SSH 验收仍待完成。**
>
> 实施边界：教学工具调用只生成命令卡，**不代表命令已执行**。学生点击后，系统仅关联同一终端、同一命令、点击后开始的那个脱敏终端块；学生再点击「基于结果继续讲解」，才会把结构化结果作为一条新的用户消息交给 Agent。
> 核心：教学模式下所有"终端可执行类"工具调用改为**终端打字机可见执行 + 步步确认**；其他三模式（观察/确认/自动）**保持现状不变**。

---

## 摘要（一句话）

教学模式是"教学演示"，学生应看到 **AI 在替我操作终端的全过程**（每条命令打字机打进终端 + 我确认后才执行 + 看到预测回显）；而不是现在的"后端静默执行 + 甩一个 JSON 卡片"。观察/确认/自动三个模式是"高效运维"，保持现有工具调用方式不变。

## 二、现状调研（诚实澄清）

### 2.1 影响预测：**真算，不是假前端**（但呈现有问题）

**诚实回答用户疑问**：影响预测**不是假前端**，是后端真实计算：

- `src-tauri/sidecar/strands_backend/tools/command_impact.py` 的 `analyze(cmd)`：
  1. `split_compound` 按 `;`/`&&`/`||`/`|` 拆分复合命令（引号内不拆）
  2. `classify_segment` 每段分类 → `{category, category_label, objects, risk_l}`
  3. `match_denylist` 硬底线（rm -rf / / mkfs / dd of=/dev/ / reboot 等）→ L4 denied
  4. `detect_dangerous_construct`（`$()`/反引号/`>系统目录`/`| sh`/eval）→ 抬到 L3
  5. `max_risk_l` = 各段最高风险
- 前端 `tool.tsx` 的 `ToolApprovalCard`（L200-252）**只渲染后端返回的真实 segments**（category_label/objects/risk_l/denied/dangerous），无任何前端伪造。

**"未知操作/只读查询"是什么**：
- `只读查询` = `CATEGORY_READONLY`（cat/ls/grep/uname 等只读命令，risk_l=0）
- `未知操作` = `CATEGORY_UNKNOWN`（不在任何白名单的命令，fail-closed 保守判 risk_l=3）
- 截图2 命令 `chmod +x x.sh && x.sh && echo ... & cat .../health_$(date +%F).log`：chmod→"变更用户/权限"、`$(date)`→危险构造 L3、cat→"只读查询"、`& ` 后台段→"未知操作"。**都是真算的**。

**用户觉得"假"的真实原因**（呈现问题，非数据假）：
1. 术语不友好："未知操作""只读查询"是内部分类名，学生看不懂
2. 排版堆砌：多段 `category_label：objects` 平铺（L224-247），乱
3. "未知操作"其实是 fail-closed 保守（宁可判高），但显示成"未知"让人以为系统不懂

### 2.2 教学模式现状（**与用户诉求相反**）

`src-tauri/sidecar/strands_backend/adapter.py` L862-867：
```
教学模式严禁调用 suggest_command 工具（教学卡片不渲染该工具的命令预测 UI）；
Teach 契约由教学卡片承载，用户可从教学卡片一键复制/插入终端。
```
- 教学模式 = `observe` 权限（只读）+ `teach=true`（教学皮肤 6 板块输出）
- 只读工具（network_diagnose/inspect_processes/ssh_command readonly/analyze_logs）**后端 execute_via_ssh 静默执行** + 前端 JSON 卡片
- observe 免审批 → **不确认、不终端打字机**
- 禁 suggest_command → **没有"命令+预测回显+执行"卡片**

**这就是用户看到"教学模式直接执行没让我确认"的根因。**

### 2.3 工具调用渲染现状

`tool.tsx` `renderToolOutput`：
- **专门卡片**（友好）：read_file/list_directory/bash_run/knowledge_search/knowledge_get_doc/suggest_command/grep
- **默认 JSON**（用户看不懂）：network_diagnose/ssh_command/inspect_processes/config_diff/analyze_logs/performance_analyze 等运维工具 → 裸 `{Input JSON}{Output JSON}`（截图1"网络"卡片）

### 2.4 打字机局限

- 只有 `SuggestCommandCard`（suggest_command）+ `CommandCard`（bash 代码块）走 `injectIntoActivePty` → human_type 打字机
- 其他工具（network_diagnose/ssh_command 等）后端执行，**命令不进终端、学生看不到**

## 三、核心方案：教学模式工具终端化

### 3.1 设计原则

| 模式 | 定位 | 工具调用方式 |
|---|---|---|
| **教学** | 教学演示（学生看 AI 操作全过程） | **终端打字机可见 + 步步确认** |
| 观察/确认/自动 | 高效运维 | 后端执行 + 卡片/JSON（**现状不变**） |

### 3.2 工具分类（关键前提）

**终端可执行类**（教学模式终端化——本质是 shell 命令）：
- `ssh_command`（本就是命令）、`network_diagnose`（→ ss/netstat/ping）、`inspect_processes`（→ ps/top）、`analyze_logs`（→ cat/grep 日志）、`read_remote_file`（→ cat）、`config_diff`（→ diff）、`performance_analyze`（→ top/vmstat）、`get_terminal_output`

**非终端类**（保留卡片，无法/不该终端化）：
- `knowledge_search`（RAG 向量检索，非 shell）、`skill_invoke`（技能编排）、`assess_confidence`（置信度计算）、`todo_write`（规划）、`save_skill`

### 3.3 教学模式新流程（终端可执行类工具）

```
1. agent 决定调 network_diagnose（教学模式）
2. 工具 → 等价 shell 命令（network_diagnose{mode:ss} → "ss -tulnp"）
3. 教学模式：不后端执行，改发【教学命令卡】到前端：
   [命令: ss -tulnp] + [预测回显: 监听端口列表] + [解释: 查看网络监听] + [执行按钮]
4. 学生看到命令 + 预测回显 → 点"执行"（步步确认）
5. 打字机注入终端 → 执行 → scrollback 回读结果 → 返回 agent
6. agent 基于终端真实输出继续教学讲解
```

### 3.4 影响预测优化（用户诉求5）

1. **术语友好化**（category_label）：
   - "未知操作" → "未识别命令（保守待确认）"
   - "只读查询" → "只读查看"
   - "变更用户/权限" → "改权限"
2. **排版分组**：segments 按风险分组（🔴写操作 / 🟢只读 / ⚪未识别），而非平铺堆砌
3. **教学模式简化**：教学场景多为只读探查，弱化风险术语，突出"这条命令做什么"

## 五、实施步骤（分阶段，从低风险到高风险）

### 阶段1：影响预测优化（低风险，快速见效，可先做）
- `command_impact.py` `CATEGORY_LABELS` 术语友好化

- 文件：`command_impact.py` / `tool.tsx`
- 门禁：command_impact py 测试 + tool.test

### 阶段2：工具 → 等价命令映射（中风险）
- 每个终端可执行工具产出"等价 shell 命令"（network_diagnose{mode:ss,port:0} → `ss -tulnp`）
- 方案A：工具定义加 `to_shell_command(params)` 方法
- 方案B：工具 result 附带 `equivalent_command` 字段
- 文件：`strands_backend/tools/network_diagnose.py` 等各工具

### 阶段3：教学模式终端执行链路（高风险，红线9 相关）
- 教学模式工具调用 → 前端【教学命令卡】（命令+预测回显+确认）
- 打字机注入终端（human_type）+ **scrollback 回读结果** → 返回 agent
- **这是 B4（安全可见执行）的教学模式特化 + 扩展到所有终端工具**
- 依赖：`ipc/terminal.rs` inject_terminal 回读 + `term/osc133.rs` + `term/scrollback.rs`
- 前置：见 `docs/B4-B5-安全可见执行与服务器实测清单.md`

### 阶段4：教学模式 system prompt 调整
- `adapter.py` L862-867 解禁/改造 suggest_command（或新"教学命令卡"机制）
- 引导 agent 教学模式对终端可执行工具走"命令卡确认"而非后端执行

**不可回退的安全契约**：不自动恢复原工具调用；不由 Agent 自动读取滚屏；不以 `author` 或短 TTL 猜测人工输入；不让两张卡争抢同一终端 leaf；任何未关联、过期或不确定的输出都不能发送给 Agent。

## 七、风险与前置条件

1. **红线9（安全可见执行）**：终端打字机 + scrollback 回读替代后端 execute，回读可靠性（OSC133 标记 / SSH 网络延迟 / prompt 再现判定）是核心难点。
2. **必须真实 SSH 服务器实测**：沙箱无法验证终端执行回读（用户明确"测试主放在服务器里"）。
3. **工具→命令映射准确性**：network_diagnose 的参数（mode/port/target）→ 正确 ss 命令，映射错误会执行错命令。
4. **非终端工具不强行终端化**：knowledge_search（RAG）/skill_invoke 保留卡片。
5. **教学模式性能**：每条命令确认+打字机比后端执行慢——但教学价值优先（这是教学模式的目的）。
6. **回读结果 vs 结构化 result**：后端 execute 返回结构化 `{status,summary}`，终端回读是文本——agent 消费需适配（或回读后再解析）。

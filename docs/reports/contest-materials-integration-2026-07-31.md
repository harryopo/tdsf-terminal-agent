## 三、整合建议

### 3.1 三文档定位分工

```
方案书（可行性论证层）
  ├─ Why：为什么做（教学痛点、目标用户）
  ├─ 可行性：技术/经济/操作三维论证
  ├─ 合规：Apache-2.0 五维合规表
  ├─ 状态：84% 完成度 + 33 次提交 + P0/P1/P2 修复
  ├─ 风险：R1-R7 风险表
  └─ 引用白皮书作为技术深度附件

说明书（产品介绍层）
  ├─ What：是什么（项目定位、核心创新）
  ├─ 功能：9 个 Agent + 9 个 MCP 工具 + 双路检索 + Strands 后端
  ├─ 场景：4 个应用场景
  ├─ 状态：量化完成度 84% + 修复清单
  └─ 引用方案书（合规/风险）+ 白皮书（技术深度）

白皮书（技术深度层）
  ├─ How：怎么实现（三进程架构、IPC、JSON-RPC）
  ├─ 核心技术：PAOR 7 节点 + Strands 集成 + 渲染池
  ├─ 安全：IPC 边界 + keyring + 审批 + SSRF
  ├─ 诚实说明：PAOR Strands 模式简化、TOFU 引导待补
  └─ 作为方案书/说明书的技术附件
```

## 四、评审翻车风险点（高优先级防范）

1. **"16 主题"vs 实际 terax-default 回归**：若评审要求现场演示切换 16 主题，无法兑现
2. **"翻译可用"vs 实际 missing 状态**：若评审要求演示选词翻译，功能存在但未命中时显示"未找到"
3. **"11 个 Agent"vs 实际 9 个**：若评审对照代码核对，会发现数据错误
4. **"TOFU 已实现"vs 实际未实现引导**：若评审要求演示首次连接指纹确认，无法兑现
5. **PAOR 在 Strands 模式下失效**：若评审专家熟悉 LangGraph + Strands 差异，追问会暴露问题

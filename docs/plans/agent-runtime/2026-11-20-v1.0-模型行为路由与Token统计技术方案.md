# 模型行为路由与 Token 统计技术方案 v1.0

日期：2026-11-20；任务：TEAM-AGENT-03；状态：待评审、未实施。基线 `f40e9d1adb06050dcabb417bc4aaefa8da5fbfe5`。本方案只扩 Strands 主链，不恢复前端第二运行时，不改变 PR56 的 D1/D6/D7 安全边界。

## 1. 现状事实与设计决策

### 1.1 已确认事实

- `src/modules/ai/lib/sidecar-config-sync.ts` 目前只同步 provider/key/baseURL/model；`agent_facade.py` 缺字段时回退温度 0.7、max tokens 2048，后端 `model_adapter.py` 虽支持这两个参数，正常 UI 链却没有完整传递。
- 主 prompt 已有模式段和教学段，但普通运维缺少机器可测试的输出 profile。现有 `/skill:`、教学模式和 `suggest_command` 匹配不是通用顶层意图路由。
- `reasoningText` 已能流经 sidecar 到 UI，但没有请求级思考开关、深度和 Provider 参数白名单。
- `_extract_tokens` 已能提取多类 usage，前端只在主响应结束后累计到全局内存 `agentMeta`；会话切换不恢复历史，total/reasoning 映射和追加轮边界不完整。
- `ModelsSection.tsx`、`AiMiniWindow.tsx`、会话 store 和配置同步 generation/readiness 防护可复用，不需要新框架。

### 1.2 核心决策

1. **代码保证确定性，模型只负责受约束生成。**权限、路由、参数白名单、配置快照和 usage 幂等由代码负责；低温不被宣传为绝对确定。
2. **单入口、纯函数、窄接线。**新增 `turn_policy.py`、`model_params.py`、`usage.py`，`adapter.py` 只调用，不复制调度或审批逻辑。
3. **不主动诱导或新增保存隐藏思维链。**prompt 要求简短结论和关键依据；路由记录枚举原因。Provider 已返回 reasoning 的展示与既有日志保持现状，D6日志治理另案，不在本需求中宣称不再记录。
4. **能力与应用状态分离。**Provider 能做什么、用户想配置什么、本次实际应用什么分别是 `capabilities/request/applied`。
5. **真实 usage 优先，未知不为零。**估算只作独立辅助显示，绝不和实报混加。

## 2. 运维输出与提示词设计

### 2.1 输出 profile

| Intent | 触发 | 输出顺序 | 默认风格 |
|---|---|---|---|
| `general` | 未命中高置信规则 | 结论 → 关键依据/必要下一步 | 简短，不主动扩展命令 |
| `ops_report` | 明确巡检、状态汇总、多项检查 | 状态表 → 异常项 → 首选处理 → 验证 | 先异常后正常，不堆解释 |
| `diagnose` | 明确报错、故障、异常排查 | 最可能原因 → 首选检查/处理 → 验证 → 条件化备选 | 一个首选，备选只在有价值时出现 |
| `command` | 明确要求生成或执行运维操作 | 首选命令 → 必要风险/审批 → 验证 → 必要回退 | 命令直接，不给等价命令清单 |
| `teach` | 用户显式教学模式 | 沿用现有教学命令卡和真实结果等待 | 不另造教学路由或工具权限 |

显式 `/skill:` 继续走现有入口，权限模式始终来自用户选择。高置信规则只匹配明确动词和上下文，不以单个“error”“生产”等词盲目分类；未命中一律 `general`。规则命中只返回 `intent/profile/reason`，不改变工具 schema、模型、权限或连接。

### 2.2 Prompt 约束模板

基础约束追加到现有 system prompt，而不是重写全部运维提示词：

- 默认只推荐一个首选方案，选择顺序为安全、稳定、可逆、影响面小、步骤少、容易验证。
- 首选足以回答时不列备选；故障复杂、首选失败或用户要求比较时，最多展开少量有实际差异的方案。
- 每个方案必须说明适用条件、验证方式；写操作还需说明影响与回退是否可行。
- 不输出“我详细推理如下”或隐藏思维链，只给简短关键依据；环境或执行结果未知时明确未知。
- 生产环境变化时重新依据实时状态选择更安全、简便、直接的办法，不沿用过期命令或假设。

用快照和机械后处理保证关键格式，不能只靠模型自觉。教学模式继续复用现有 marker 补正思路；普通模式先做 schema/结构校验，不合格时优先返回简短骨架，不额外调用模型重写。

### 2.3 温度与微调路线

建议命令/常规运维默认 `0.0–0.1`，诊断仍保持低温；多方案比较只有用户显式要求时才允许独立 profile，不默认提高温度。具体默认值在离线基准中对比 `provider_default/0/0.1/0.2` 后冻结，能力不支持的模型为 `null`。

微调不是第一阶段。顺序固定为：输出合同 → 参数与规则 → 离线评测 → 数据缺口分析 → 独立微调方案。只有合法脱敏数据、可复现基准和显著收益同时成立才进入微调，不把少量提示词样例包装成训练集。

## 3. 类型化配置与 Provider 能力合同

### 3.1 中性配置

    ModelGenerationConfig {
      temperature: number | null,
      maxTokens: number | null,
      thinking: "provider_default" | "on" | "off",
      reasoningEffort: "provider_default" | "low" | "medium" | "high"
    }

    ReasoningDisplayPreferences {
      showReasoning: boolean
    }

`maxTokens=null` 表示用户未显式指定，不代表所有 Provider 都省略：OpenAI/OpenAI-compatible/LiteLLM 可省略；Anthropic 使用应用默认值 8192，并在回执中分别记录 `requestedMaxTokens=null`、`effectiveMaxTokens=8192` 和 `source=application_default`。任何 Anthropic 配置的 `effectiveMaxTokens` 都必须为正，思考预算必须小于该值。

`thinking` 和 `reasoningEffort` 只表达用户意图，不能直接拼进任意 Provider 请求。`showReasoning` 是纯前端展示偏好，不进入 `agent.configure`、`LLMConfig`、`model_params.py` 或模型工厂，也不触发模型重建；模型参数的 `applied/warnings` 不包含该显示开关。

建议新增 `ModelCapabilities`：`temperatureRange`、`supportsThinkingOff`、`supportedEfforts`、`reasoningParameterStyle`、`usageFields`。发送能力只能来自代码中已验证的 Provider+model 映射；未知端点使用未知默认。用户声明在MVP只能改变自定义显示名称和说明，不能把未知端点提升为可发送白名单，也不通过自动付费请求探测。

### 3.2 参数映射

`model_params.py` 作为唯一映射点：

- OpenAI/OpenAI-compatible：温度/max tokens 沿用现有参数；reasoning 只对白名单模型映射为实际字段，未知端点不发送。
- Anthropic：独立映射 thinking/budget；`maxTokens=null` 使用上述应用默认正值，用户给值则校验为正值，思考预算必须小于 `effectiveMaxTokens`。
- LiteLLM：只使用已验证的中性字段，不允许任意 `providerOptions` JSON 穿透。
- 不支持或未知：省略对应可选参数并返回 `applied=false + reason_code`；Anthropic 的应用默认 max tokens 不属于“未发送”。配置可保存但 UI 不得把未应用项显示为“已生效”。

`agent.configure` 继续先构造后发布，返回脱敏后的 `requested/effective/applied/warnings`。UI 的温度、max tokens、思考选项和说明都以该回执为准；showReasoning 仅由前端 store 控制。

### 3.3 配置链与快照

模型生成参数链为 `Preferences.modelGeneration` → `SidecarLlmConfig` → `agent_facade.configure` → `LLMConfig` → `model_params.py` → 三个 Provider 工厂。显示偏好链仅为 `Preferences.reasoningDisplay` → 前端 `sidecar-adapter`/UI，不经过模型RPC。所有模型字段做范围校验和旧配置迁移；API Key 继续走现有 keyring/内存链，不进入 applied 回执或 usage。

每轮保存 `ModelTurnSnapshot {provider, requestedModel, resolvedModel, requestedMaxTokens, effectiveMaxTokens, generation, applied, configGeneration}`。配置变更只影响新回合；在飞请求和迟到事件继续携带旧 snapshot ID。

## 4. Token 数据架构

### 4.1 事件合同

    UsageEvent {
      eventId, requestId, turnId, sessionId, callSequence,
      provider, requestedModel, resolvedModel,
      inputTokens, outputTokens, cacheReadTokens,
      cacheCreationTokens, reasoningTokens, totalTokens,
      inputTokenSemantics, source, status,
      startedAt, completedAt, latencyMs, firstTokenMs,
      configSnapshotId, errorCategory
    }

Token 字段可空；`source=provider_reported` 才能进入实报汇总，`local_estimate` 单独保存或仅瞬时显示。事件不包含 prompt、response、命令、工具输出、工作区路径、SSH 用户/主机、API Key 或自由文本错误。

### 4.2 调用边界与幂等

将现有 `_extract_tokens` 抽到 `usage.py`，保留 metrics/cycles、prompt/completion 别名和缓存字段兼容。每个实际模型调用产生唯一 `eventId`；同事件重放唯一约束去重。明确区分：

- 单次模型调用 usage；
- 一个用户回合的多个工具循环/续跑 aggregate；
- 流式 step delta。

不得同时把 aggregate 和其组成 delta 加入总计。max tokens 续跑、todo/写后验证追加轮、取消、异常和前端 degraded 分支均先补合成反例，不能默认 `latest_agent_invocation` 已覆盖全部。

### 4.3 存储与汇总

MVP直接建立独立 `.tdsf-data/usage.db`，不复用D6/D7日志或审计副本，也不引入cc-switch代理日志系统：

- `usage_events`保存最小化UsageEvent，`eventId`唯一索引提供跨重启、迟到重放幂等；日期、Provider、模型、会话字段均可查询，支撑设置页筛选和短期趋势。
- `session_usage_summary`保存每个会话的长期汇总和最近请求，明细到期清理不得让其归零；汇总由事件增量更新并以事件重放对账。
- sidecar提供只读汇总/趋势RPC和入账后失效事件，前端会话store与设置页使用同一数据源。`SessionMeta.usageSummary`只能作为可选缓存/旧版本迁移载体，不是跨重启去重或趋势的唯一真源。
- 后续需要日汇总时增加独立rollup，保留会话汇总；不得复制cc-switch丢失session维度的归档方式。明细保留期按PRD开放项确认，清理只删明细，不删除持久化去重所需的轻量水位/事件ID账本。

实报总量展示input/output/cache分项，同时给出Provider total（若存在）和统一计算口径；不同协议的input是否含缓存由 `inputTokenSemantics` 标明。缓存命中率只在分母已知时计算。

## 5. UI 设计

### 5.1 模型设置

在 `ModelsSection.tsx` 的默认模型附近增加“生成与思考”：

- 运维默认值摘要、温度/Provider 默认、max tokens、思考开关、深度、思考显示。
- 支持状态徽标和禁用原因；保存后显示实际应用回执，失败回滚。
- 复杂参数显式保存，简单显示开关可即时保存；提供“恢复稳定运维默认值”，但不自动修改 Provider/key/model。
- 不提供任意 JSON 主入口，不在摘要显示 Key。

风格沿用当前设置行、卡片、黑白灰和现有控件，不复制 cc-switch 多 CLI Provider 卡片体系。

### 5.2 会话摘要与设置汇总

会话摘要复用 `AiMiniWindow`：最近请求、会话输入/输出/缓存、实报/估算徽标、按模型拆分和参数快照。没有数据时显示“尚无实报”，不是 0。

设置页增加“用量”分节：日期/Provider/模型/会话筛选，请求数、Token 分项、缓存命中率、短期趋势和详情 Drawer。MVP 可用现有 CSS/SVG，不为了图表立即新增 Recharts；若后续图表复杂度证明需要，再单独评审依赖。

刷新采用 usage 入账后的事件失效，窗口隐藏时降低无意义刷新。成本不进入首版主卡片；未来若增加只能标“本地估算”，记录价格来源和日期。

## 8. 测试与验收分层

- 纯函数：参数白名单、0 值/null、能力禁用、路由默认、权限不变、usage 归一化与幂等。
- 跨层：UI→同步→RPC→工厂，配置构造失败不发布，旧回合 snapshot 不被新配置污染。
- 假服务：本地 SSE 含 usage、reasoning、续跑、异常和取消，不接真实付费模型。
- 前端：设置迁移、保存回滚、会话恢复、筛选、空/错/未知、实报与估算隔离。
- 风格基准：同一合成运维问题集比较基线和新策略，评估首选唯一性、结构、命令有效性、安全性和冗余；低温重复试验只作为稳定度证据之一。
- 原生/真实模型：只有队长另行授权环境后执行，和自动测试分开报告。
